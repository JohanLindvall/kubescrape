## Commands

```sh
make build              # build to bin/kubescrape
make test               # go test ./...
go test ./internal/store/ -run TestWaitIsPerContainer -v   # single test
make vet fmt tidy
make lint               # golangci-lint v2 (auto-installed to GOPATH/bin; config .golangci.yml)
make image              # docker build; service is CGO_ENABLED=0 static, agent is CGO_ENABLED=1 (libsystemd/journald) on distroless/base; release binaries strip -s -w (~30% smaller; panic traces unaffected — the runtime reads pclntab). `make build` stays unstripped for delve/gdb.
make build TAGS=azure   # optional-pipeline build tags; TAGS defaults to journald,azure
make verify-tags        # the guard: no cgo without journald, no franz-go without azure — and, in its third command, the only step of `make check` that COMPILES the tag-less variant, hence the only one that type-checks `azure_disabled.go`
make image-static       # Dockerfile.static: no journald ⇒ both binaries static on distroless/static
make check              # fmt-check → vet → lint → helm-lint (bootstraps helm into hack/bin via hack/ensure-helm.sh) → test → verify-tags. It vets/lints/TESTS the DEFAULT tag set and COMPILES every variant's stubs (verify-tags now ends with a tag-less `go build`, which is the only step that type-checks `azure_disabled.go` — the `-tags azure` build covers `journald_disabled.go`, and the franz-go half is a `go list -deps`, which resolves imports without type-checking). CI adds two things on top: the tag-less variant's TEST run (`make build test TAGS=`) and the `-race` pass below. Not "the whole local CI story" — that phrasing is what let a file go uncompiled by every step.
make e2e                # kind smoke test (hack/e2e.sh): image build+load, shipped deploy/*.yaml + collector fixture, asserts readiness gates, target discovery, a container-ID store lookup, telemetry arriving at the collector, and the PROTOBUF scrape path (below). KEEP=0 tears the cluster down, SKIP_BUILD=1 re-runs against the loaded image
make chaos              # the four chaos scenarios (hack/chaos/*.sh) against whatever `make e2e` left running: collector outage, agent SIGKILL, kubelet log rotation, API-server blackhole. Minutes each (real outages), so deliberately NOT part of `make check`
```

**Docs are guarded like the manifests.** `docs/FLAGS.md` is GENERATED per binary from the registered flag sets (`flagsdoc_test.go` in each cmd package; regenerate with `go test ./cmd/<binary> -run TestFlagsDocIsCurrent -update-flags-doc`) — defaults there cannot drift. `TestFlagsAreMentionedInConfigurationDoc` (same files) fails when a registered flag is never mentioned in CONFIGURATION.md, and `internal/docscheck` fails when a doc TABLE documents a flag neither binary registers — the prose siblings of `internal/manifestcheck`. `internal/chartcheck` pins the RENDERED chart against golden files per value fixture (helm from hack/bin or PATH, but only at the version pinned in `hack/helm-version` — helm MAJORS differ in rendered whitespace, so an unpinned binary reports a diff no template change caused; skips without a matching one, FAILS instead when `CI` is set; regenerate an intended template change with `go test ./internal/chartcheck -run TestChartGolden -update-chart-golden`) — which is what guards template logic like the `logsExcludeNamespaces` derivation that text-reading `manifestcheck` cannot see.

**Optional-compilation build tags** (`cmd/kubescrape-agent/buildtags.go` + the `*_enabled.go`/`*_disabled.go` file pairs). Two agent pipelines are behind POSITIVE tags — `journald` and `azure` — and the DEFAULT IS CARRIED BY THE MAKEFILE, not by the constraint: `TAGS ?= journald,azure`, passed by `build`, `test`, `vet`, `lint` and `image`, so the shipped binaries and image are exactly what they always were. **The corollary bites: a bare `go build ./cmd/kubescrape-agent/` (or `go test`, or `go vet`) has NEITHER pipeline** — always go through `make`, or pass `-tags` yourself. The mechanism is the file-level import: `startJournald`/`startAzure` live in the tagged pairs, so a tag-less build never names `internal/agent/journald` or `internal/agent/azurediag` and the linker never sees them. Dropping `journald` removes the agent's ONE cgo dependency (below), so it then builds CGO-free and fully static; dropping `azure` removes 11 franz-go packages (~5 MB stripped) shipped in every DaemonSet image for a feature that only ever runs in the singleton Deployment. **The FLAGS never disappear** — `internal/manifestcheck` asserts every flag the shipped manifests pass exists, and the chart passes both, so a vanished flag would turn a diagnosable refusal into `flag provided but not defined` + exit 2 for exactly the deployments most likely to use it. Instead `-journald`/`-azure-diagnostics` on a build that lacks the pipeline is a startup error naming the tag and the rebuild, raised from `validateConfig` so `-check-config` catches it before a rollout does, and mirrored by each stub (one constructor returning an error — never a fake implementation). No `-config` section belongs to either pipeline, so a shared ConfigMap stays decodable by every variant; only ENABLING fails. Which binary you have is on the startup log line and in `-check-config` (`optionalPipelines=journald,azure` / `=(none)`). The package's OWN files are untagged, so `go test ./internal/agent/journald/` passes under any tag set.

`CGO_ENABLED=1 go test -race ./...` works (gcc is available); run it for concurrency-touching changes (store, metaclient cache, otlpingest). The concurrency tests in `internal/store` and `TestEnricherConcurrent` are the targeted exercises.

**Benchmarks use `b.Loop()`, and every allocation budget is ALSO a Test.** A benchmark cannot fail a build (`go test ./...` runs each for zero iterations), so an invariant that lives only in a `bench_test.go` comment is documentation, not enforcement — the budgets are asserted by `TestXxxAllocationBudget` / `TestXxxIsAllocationFree` with `testing.AllocsPerRun` and an explicit ceiling (tailer line + flush, log-metrics matched/no-match/histogram, promparse per-sample, promscrape's filter session, logscrub no-match, spanmetrics Consume, servicegraph Record + paired/unpaired Consume, tailsample Decide, tailbuffer late-drop). `b.Loop()` rather than `for i := 0; i < b.N; i++` because the old form lets the compiler eliminate a body whose result is unused — the exact failure mode for a benchmark claiming zero allocations. Those budget tests SKIP under `-race` (`internal/testrace.Enabled`, ONE build-tagged const package imported only from _test files — it replaced eleven per-package `race_test.go`/`norace_test.go` pairs whose mis-copied tag would have silently un-skipped a budget under `-race`): the detector changes escape analysis and adds bookkeeping allocations, and widening a ceiling to survive it would let a real regression through.

### End-to-end verification (kind)

**The collector fixture CAPTURES payloads, not just summaries.** `hack/otel-collector.yaml` runs the debug exporter (whose summary lines the e2e greps) AND a FILE exporter per signal, plus a busybox `reader` sidecar that exists solely so assertions can `kubectl exec -c reader -- cat /data/<signal>.json`: the collector image is distroless, so exec/cp into it fail (no shell, no tar). At the fixture's `verbosity: normal` the debug exporter prints a summary line per push AND one line per item — a log record's BODY plus its record attributes, a metric data point's NAME plus its data-point attributes — which is what `hack/e2e.sh`'s `negotiating_scraped` greps for and why lowering that setting to `basic` (whose push functions return before the marshaler runs) breaks the run with no hint why. What it never prints below `detailed` is the RESOURCE: normal's marshalers walk ResourceLogs/ResourceMetrics only to reach the leaves. So stdout can prove data ARRIVED and that a name or body is present; only the captured payload can prove a RESOURCE ATTRIBUTE has the right VALUE. Two traps that cost real time: never truncate those files in place (the exporter holds an open fd at its own offset, so a truncate leaves a sparse file and every later line count lies — delete the collector POD for a clean slate, which also gives it a fresh emptyDir), and a reader that stops early makes `kubectl` die of SIGPIPE, which under `set -o pipefail` reads as "no data" exactly when the data is there (the script documents this for `grep -q`; it applies identically to a Python filter that exits on first match).

**Native histograms have a FIXTURE, because no shell one-liner can serve them.** `hack/nhexporter` is a real client_golang target: native-histogram fields exist ONLY in the protobuf exposition, and promhttp negotiates that from the scraper's Accept header — which is what the agent sends under `-scrape-native-histograms`. It also exposes a classic histogram, an exemplar-bearing counter, a gauge and a summary, so ONE target proves the protobuf path converts every family kind and honours `-scrape-exemplars` there too. `FORCE_PROTO=1` makes it answer protobuf whatever was asked: that is the MISBEHAVING target the agent must refuse when the operator has not opted in, since the decode materialises the whole message and is gzip-amplified — the format is the operator's choice, never the target's. It lives in the main module (client_golang is already a direct dependency via `internal/obs`), so it costs no new deps and is covered by `make vet`/`make lint`. The e2e asserts all three: the refusal, that a WELL-BEHAVED target is unaffected (it negotiates down to text — the refusal must be a targeted guard, not collateral damage), and that schema→scale plus span/delta→dense buckets actually converts.

**Chaos scenarios** (`hack/chaos/*.sh`, `make chaos`) run against the SHIPPED deployment `make e2e` leaves up — no bespoke overlay, so what they prove is what an operator gets. They all assert the same universal invariant, and it is the only one that can be asserted honestly: **NO GAP**. A writer emits densely numbered lines; at-least-once means duplicates are ALLOWED and expected (the agent-kill run routinely shows ~20, which is the checkpoint lag being re-read), but a sequence number produced and never delivered is loss. Counting deliveries cannot show that — only the numbering can. Two design rules learned by getting them wrong: the collector-outage scenario starts its writer AFTER the collector is down (scaling it to zero gives the replacement a fresh emptyDir, so anything delivered beforehand is unreadable and reads as a false loss), and the rotation scenario ASSERTS THAT IT ROTATED before asserting the invariant — the first version wrote a few hundred kilobytes against the kubelet's 10Mi default, rotated nothing, and passed vacuously. `hack/kind-config.yaml` therefore sets `containerLogMaxSize: 1Mi`, which is what makes a few megabytes cross the threshold several times; a cluster created before that setting fails the scenario with a message saying to recreate it.


Changes to informer wiring, the store, or the HTTP API should be verified against a real cluster, not just unit tests:

```sh
make cluster-up         # 3-node kind cluster; downloads kind/kubectl into hack/bin; deploys hack/test-workloads.yaml
go run ./cmd/kubescrape # uses the kind kubeconfig context
make image && hack/bin/kind load docker-image ghcr.io/johanlindvall/kubescrape:latest --name kubescrape
kubectl apply -f deploy/kubernetes.yaml   # in-cluster deployment (namespace: monitoring)
make cluster-down
```

`hack/test-workloads.yaml` intentionally exercises every code path: a pod-annotated Deployment (ReplicaSet→Deployment chain, pod-source targets), a non-annotated Deployment behind an annotated Service with a named `targetPort` (service-source targets), a CronJob (Job→CronJob chain), plus a StatefulSet and a DaemonSet (direct-owner chains).

## Public packages (`pkg/`)

`pkg/promparse` (the exposition parser — `internal/agent/promscrape` aliases its types in `promparse.go`), `pkg/kubemeta`, `pkg/metaclient`, `pkg/logattrs`, `pkg/otlpsplit` (size-bounded OTLP payload splitting) and `pkg/cgroupid` (cgroup path → pod/container identity) are importable by other modules. **They must never import `internal/`** (Go would allow it inside this module but break every external consumer) — the boundary is worth re-checking when adding code there. `metaclient` deliberately has no metrics dependency: the agent passes `Config.Observe` to bump `obs.MetadataRequests`. Its constructor is `New(Config)` like every other constructor in this repo — Base/Timeout/Observe/ScrapeAuthToken/Transport, so nothing is assigned to a `Client` after construction (the old public `Observe` field and `SetScrapeAuthToken` setter each carried an unenforced "install it before you share the client" contract) and the tuned transport is overridable via `NewTransport()`. A response this client cannot decode returns a typed `*DecodeError` naming the package and the URL, not encoding/json's bare `invalid character` — the sibling failure paths were typed and this one was not. `kubemeta.PeerIP` moved OUT to `internal/peerip` (it parses an HTTP RemoteAddr and has nothing to do with the metadata model; the one implementation is still shared, because the /v1/self attribution and the agent's peer-IP fallback must key the pod-IP index identically), and `logattrs.LoadConfig` moved into that package's _test file like every other standalone loader — it did file I/O and dragged `os` + `sigs.k8s.io/yaml` into a public package for a function only its own test called.

## Shared internal primitives

Decisions that more than one package needs live in ONE package each. Reach for these before writing a fourth copy of something:

- **`internal/bearer`** — "a bearer token lives in a mounted file that rotates under us". `Rotating.Tokens` does its re-read with the mutex DROPPED (an auth check must not serialise behind a slow projection) but claims the refresh slot with a FLAG, never a deadline: a timestamp claim expires while a read is still blocked, so on a wedged mount every interval starts another blocking read, each pinning an OS thread, and the process reaches the runtime's fatal 10000-thread limit in hours — strictly worse than the one pinned thread holding the lock produced. `File` is the CLIENT half (the token this process presents: per-interval re-read, and a FAILED re-read keeps the last good value), `Rotating` is the RECEIVER half (the accepted set: current file contents plus its predecessor for a grace window), `Authorized`/`Parse` are the constant-time header check (every candidate compared, no early exit, an empty candidate never authorizing). There were FIVE implementations and they disagreed on the decision that matters: two kept the last good token across a swap window and two failed the operation (the OTLP export, the kubelet scrape). What is deliberately NOT unified is the fatality of the INITIAL read — `NewRotating` reads fatally because a receiver must never open a listener with an empty accept set, `NewFile` does not read at all and callers that want a fatal first read call `File.Read`. Out of scope: `azurediag/auth.go`'s connection string and Entra token source, which refresh against an issuer's expiry rather than a file mtime.
- **`internal/config`** — `config.Duration(field, value, def, opts...)` is the one reader for an optional Go-duration config STRING (the agent's YAML decodes through encoding/json, which takes only raw nanoseconds for a `time.Duration`, so every duration in a config section is a string parsed by hand). Empty takes the default; a NEGATIVE value is always an error naming the field and the value; an explicit `"0"` is legal and means "off" unless the call site says `config.Positive(why)`, which folds the follow-up bound check and its explanation into the same error. Not in scope: prometheus-operator's `y/w/d` CRD syntax — a different input language, owned by `internal/promdur`.
- **`internal/promdur`** — prometheus-operator's `y/w/d/h/m/s/ms` duration syntax: the ONE parser the metadata service's monitor merge (which picks the "finer" explicit interval) and the agent's scraper (which schedules by that interval) must agree on. They were byte-identical copies held equal by nothing, and their `"0"` edge semantics had already split — that split is now EXPLICIT at the call sites (merge: non-positive is not a usable interval, the holder keeps; scraper: warn-once fallback), while the regex, unit table and overflow guards live once. `internal/config.Duration`'s sibling, not a competitor.
- **`internal/cli.RegisterOTLPFlags`/`RegisterObsFlags`** — the flag blocks BOTH binaries register (the nine shared `-otlp-*` flags; `-metrics-listen`/`-pprof-listen`/`-self-metrics-interval`/`-log-level`/`-log-format`) are registered once, the two genuinely different help hints as parameters; `flags_test.go` pins the set, and `internal/docscheck` scans `internal/cli` too, so cross-binary default drift is structurally impossible (the help text had already micro-drifted). Same move one level down: `otlpingest.DefaultContainerIDKeys`/`DefaultPodUIDKeys` build the `-ingest-*-keys` flag defaults, and `tracesample.Config.SlowerThan` is the one parse of `keepSlowerThan` that `configWarnings` reads through instead of re-parsing. `config.Glob` owns the parse-time `path.Match(pat, "")` probe (a malformed glob otherwise reads as silent no-match at runtime) for routing validation, tailer source namespaces and the debug tap's filters.
- **`internal/logdedupe`** — "throttle a complaint about a persisting STATE, so it does not become a flood proportional to fleet size". Both binaries complain about conditions rather than events (a monitor field the scraper cannot honour, a Secret ref the service cannot resolve): the condition persists, the noticing code runs every cycle for every target on every node, and the useful information is one line. `Throttle` is the KEYLESS half (one atomic + CAS, no mutex; the rule three hand-rolled copies each re-derived is that the LOSER of the race must stay silent — logging on a lost CAS is the duplicate the throttle exists to prevent), `Table` the bounded per-key half. The decision the two written copies disagreed on is settled here: **saturation SUPPRESSES, it never clears**. The metadata service's copy aged entries out and then cleared the map, so at cap+1 distinct keys every key logged on every cycle forever — worse than the unbounded map the cap replaced, and silent about it, since a cleared table cannot be told from a genuinely new key. An existing key still re-warns on schedule under a full table (the cap refuses only NEW keys).
- **`internal/agent/tracehash`** — the nesting-critical trace-ID sampling arithmetic shared by the head sampler (`agent/tracesample`) and the tail sampler's `probabilistic` policy (`agent/tailsample`), plus the spans/second `Bucket` both rate caps are built on. Both stages hash the trace id UNSALTED against the same threshold arithmetic, so they NEST rather than compound (a 50% tail policy keeps exactly what `probability: 0.5` already passed) and every trace decides identically across shards, retries and restarts — whole traces, never halves. `Threshold` takes a FRACTION (tailsample's percent policy passes `pct/100`) so both sides round bit-for-bit identically. The Collector's decorrelating hash salt is deliberately NOT implemented. The two copies were held equal only by cross-package tests and had already micro-drifted: the `threshold == MaxUint64` keep-all guard existed on the tracesample side only, so `samplingPercentage: 100` dropped the one trace in 2^64 hashing to exactly MaxUint64. **Two hash FUNCTIONS live here on purpose, now from one library** (`github.com/JohanLindvall/haste`). Identity hashing — where a collision silently MERGES two objects' data — uses `haste/xxh3` at 128 bits: the log-metrics series key (`metrics.strHash`), the HTTP ETag (`server.bodyHash`, where a collision serves a 304 for a body that changed) and the disk buffer's stuck-payload key (`otlpexport`, where a collision pools two payloads' poison budgets and can drop a healthy batch). Everything that hashes for DISPERSAL rather than identity uses `haste/rapidhash`, a 64-bit hash with no vector unit at all: this package's sampling threshold, where 128 bits buy nothing (the comparison is against a 64-bit threshold), plus `logline`'s per-line selector memo and the tailer's `obsKey` body hash. Do not "unify" the two without that argument — the split is identity-vs-dispersal, not library availability. **The migration off zeebo/xxh3 + cespare/xxhash was two different changes wearing one commit.** The 128-bit half was VALUE-PRESERVING: haste's XXH3 is bit-identical to zeebo's (both track the reference implementation; verified over 600 inputs across every size class including the 240-byte seeded-secret boundary), so series keys, ETags and stuck-payload keys all kept computing the same numbers and nothing churned. The 64-bit half was NOT: rapidhash is a different function, so it RE-ROLLED which traces are sampled — see tracehash's own doc, which now carries that hazard. On the measured machine the identity half is a wash (interleaved n=6: zeebo 5.2-10.4ns, haste 6.1-13.3ns on a short label — the ±2x machine noise swamps it, so do not quote a win there), while the sampling path is ~12.9ns → ~5.6ns (about 2.3x) because a trace id can be fed to `rapidhash.Sum64Uint128` as two registers instead of a slice. That pair is an IN-BINARY A/B on the real `Keep` with varying ids; the commit that landed this quoted 12.6 → 2.4 (~5x) from an isolated microbenchmark over a CONSTANT id, which flatters the cheaper function — a reminder that a hash benchmark with a fixed input measures branch prediction as much as the hash. Out of scope: `servicegraph`'s `ring.TokenFor`, which is Tempo's FNV-1 ON PURPOSE (it must place spans where Tempo's would, and must NOT correlate with the sampling hash), and the tailer's `allowLine`, whose per-file bucket is unsynchronised by design.
- **`internal/agent/logchain`** — the log-record chain and its key resolver; see the agent section below.
- **`otlpingest.BodyReader`** (`httpbody.go`) plus `WriteBodyError`/`WriteProto`/`GRPCForwardStatus`/`HTTPForwardStatus` — the OTLP/HTTP request seam every receiver in this repo uses. The CAP is a parameter (16 MiB for application pushes, 4 MiB on the trace tier's internal hop) and the byte budget is optional (nil = no accounting, which is what the tier's authenticated receiver wants).
- **`servicemonitors.Endpoint.secretRefs`** — the one list of secret-bearing endpoint fields, used by both monitor parsers (namespacing) and by `AuthSecretRefs` (allowlisting). It is a security boundary: a new field updated in two of the three places used to fail only at runtime, with `up=0` as the only signal.

## Architecture

Two binaries: `cmd/kubescrape` (metadata service) and `cmd/kubescrape-agent` (per-node DaemonSet: log tailer + Prometheus scraper exporting OTLP). Both live in one image; the DaemonSet overrides `command: ["/kubescrape-agent"]`.

### Metadata service

`cmd/kubescrape` serves Kubernetes pod/container metadata over HTTP. Everything is driven by one initial LIST + WATCH per resource (client-go informers); there is **no per-request API-server traffic**.

Data flow:

- **Pod informer** (full objects) → `internal/store.Store`: pods keyed by UID, with FOUR derived indexes — normalized container-ID → entry, nodeName → pods, `byPodName` ("ns/name", carrying the same-name-replacement guard a missed delete would otherwise leak through), and `byPodIP` → the live claimant, backed by `ipClaimants` (EVERY record reporting an address, so a release can promote a survivor without an O(pods) scan under the write lock). The IP indexes have the most delicate lifecycle rules in the package — claim, release, promote, and the `ipSeq` acquisition ordering — and `podip_delete_test.go`/`ipclaimants_test.go` exist to pin them. The informer transform (`trimPod`) strips `managedFields` and, for PODS ONLY, the bulk of the spec that never reaches `kubemeta.Pod` (env, volumes, probes, resources, tolerations); Service specs are left intact because `services.Index` reads them, and `TestTrimPodPreservesEverythingFromPodReads` is what keeps the two in step.
- **Service informer** (full objects) → `internal/services.Index`: selector-based matching of Services to pods, for service-annotation scrape discovery.
- **Metadata-only informers** (`PartialObjectMetadata`, cheap) for ReplicaSets, Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, Namespaces, Nodes → `internal/owners.Resolver`. StatefulSets and DaemonSets own their pods DIRECTLY (no intermediate object), so they are cached for their labels/annotations, not for a chain to follow. Owner chains and namespace metadata are resolved **lazily at request time** from these caches, never stored on the pod record. Adding a new owner kind means extending `owners.AllGVRs` + `kindGVR` and the ClusterRole in `deploy/kubernetes.yaml`. **Readiness gates on the HANDLER REGISTRATIONS' `HasSynced`, never the informer's** (`registerCoreInformers` returns `podReg.HasSynced`/`svcReg.HasSynced`): the informer's flips when its DeltaFIFO drains, which says nothing about whether OUR handlers have run, and the store and service index are filled from inside those handlers — so gating on the informer let `/readyz` report 200 while the store was still filling and an agent's first poll got a half-built target list. Owner informers are the exception and legitimately use the informer's, since their lister reads the informer's own indexer. The ServiceMonitor/PodMonitor informers are BOTH gated (`startServiceMonitors` returns a combined func); the PodMonitor one was created and started but never awaited, so a missing `podmonitors` RBAC rule 403-looped forever behind a green `/readyz`. A discovery error is FATAL rather than read as "the CRD is absent" (`monitoringResources` returns `(map[string]bool, error)`: only a genuine NotFound/NoMatch becomes an empty map, every other error propagates. It reports the RESOURCE NAMES rather than a bool because a cluster can serve other `monitoring.coreos.com/v1` kinds without `servicemonitors` itself, and a group/version check alone would read that as present): one 503 from a rolling API server used to disable an explicitly-requested `-servicemonitors` for the process lifetime. `-monitor-namespaces` restricts WHICH namespaces' monitors are honoured (empty = all, the historical default): a monitor is an instruction to every agent to issue a GET, and without an admin-owned gate anyone who can create a ServiceMonitor in their own namespace can point `selector: {}` + `namespaceSelector.any: true` at an arbitrary path cluster-wide. The gate applies at INDEXING time so a refused monitor never widens `AuthSecretRefs`. **Readiness LATCHES, and the compensating signal is a REACHABILITY PROBE, not the watch-error counter** (`cmd/kubescrape/apiserver.go`, `-apiserver-probe-interval`, default 30s, 0 disables): latching is deliberate — flipping `/readyz` during an API-server outage would drop the pod from its Service endpoints and cut every agent off a cache that is still serving useful data — but the metric that was documented as the alarm for a cache that has stopped advancing does not fire for the likeliest outage. client-go reaches `watchErrorHandler` only when `ListAndWatchWithContext` RETURNS (reflector.go:429); a refused connection is classified retriable and `continue`s inside `watchWithResync` (~607) without ever returning, and a broken stream logs "Warning: watch ended with error" at INFO and returns nil (~665). A failed RELIST does return and does count — but while the server is unreachable the reflector never gets that far: measured silent across four outage shapes up to five minutes, with one real outage stepping the counter five seconds AFTER recovery. So the watchdog issues a `limit=1` metadata list of Namespaces (already-watched resource, no new RBAC; no `resourceVersion`, so it fails when etcd does instead of being answered from the watch cache), publishing `kubescrape_apiserver_reachable` + `kubescrape_apiserver_probe_failures_total` with a transition WARN, a throttled re-warn and a recovery INFO. Alert on it SUSTAINED: it measures whether a NEW connection reaches the API server, which neither proves the caches are advancing (a blackholed established watch probes healthy) nor that they stopped. And the store gauges are no help either — the sweeper keeps expiring tombstones, so `kubescrape_store_pods` DECAYS during an outage (89 → 85 over five minutes) rather than freezing, so a flat-gauge staleness alert reads healthy exactly when it must not.
- **ServiceMonitor CRDs** (opt-in `-servicemonitors`, dynamic informer over unstructured) → `internal/servicemonitors.Index`. A discovery pre-check disables the feature gracefully when the CRD group is absent. Targets resolve monitor → Services (label selector over `services.All(m.ServiceNamespaces())`) → pods (the existing service selector matching), so scraping stays node-local; `scrape.MonitorTargets` handles endpoint `port` (service-port name) / `targetPort` (pod port) / `path` / `scheme` and stamps `Source: "servicemonitor"` + `Monitor: "ns/name"`; an endpoint naming NEITHER port nor targetPort resolves to nothing (an empty `port` must not match a Service's unnamed port by `""==""` and fabricate a phantom target, as prometheus-operator emits no config for it). **PodMonitors** select PODS directly (same `-servicemonitors` gate; watched when the CRD is served): `scrape.PodMonitorTargets` resolves endpoint `port` (container port NAME) / `targetPort` (number or name), `Source: "podmonitor"`. **Endpoint auth/TLS/relabelings** interpreted: `basicAuth` (username/password secret refs), `authorization` (type + credentials), `tlsConfig` `ca`/`cert`/`keySecret` (SECRET-backed only — the configMap arm is reported as ignored, since the agent reads secret keys through one channel) and `serverName`, plus the keep/drop relabel subset: `tlsConfig.insecureSkipVerify` → per-target skip-verify client; every credential rides as a `"ns/name/key"` ref (namespaced with the MONITOR's namespace, so a monitor can only name secrets in its own namespace — that is what bounds `AuthSecretRefs`, the allowlist keeping `-scrape-auth-secrets` from being a general secret-read API), resolved by agents via `GET /v1/scrape-auth/...`; the scraper builds a per-target `http.Client` from the resolved CA/cert/serverName (`targetauth.go`, cached by the resolved MATERIAL so targets sharing a CA share a connection pool and a rotated secret yields a new client, bounded by `maxTLSClients`) — served ONLY when the service runs `-scrape-auth-secrets` (needs secrets get RBAC; ### Invariants the API guarantees (user requirements — do not regress)

- **One pod's targets are BOUNDED** (`scrape.MaxPortsPerPod`, enforced in `server.targetDedup.add`). Every `ScrapeTarget` embeds the whole pod by value, so N targets carry N copies of its annotations and an unbounded count is an O(N²) response that OOMs the singleton. The ceiling lives where targets are ACCUMULATED, not at any single door — an earlier attempt capped only the pod-annotation resolution and a ServiceMonitor's endpoint list walked straight past it (400 endpoints → 400 targets, 3.40 MiB, needing no annotation on the pod at all; capped, 16 targets and 0.14 MiB). It is applied on the NEW-URL arm only, so endpoints merging into a URL the pod already holds are free. A refused target is not scraped, so it moves `kubescrape_scrape_targets_capped_total` on the SERVED path and `/v1/explain` names it: the count on the document's `cappedTargets` and a note where the refusal happened (a port entry loses its `ports`, a monitor endpoint keeps its resolution and gains the note), all through the one wording `scrape.CeilingNote` — or explain answers "why is my 17th port not scraped?" with "it is", which is what the Service door did, complete with "the target is still served". Only the ACCUMULATOR can name a refusal, which is why `targetDedup.add` RETURNS its verdict: with a 10-entry pod annotation beside a 10-port Service each door is individually under the ceiling and the two still overflow together, so a per-door counter is not a fix. The scrape-side mirrors carry each DOOR's own cap (`portFilter.kept` for `podPorts`, `servicePortFilter.kept` for `ServiceTargets`' break, which is checked BEFORE the resolution because the derivation breaks before resolving), and explain sets `targetDedup.diagnostic`, which keeps `d.capped` filling while suppressing the obs counter — the endpoint's contract is that it moves none.

- **Container lookups block per container ID.** An unknown ID registers a waiter channel keyed by that exact ID; the pod-upsert path wakes only those waiters. Multiple concurrent requests for the same ID are all released. Waiting is bounded by `-wait-timeout` (client can shorten via `?wait=`, never lengthen). Requests may legitimately arrive ~1s before the kubelet posts the container ID to the API server — this wait covers that gap. **A parked lookup is ANSWERED on shutdown, never dropped**: `Server.Drain` (called before `srv.Shutdown`) releases both parking spots — the store's per-ID waiters and `waitReady`'s pre-sync park, whose `ready` channel a failed `WaitForCacheSync` returns without ever CLOSING, so the park would otherwise last the whole budget — and each returns 503 + `Retry-After: 1`. Only the store half moves `kubescrape_container_lookups_drained_total` (a sibling of the shed counter, not the same series: a rolling update must not page like an abuse event); a lookup drained from the pre-sync park never reached the waiter table, so it is counted nowhere. Without it, a `-wait-timeout` longer than the shutdown step meant the process exited under the parked request and the client got an empty reply with nothing logged. Note what does NOT happen: `http.Server.Shutdown` does not close active connections when its deadline expires — it returns `DeadlineExceeded` and leaves them attached, and it was the process EXITING that cut them; the expired budget now warns with the in-flight count instead of being swallowed.
- **Deleted pods stay resolvable via the container endpoint for `-cache-ttl`** (tombstone: `expireAt` + `deletedAt` stamped, swept periodically). Container IDs replaced by restarts get the same TTL; `lastState.terminated` IDs are indexed while the pod lives.
- **Scrape targets never include deleted, finished or TERMINATING pods**: `DeletePod` removes the pod from the node index immediately, before tombstoning. `Succeeded`/`Failed` pods and pods with a `deletionTimestamp` (`kubemeta.Pod.DeletionTimestamp`, filled by `kubeconvert.FromPod` and the single source of truth for the store's `record.terminating`) are excluded by `scrape.Scrapeable` — a draining pod stays `Running` for its whole grace period, so scraping it is pure `up=0` churn, and Prometheus' endpoints SD drops those too. They all remain resolvable by container ID / UID / name: a draining pod's last logs must stay attributable. `kubemeta.Pod.Ready` (PodReady condition) is metadata only — a not-ready pod IS still scraped.
- **`prometheus.io/port` is a comma-separated list** (numbers and/or port names) on both pods and Services; service ports translate to pod ports via `targetPort`. **A port NAME resolves to exactly ONE port, and every path resolves it identically** (`scrape.containerPortByName`): the pod annotation, a Service's named `targetPort`, and a monitor endpoint's `port`/`targetPort` all take a REGULAR container's declaration in preference to an init/sidecar or ephemeral one, then the first of those. The preference is not cosmetic — `kubeconvert.FromPod` appends init containers FIRST, so plain document order handed a native sidecar (`restartPolicy: Always`, the recommended shape since 1.29) the app container's port name, which is the opposite of what `podutil.FindPort` and the EndpointSlice controller do. A name NO regular container declares still resolves from the fallback pass: Kubernetes has no answer for that case at all, so nothing is contradicted, and refusing it would stop scraping a metrics port a sidecar legitimately owns (`/v1/explain` says which case it took). The paths used to DISAGREE — the annotation resolved every declaration while a Service `targetPort` resolved only the first, so one request contained two resolutions of one name. Duplicate endpoints reachable via both pod and service annotations are deduped by URL (pod source wins; a monitor-derived target upgrades an annotation one wholesale). Two MONITORS resolving to one URL on one pod are served as ONE target that honours BOTH endpoint declarations (`scrape.MergeMonitorEndpoint`): the first monitor in encounter order (matched Service name first, then monitor (namespace, name) within each Service) names it, the second's relabel chain concatenates after the first's, the finer explicit cadence wins with its own timeout, one-sided auth/TLS is adopted whole — only auth/TLS material both declare DIFFERENTLY keeps the winner's, counted `obs.MonitorTargetShadowed{kind}`. The merged keep/drop chain is the UNION applied to the single scrape (a series any monitor asked to drop is dropped for everyone) — the documented divergence from prometheus-operator, whose job per (monitor, endpoint) scrapes twice and applies each chain to its own copy.

### Concurrency model

One `sync.RWMutex` in `store.Store` (plus one in `services.Index`) guards everything. The goroutines that TOUCH the store are the HTTP handlers, the informer callbacks, the sweeper (`Store.Run`), the cache-sync reporter (`st.Stats()` once, after `WaitForCacheSync`) and the self-metadata poller (`selfResolver` → `st.GetPodByName`, on `-self-attributes-refresh` forever) — this used to say there were "no goroutines besides" the first three, which omitted both of the background readers and contradicted the API-server watchdog described a few paragraphs up. `cmd/kubescrape` runs several more that never touch it: the watchdog (`apiserver.go`), `obs.Registry.Run`, `bearer.Rotating.Run` and the listener goroutine. Every mutation of a stored record happens under the WRITE lock — upserts replace whole records, and the one in-place field write is `DeletedAt` on the tombstone path — so returning shallow copies under RLock is safe. (The invariant is the lock, not immutability: this used to say records are never mutated in place, which would license a lock-free read path that would in fact race `deletePodLocked`.) `FromPod` deep-copies everything it takes from informer objects; never retain or mutate an informer-owned object.

Store tests use an injectable clock (`s.now`); follow that pattern for any time-dependent behavior instead of sleeping.

`t.Parallel()` is used where a package's tests are genuinely free of shared mutable state — `internal/agent/tailsample`, `internal/agent/route`, `internal/logline`, `pkg/logattrs`, `internal/peerip`. It is deliberately NOT blanket-applied: `cmd/kubescrape-agent` mutates process-global flags, `internal/metrics` still pins one shared test clock, and an `AllocsPerRun` assertion must never run concurrently with anything.

### Panics: there is no `recover()`, and none is wanted

Neither binary contains a single `recover()` — not in a handler, not in an interceptor, not in any of the ~26 goroutines — and **new code must not add one**. A panic is a bug, and letting the process die is the loudest and most honest report of it: the DaemonSet/Deployment restarts, CrashLoopBackOff is visible to anyone looking at the namespace, and the crash costs no data, because every producer's accounting is already built for a hard kill (log offsets, the journal cursor, the events position and the Kafka offsets all re-read; the disk buffer commits only after an ack; the ONE exception is `tailbuffer`'s undecided spans, which say so). A recovered panic buys none of that and costs the thing the design is built around: it leaves ONE pipeline silently dead inside a process that goes on answering `/readyz` with 200 and exporting its own self-metrics — the exact failure mode the readiness gates and per-pipeline counters exist to make impossible.

The asymmetry a review WILL rediscover, so it is written down here rather than re-litigated: **`net/http` recovers a handler panic and grpc-go does not.** `net/http`'s conn serve loop has a `recover()` (logs the stack, closes that connection, process survives); grpc-go has none anywhere in its server path, which is why `go-grpc-middleware` ships a recovery interceptor at all. So the same malformed push takes the whole process down on the gRPC arm (`otlpingest`'s `:4317`, the trace tier's application and internal ports in `cmd/kubescrape-agent/servicegraph.go`) and merely drops a connection on the HTTP arm (`:4318`) — on listeners that are UNAUTHENTICATED by design. That asymmetry is **accepted, not fixed**: an interceptor that made gRPC behave like `net/http` would convert a crash into precisely the silently-dead-pipeline case above, and it would do it on the path where a panic is most likely to mean a real parsing bug worth crashing over.

The consequence for review findings: a panic reachable from a receive path is a **bug to fix at the source** — a bounds or shape check at the parse/convert seam, next to the ones `pkg/promparse`, `protoparse` and `pkg/otlpsplit` already carry — never something to catch. "Add a recovery interceptor" is not an accepted remedy in this repo.

### Node agent (`internal/agent/...`)

The agent talks only to the metadata service (`metaclient`) and an OTLP gRPC collector (`otlpexport`, built on `go.opentelemetry.io/collector/pdata`) — no Kubernetes API, no RBAC (except `nodes/metrics` for the kubelet scrapes). Resource-attribute building lives in `agent/attrs`: `attrs.Builder` (nil = defaults) runs defaults → static → config templates (funcs: env/coalesce/default/regexMatch/regexReplace; context: Node/Pod/Container/Service) → `attrs.Filter`, driven ENTIRELY by the config's `resourceAttributes` section (the former `-resource-attrs-static`/`-enable`/`-disable` flags are gone: static duplicated `resourceAttributes.static`, and enable/disable are now `enable:`/`disable:` LISTS there — lists because the comma-separated flag form could not express a pattern containing a comma, which silently fragmented into literal-brace regexes. The filter is global, so a `pipelines:` section setting enable/disable is REJECTED, not ignored); `attrs.Builders` holds one per pipeline (`attrs.pipelineNames` is the authoritative list — currently logs/targets/cadvisor/node/summary/journal/ingest/self, and `validatePipelines` prints it on a typo, which is where the eighth name went missing from three prose copies at once) merged from the section's `pipelines:` subsection. `summary` governs the `/stats/summary` NODE resource and nothing else: that scrape's pod/container/volume resources are the CADVISOR pipeline's, because a summary series is worth something only while it joins the cadvisor series for the same object, and two resources join only while they are byte-identical. The defaults set `k8s.pod.ip` (from `Pod.PodIP`) as a resource attribute and derive `service.name` via `attrs.ServiceName` (workload owner → pod name), then finish with `attrs.Identity(res)`, which reads whatever identity attrs are on the resource to derive `service.namespace` (= k8s namespace) and `service.instance.id` (fallback: container.id, pod-uid[/container], namespace/pod[/container], node) for Mimir job/instance — neither overwritten if a template set it; it works for pod/container/node AND pre-populated (KSM splitter, ingest, log-metric) resources. **Instance-collision avoidance** (`attrs.PrefixInstance`, cmb-alloy `instance_prefix`): an exporter that DESCRIBES other objects (cadvisor, a KSM splitter) shares the described pod's `service.name`/namespace, so its `service.instance.id` would collide with the pod's own self-scraped metrics (same job+instance, different resource attrs → flapping target_info). The config's `instancePrefix` prepends `prefix-` to the derived instance; it defaults per pipeline via `defaultInstancePrefix`, which holds TWO entries and not one (cadvisor → `"cadvisor"`, summary → `"summary"`, others none): the summary entry prevents the same collision one level up, the kubelet's `/stats/summary` node resource carrying `service.name` `kubelet` and the node's name exactly as the `-node-metrics` scrape's does, so without it the two share (job, instance) while differing on `url.full` — a flapping target_info and two conflicting `up` values in one payload from `exportHealth`. Precedence is **explicit pipeline section > built-in default > top-level base** (so a global base can't strip cadvisor's or summary's protection — a top-level `instancePrefix: ""` leaves `summary-<node>` standing, and only `pipelines.summary.instancePrefix: ""` removes it); split rules default it to the describing target's `service.name` (`splitBatcher.defaultPrefix`), overridable per rule (`SplitRule.InstancePrefix`, `""` disables). Split rules also take `dropLabels` (anchored name regex, labels omitted from data points in `putSplitLabels`) and `attributes` (set-if-absent resource fallbacks applied after `Build` in `fillSplitResource`); several groupBy labels may map to one attribute — applied in sorted label order, non-empty overwrites, giving a deterministic coalesce; the split-resource ROUTE KEY and the enrichment identity extraction key on the SAME coalesced per-attribute values (container.id normalized), because keying on the raw per-label vector minted byte-identical duplicate resources/series whenever two rows spelled one object through different labels. It is invoked at every point a final resource is built — tailer metadata resolution, both single-resource batchers, the cadvisor per-pod resources and the splitter resources (which may pre-put identity attrs before Build). The identity half — `k8s.namespace.name`, hence `attrs.Identity`'s `service.namespace`, hence half the Prometheus job — is set at STARTUP from `selfmeta.Namespace()`, never by the stamp: learning it when the lookup lands would rename the job of already-running CUMULATIVE series, on some nodes and not others. The pod is RE-READ on `-self-attributes-refresh` (1m) so an edited pod/namespace label reaches the metrics it stamps, which the `private` caching makes nearly free (fresh entry served locally, stale one revalidated as a 304); a mis-resolution — realistically a pod IP recycled from a predecessor the store has not dropped yet — heals on the next read rather than lasting until a restart. `selfmeta.verified` (pod name == container hostname) is REPORTED on the resolution log line (`confirmed=`) rather than gating anything: a custom `spec.hostname` is legitimate, but it is the thing to look at if the attributes ever look like someone else's. `obs.RegisterSelfMetadata` publishes `kubescrape_self_metadata_resolved` on both binaries — registered exactly when the lookup RUNS, so a published 0 always means unresolved and never "disabled" — and `kubescrape_self_metadata_lookups_total{outcome}` counts the lookups SEPARATELY from `kubescrape_metadata_requests_total`, whose `not_found` is the container-attribution health signal and would otherwise carry a permanent stream from a fleet that cannot resolve. The stamp's Build runs even with a NIL pod: the operator's static attributes (a cluster name) are what an alert on `resolved == 0` selects by, so they cannot be conditional on the lookup working. The agent (`cmd/kubescrape-agent/selfattrs.go`) resolves over `GET /v1/self` (metaclient `Self`; the service attributes the caller by its CONNECTION's source address — never a header as the SOURCE, and a request carrying a forwarding header is refused outright — through the same live-only pod-IP index, so hostNetwork callers and address-rewriting hops get a 404 instead of someone else's identity; a 404 FALLS BACK to `PodByName($POD_NAMESPACE-or-SA-projection, $POD_NAME-or-hostname)`, which is what covers hostNetwork, SNAT and dual-stack agents, and metaclient sets `Proxy: nil` because a proxy hop REPLACES the address the attribution depends on), and wraps the exporter used by `obs.Registry.Run`/`FinalExport` and `spanmetrics.Generator.Run`/final `Export` (ALL of them — the last data point of a series must not carry a different resource than the rest); the METADATA SERVICE (`cmd/kubescrape/selfattrs.go`) needs no HTTP hop and no downward API for the same thing: every pod is already in its store, its pod name is `os.Hostname()` and its namespace comes from `leader.Namespace()` ($POD_NAMESPACE or the ServiceAccount projection it already mounts for in-cluster credentials), so `GetPodByName` + the server's own owner/namespace enrichment is the whole resolve. Stamping is a wrapper, not a resource built once at startup, because a process and the metadata it needs come up together: the attributes must appear without a restart when the store (or the service) fills in second, and nothing may WAIT on the lookup (self-metrics are how such an outage is diagnosed). Fill-if-absent — via the `self` pipeline builder on the agent, the built-in `attrs.Pod`+`Identity` mapping on the service (which has no `resourceAttributes` surface): `service.name` stays `kubescrape-agent`/`kubescrape` and `service.instance.id` stays the NODE / the hostname (stable across restarts, unlike the pod UID `Identity` would otherwise derive) while `service.namespace` newly becomes the pod's namespace — i.e. the job reads `<namespace>/kubescrape-agent`. `.Container` is deliberately nil: which container of the pod this process is cannot be known (sidecar injection makes "the only one" a guess).
- **Series filtering & splitting** (`agent/promscrape/filter.go`, `split.go`, config `metrics` section): ordered first-match-wins keep/drop rules per pipeline (`filterPipelineNames` is the authoritative list — `all` plus the four scrape pipelines, `summary` among them) applied in `parseAndExport` before conversion (so partial histogram families are possible, as with Prometheus relabeling); splitters route KSM-style targets into per-object resources via `splitBatcher` (groupBy label → attribute mapping + optional metadata enrichment; requires `Kubelet.Meta` even without kubelet scrapes; the shared `podCache` is mutex-guarded because splitters run on concurrent scrape goroutines).
- **Exporter** (`agent/otlpexport`): gRPC or OTLP/HTTP (protobuf POST to /v1/logs, /v1/metrics), bearer token file re-read per minute through `internal/bearer` (a FAILED re-read keeps the last good token — this used to fail the whole export, so a Secret-projection swap dropped a batch for a credential the process still held), TLS CA/skip-verify, bounded retries for metrics only — log retries/rewind belong to the tailer. **Size-bounded sending** (`pkg/otlpsplit` + `Config.MaxSendBytes`, `-otlp-max-send-bytes`, default ≈3.75 MiB under the 4 MiB gRPC limit): every send measures the exact proto size (`plog/pmetric/ptrace ProtoMarshaler.*Size`, attributes+framing included, not just bodies) and splits an over-cap payload into parts each within the cap, preserving resource/scope grouping (`otlpsplit.Logs`/`Metrics`/`Traces`; an over-cap resource splits by record/metric/span, an over-cap METRIC FAMILY splits further by DATA POINT — all five types, preserving the metric shell plus per-point exemplars/quantiles/exponential scale — and a single leaf over the cap goes alone). This is the ONE hard guarantee against wholesale rejection for producers that batch by count (journald, tailer) or forward sender-sized pushes (the ingest server) rather than pre-chunking (promscrape stays under the cap and never trips it). A part-send failure returns immediately and the caller retries the whole payload — at-least-once tolerates the re-sent parts, and nothing commits until every part lands. A non-empty input never yields zero parts (an over-cap record-less resource is sent whole, rejected+counted at the collector, never silently reported delivered); an empty scope's identity is preserved across a big-resource split. Payloads are gzip-compressed by default (`Config.Compression`, `-otlp-compression=gzip|none`) via klauspost/compress: `gzip.go` registers a klauspost-backed gRPC "gzip" codec (do NOT import grpc/encoding/gzip too — last init wins) and **pools READERS as well as writers** — that half was missing for as long as the writer pool existed, and it is paid on the SEND path too, not just on receive: grpc-go compresses its responses, so the two-byte OTLP ExportResponse answering every single export was minting and dropping a ~36 KiB gzip reader (received push 17 allocs → 1, empty response 5 → 1). The release contract is the hazard: the pool holds the bare `*gzip.Reader` and the per-message wrapper decides when it may go back — on the FIRST of a terminal Read or Close, exactly once, under a mutex so a Close racing a Read waits rather than pooling the reader out from under it. Close is NOT optional, because grpc-go reads through a `LimitReader` of max+1, so every over-limit message stops short of EOF — precisely the payload a hostile sender picks. A released reader is `Reset` onto an empty source before it goes back, since the gzip header is SENDER-CONTROLLED (FEXTRA up to 64 KiB) and a pooled reader must not park memory a pusher chose. The pool-identity tests skip under `-race`, where `sync.Pool` deliberately drops one Put in four. It gzips HTTP bodies with pooled writers into `github.com/JohanLindvall/bufpool` buffers, and the pooled buffer IS the request body — wrapped in a `pooledBody` whose `Close` is a deliberate NO-OP, because bufpool's Close IS Release and net/http closes a request body TWICE on a 301/302/303: the transport closes it when it finishes writing, and `Client.do` closes it again at the bottom of its redirect loop BEFORE `CheckRedirect` is consulted, so this client's `http.ErrUseLastResponse` cannot prevent it. A redirect is answered before the body has been read, so that second Close lands while the transport's writeLoop is still Reading — and Release resets the handle and returns the storage to a PACKAGE-LEVEL pool shared by every client in the process, i.e. hands a buffer this export is still streaming to the next one (`TestRedirectDoesNotDoubleReleaseTheGzipBody` reproduces it under `-race`; `gzip.go`'s `gzipBody` says the same thing from the other end — "the returned buffer must NOT be handed to net/http as the request body"). So the release is the exporter's own (`httpPost`'s `defer pb.release()`) and happens only once the buffer has been read to EOF, which is also what proves the writeLoop is done with it; a body that never reached EOF — a redirect answered early, but also a refused dial or a cancelled context — is left to the GC rather than pooled, so an unreachable collector on the HTTP protocol runs the gzip pool cold. Never set `req.GetBody`: a replay would read reused memory.
- **Disk buffer** (`github.com/JohanLindvall/diskqueue` + `otlpexport.Buffered`, opt-in `-buffer-dir`/`-buffer-max-bytes`): a Fluent-Bit-style filesystem write-ahead buffer. The queue is the external diskqueue library (one `Queue[[]byte]` per signal with an identity codec — the sink owns the pdata (un)marshaling): durable FIFO of checksummed records in preallocated segments, headers publishing the cursors (data-before-header, each fsync'd), corruption degrading to REPORTED loss (never a wedged queue, never silent), reopen resuming from the committed cursor (at-least-once across restarts), flock on the directory, `Stats()` as a plain struct. `otlpexport.OpenBuffer` sets `MaxBytes` from the flag with `MaxSegments: -1` — MaxBytes is the ONE operator knob, and the default 32-segment cap would bind behind its back at 256 MiB — and `MaxOpenFiles: 8` so a deep backlog does not hold an fd per segment. The drain runs on `Reader.Reserve(ctx)` (blocking; the queue's own wakeup replaced the old signal channel) with `Commit(offset)` only after the collector acks; commits are a CURSOR (in-order), so a stuck head batch goes back via `Rewind` and rotates to the back via `Requeue` — which is EXEMPT from the capacity caps as of diskqueue v0.0.4, because a poison head at a FULL queue was precisely the wedge `spool.AppendForce` existed for (nothing behind the head can retire first; the rotation is backlog-neutral once its commit lands). A reserved payload ALIASES the reader's buffer (valid until its next read): the sink hashes it for stuck-tracking BEFORE any queue operation — `Requeue` in particular clobbers that buffer. A latched I/O failure (diskqueue latches a failed fsync: every later Add/commit returns `ErrIO`, since a retried fsync can claim success over dropped pages) is recovered by `Buffer.recover` — guarded close-and-reopen keyed on the observed handle, so enqueue and drain goroutines never double-reopen; the affected batch redelivers. `ErrRecordTooLarge` (one batch over the whole cap — refused outright, unlike the transient `ErrFull`) counts into `obs.BufferFull` like a full-queue refusal, while EVERY other enqueue refusal (a latched I/O error, a closed queue, the raw `*os.PathError` diskqueue returns when segment preallocation hits ENOSPC) counts SEPARATELY into `obs.BufferEnqueueErrors` (`kubescrape_buffer_enqueue_errors_total{signal}`) — those used to return bare, so a full disk made a node go dark with every buffer metric flat: `_full_total` is the wrong class, `_dropped_total` is drain-side, and `obs.Exports` sits BELOW the buffer and is never reached. `Buffered` wraps the client with one queue per signal (generic `sink[T]` over plog/pmetric/**ptrace**), implements the shared `otlpexport.Exporter` (ExportLogs+ExportMetrics), enqueues on Export and drains in `Run` with retries (single-attempt inner sends; the backoff persists across cycles to the 30s cap) — commit only after the collector acks (at-least-once across restarts). `IsPermanent` classifies definitive rejections (dropped + counted); auth failures and 404 are deliberately transient — a rotating token or a collector rollout must not drain the backlog into drops. A batch whose TRANSIENT rejection is in fact permanent for that payload (an over-limit message comes back as `ResourceExhausted`) would otherwise circle the queue forever: it is dropped + counted after `maxDrainCycles` (3) accountable failed cycles (`sink.stuckTooLong`, keyed by payload hash into `sink.stuck`, bounded by `maxStuckTracked`). A lap that IS accountable ends after ONE attempt instead of `stuckAfterAttempts` (`sink.accountableLap`, the SAME predicate `stuckTooLong` weighs, read before the send): the remaining attempts would only re-ask, at the QUEUE HEAD, a question this payload already had answered — and commits are a cursor, so a head nothing will accept stalls every other producer on the node for the ~2 minutes a backed-off cycle takes. The gate is the PAYLOAD's evidence, never "the collector is up": `respondedError` is true for exactly the classes `IsPermanent` treats as deliberately transient (a rotating token's 401, a rollout's 404), so a sink-warm gate cut GOOD data's retry depth to one attempt during precisely the two events that depth exists for. A first sighting is therefore never shortened — a transient condition lasting four attempts is still delivered on the fifth — and a poison payload costs `stuckAfterAttempts + maxDrainCycles` = 8 wire attempts before the drop, against 20. A cycle is accountable only when BOTH hold: the collector delivered some OTHER batch since THIS payload's OWN previous failed cycle (`s.delivered > stuckBatch.lastDelivered`, re-established EVERY lap and never latched — latching it once, "it delivered something at some point, so every later responded lap counts", spent the whole budget during a pure back-pressure event and destroyed good data in exactly the outage the buffer exists to survive; deliveries banked before the payload got stuck, or while it merely sat behind in the queue during a recovery, advance `s.delivered` without a failed lap of ours spanning them and so cannot count), AND the cycle's final error was a collector RESPONSE (`sink.stuckResponded`, set by `trySend` from `respondedError`: an HTTP status other than 408/429/5xx, or a non-Unavailable/DeadlineExceeded/Canceled gRPC status — the retryable statuses OTLP defines are back-pressure, not a rejection of this payload) rather than a transport failure. So a blip delivery followed by a resumed outage spends nothing, and a collector rejecting EVERYTHING (a memory-limiter overload) never arms. Only a live collector repeatedly refusing THIS payload while accepting others is poison evidence. Keying by content hash means the count RESETS on restart, deliberately: a fresh process should re-offer the batch, the collector may have been fixed. A recovered stuck payload is `forget`-ten on success (and on a later permanent rejection) so the tracking map cannot leak. When enabled, main routes ALL consumers (tailer, journald, scrape, log-metrics, ingest) through the single `out` value; the buffer's inner is the raw client. **Traces are PASS-THROUGH except when the payload is OWNED** (`otlpexport/owned.go`, `Own(ctx)`/`Owned(ctx)`): a forwarded trace is still held by the pushing SDK, whose retry IS the durability, so spooling it would ack a sender for data that has not shipped — but a tail-sampling DECISION (`agent/tailbuffer`) acked its senders when it BUFFERED the spans, seconds earlier, and nobody else holds them. The distinction is per PAYLOAD and rides the CALL rather than the wiring, because the layers in between (transform wrapper, router) are shared by both classes and must not know which they carry; `NewBuffered` takes a third `traceBuf` and main opens `traces/` ONLY under `*serviceGraphOn && fileCfg.TailSampling.Enabled()` (elsewhere it would be a flock and a preallocated segment that never take a record). With no traces spool an owned payload still passes through — the marker asks for durability, it does not require it. Physical disk can exceed the cap by up to one 8 MiB segment (delivered-but-unreclaimed records retire whole-segment; `Stats().DiskBytes` reports the real footprint). **Occupancy is observable before anything is lost**: `obs.RegisterBufferStats(buffered.Stats)` publishes `kubescrape_buffer_backlog_bytes`/`_max_bytes`/`_segments` per signal as `Registry.GaugeFuncVec` (a one-label func gauge added for this), so `backlog/max` alerts on a degrading collector — every other buffer metric is a counter that only moves once data is ALREADY being dropped or refused.
- **Shutdown budgets and context seams**: every shutdown flush is BOUNDED and DETACHED — `context.WithTimeout(context.WithoutCancel(ctx), …)`, never a bare `context.Background()`, because `otlpexport.Own` rides on the context and a fresh Background silently strips a payload's durability marker. `metrics.Registry.FinalExport` takes the CALLER's ctx (it used to manufacture its own 10s Background, so neither main could fit it inside the termination grace it budgets every other final export against; `metrics.FinalExportTimeout` is the default `Run`'s own branch uses). journald's final flush was the one of the four (tailer/events/azurediag/journald) with NO deadline — an unreachable collector held it for as long as the export's retries took while the rest of the agent's shutdown waited behind it; it is `shutdownFlushBudget` now, and missing it loses nothing (the cursor commits only on a successful export). `transform.Reload`'s fsnotify debounce selects on `ctx.Done()` rather than sleeping. `cmd/kubescrape-agent`'s `pipelines` no longer carries a `ctx` FIELD: the process lifetime is a parameter of every `start*` function (`stop` stays, being state). `tailbuffer.Flush`'s payload is still owned because `drain` applies `Own` itself, which `TestFlushedKeepsAreOwned` pins.

- **Routing** (`agent/route`, config `routing` section): fans exported payloads out by `k8s.namespace.name` globs (first-match-wins, `path.Match`) to per-route OTLP clients — different endpoint and/or extra `headers` (e.g. `X-Scope-OrgID` tenancy; `otlpexport.Config.Headers` sends static headers on both transports). Composition: producers → transform → **router** → {default buffered chain | route clients}; an all-default payload forwards untouched (no copy). Route destinations are direct/UNBUFFERED by design (tenancy fan-out, not a second durability chain); a failed destination fails the whole export and the producer's retry re-splits deterministically (already-delivered destinations get at-least-once duplicates). Parts count `obs.Routed{route,signal}`. A MIXED failure (some destinations permanent, some not) returns `partialFailure`, which is opaque to `errors.Is`/`As` by NOT implementing `Unwrap` — not by destroying its leaves: it keeps `errs []error` for logging and an `Errors()` accessor, since opacity is the absence of Unwrap and nothing else. Its `Error()` FLATTENS (errors.Join separates with newlines, and this string is written straight into `http.Error` and `status.Error`, where a multi-line body is a malformed header value and an unreadable gRPC status).
- **Debug tap** (`agent/debugtap`): the on-demand collector-debug-exporter equivalent — `GET /debug/otlp` on the agent's `-listen` port streams what the agent is exporting (logs/metrics/traces) as OTLP JSON lines, with `attr=key=value` resource filters (path.Match globs on BOTH halves, ANDed), `sample=<pct>` and `signal=` query params; `/debug/otlp/ui` is a self-contained page driving it, and `GET /debug` is the homepage indexing every debug surface the process serves (links appended beside the handler registrations in startDebugServer, so it cannot advertise what is not served; debughome.go). - **Transforms** (`agent/transform`, flag `-transforms-file`, SEPARATE from `-config` so it hot-reloads without the chart's checksum restart): Starlark scripts per signal (`logs:`/`metrics:`/`traces:`, each defining `transform(batch)`), run once per exported BATCH at the exporter seam ABOVE the disk buffer (producers → transform → buffer → client — spooled bytes are final, reloads never re-interpret a durable backlog). It is the one marker that reads the payload back AFTER the call — `md.ResourceMetrics().Len()` for that counter — so under an in-place script run the count is of the post-script survivors). The roster is ENFORCED: `internal/agent/transform/handoff_roster_test.go` pins where the marks are, per file, so a new marker fails the build until `handoff.go`'s list and the test's map are both updated — it had already drifted once, cgroupstats marking two call sites while the list still named four producers. This fold WAS a wrapping sum for exactly that reason, which was never the fix it looked like — under the sum the same input merely hashed distinct from the `{k=v}` it RENDERS, i.e. duplicate points every export and merged corrupt points for histograms rather than a merge with something unrelated. **The invariant is the folds' own now, not their callers'**, and that change is what this bullet used to describe the other way round: a resource's IDENTITY is the label set `resourceIdentity` builds through `set()` (empty key/value dropped, value cut at `truncLabelCut`, repeated key LAST-WINS), `resourceString` renders it and `labels.resAccum` folds it, so hashed identity and rendered identity are two views of ONE derivation. `resourceAccum` keeps a one-pass fold that materializes nothing, but it is licensed by a PROOF rather than by a promise — it probes the key hashes it is already computing (`resourceIdentityAttrs` = 64 = otlpingest's `maxObservedResourceAttrs`, which is where the one BOUNDED wire path stops observing at all — NOT a bound on what reaches the store: the unbounded door is `EmitDirect`, a transform script's `emit_metric` folding the SENDER's resource at whatever width the sender chose, which is precisely why this is a fallback and not a refusal) and materializes the identity when it cannot prove uniqueness. That fallback is QUADRATIC and it ALLOCATES — quote the shape, not the nanoseconds, which re-measured 2-4x apart on two machines. The proof may fail safe (a key-hash collision, or a resource too wide) and cannot be wrong; on a key-unique resource the answer is bit-for-bit the old one, so nothing churned. Quote the ALLOCATION counts and the shape — the wall-clock figures this sentence used to carry re-measured 2-4x apart on two machines, which is the trap the transform bullet already records. `uniqueResourceAccum` is GONE (it was the second, dedup-ing door — now exactly what `resourceAccum` does), and so is the "do not call this on a resource of unknown provenance" contract. **The contract had already leaked**, which is why it went: `resLabelsAccum` cancelled an overridden resource key through `pcommon.Map.Get`, which is FIRST-wins against a LAST-wins render, so the door the contract told you to use gave a wrong answer as soon as a rule declared `resourceLabels` — the cancel now resolves against the RESOLVED IDENTITY `Bind` already computed (`resourceFold`), which fixes the semantics and takes the per-line whole-map walk out with it, and `logchain.Resolver` still reads resources Get-first, which is (with the forwarded payload) why `otlpingest.dedupeResourceKeys` STAYS even though the store no longer needs it. `TestXorFoldIsSafeBecauseNoFoldCanRepeatAPair`, `TestResourceIdentityIsWhatItRenders`, `TestOverrideCancelsTheValueTheResourceRenders` and `FuzzResourceIdentityMatchesItsRender` pin it — the fuzz target is the one that keeps the one-pass fold from drifting from the definition it shortcuts, asserting on arbitrary inputs that a resource keys as the resource it RENDERS, with the rendered string re-parsed as the oracle. Measured before switching: XOR and the sum are indistinguishable on both speed (interleaved n=8, geomean 0.13%, every benchmark `~`) and DISTRIBUTION (chi-square on the finalized `mixHash`ed key over 400k label sets x 8 populations x 2 bit windows: mean |z| 0.65 XOR vs 0.51 sum, both at the ~0.80 uniformity predicts, ordering inverting against the raw fold) — the choice is the self-inverse, not either of those. **There is no second "check" hash any more and that is deliberate**: the pair existed because the primary was 64 bits, where the birthday bound at the 10000-label-set cap is ~2.7e-12 per series map — small but not nothing across a fleet over years. At 128 bits it is ~1.5e-31, which even across a million series maps sits far below the rate at which RAM corrupts the value anyway, so the guard was retired WITH the widening rather than carried beside it (keeping both is carrying the compensation and the fix at once). The pair was also weaker than advertised — both halves were projections of the SAME two 64-bit xxhash values per label, so a collision in the STRING hash fed both an identical contribution and the check saw nothing; its ~2^-128 only ever covered a collision arising in the combine. The log-metrics collision-drop counter was REMOVED with it (a counter that can no longer move reads as evidence of absence, and an operator alerting on it would believe they were watching something); the removal, and the metric's exact former name, are commented at its old registration site in `obs.go`. What the width does NOT make redundant is the separate resource hash DOMAIN (`combineResHash`), which defends against two series producing the same MULTISET of terms split differently between resource and labels — genuinely equal inputs, which no width fixes. Measured (interleaved A/B, n=8, vs the 64-bit two-accumulator predecessor): the FOLD gets faster — `BenchmarkLabelsAccums` -11.4%, `BenchmarkResourceAccum` -7.3%, since one 128-bit xxh3 fold costs less than two 64-bit xxhash ones — while the end-to-end observe paths get SLOWER by +2.2% to +6.2% (`DynamicAddBound` +6.2%, `DynamicAddHistogram` +5.2%, `DynamicAddJSONLine` +3.7%, `DynamicAddAttrs` +3.1%), `Export`/`DynamicAddValueFromLine` unchanged and `DynamicAddNoMatch` -3.9%, allocations unchanged everywhere. **The residual cost is the MAP KEY, not the hashing**, and `DynamicAddBound` is what proves it: that path uses `observePreHashed` with a hash precomputed at construction, so it does no folding at all, and it still slowed 6.2%. Go specialises `map[uint64]` to the `mapaccess*_fast64` routines; a 16-byte comparable struct key falls back to the generic path with a memequal, and on an observe path that is little more than one probe that is the whole difference. It is irreducible while the key is 128 bits wide — the alternative is keying the map on one 64-bit half and keeping a full-width comparison in the bucket, which is the two-value design in a different costume. - **Tailer performance** (`bench_test.go`): the multiline package (>= v0.0.4) prefilters its start-state regexes with literals derived from the patterns — lines containing no literal skip all start regexes (~12x less per-line CPU). If a pattern change makes the literal set unprovable the matcher silently falls back to full regex evaluation (correct, slower); `TestPrefilterEnabled` (via `patterns.StartLiterals()`) is the alarm. `feedLine` parses the CRI header once and feeds the result to `cri.AddParsed` (multiline >= v0.0.6; the stage's internals never re-parse — the single `cri.Parse` per line is feedLine's), uses precomputed `file.keyStdout`/`keyStderr` (no per-line key concat), and the ledger's offset accounting lives in per-stream `streamState` structs reached via pointers cached on the file (`stStdout`/`stStderr`/`stPlain`, re-derived after every `reset()`) — no map operations per line. The `streamState` fifo of buffered offset ranges is consumed by advancing `fifoHead` (`live`/`push`/`pop`), never by re-slicing: re-slicing walked the backing array forward until its capacity ran out and then, since the steady state is one line pushed and one popped, reallocated a one-element array for EVERY line — that was the tailer's entire per-line allocation. **The line path is now zero-alloc** (BenchmarkIngestLine: 0 allocs/op; keep it there — `TestIngestLineAllocationBudget` is what fails the build if it moves, and `TestIngestFlushAllocationBudget` bounds the production shape). The same re-slicing trap applied one level up, to the per-file carry buffer: `consume` advances `f.pending` by re-slicing, so `ingestChunk` appending the next 64 KiB read into its drained-to-zero spare capacity allocated a fresh array per READ. `file.pendingBase` pins ONE array per file and `appendPending` memmoves the unconsumed remainder back to its front (`TestPendingBufferIsReusedAcrossChunks`: the only per-chunk allocations left are `consume`'s per-line `string(line)`); a buffer grown past `maxIdlePendingBytes` by one over-long line is released once the file drains, so a node tracking thousands of files cannot pin a megabyte each. BenchmarkIngestLine/BenchmarkIngestFlush track the per-line budget (~0.2µs pipeline, ~0.8µs with enrich); BenchmarkIngestChunk covers the read path (~130 B/line, down from ~260).
- **Tailer** (`agent/tailer`): single sweep goroutine over the configured log sources (see the Log sources bullet; default `/var/log/containers`). Log lines flow through the two-stage `github.com/JohanLindvall/multiline` pipeline, per file: `multiline/cri` parses the CRI format and rejoins P/F fragment runs (non-CRI lines pass through rather than being dropped), then `multiline` joins stack traces. Offset mapping relies on stage emission being synchronous inside `Add`/`Flush*`: `lastEnd[key]` is exact because the line completing a run is always the line currently being fed, and `Entry.Lines` (which since multiline v0.0.11 charges even cap-dropped lines to the last emitted entry, so `sum(Lines)` equals lines consumed — pinned upstream by FuzzCappedConservation — and the FIFO pops exactly) pops the per-key FIFO of logical-line offset ranges. The pre-v0.0.11 compensation machinery is DELETED, not dormant: the deferred F-closed-run emission (`streamState.closed/nextStart/hasNext` — FinalMatcher emits inside the F line's own AddParsed, where `runStart`/`lastEnd` still describe the run), the orphan head-drop, `reconcileFifos` and its fifo-orphans counter are gone, so an upstream regression of the Lines contract would now wedge a file's watermark rather than self-heal — the contract is the library's to keep. A NEVER-COMPLETING group (continuation-shaped lines refreshing the staleness stamp on every line, so `FlushBefore` never fires while the stage consumes past its caps) is force-flushed once its FIFO passes `maxGroupBuffered` (2x the trace stage's retention cap, `boundGroup`): without the bound the FIFO grew one ~56 B item per line forever while `committed` stayed pinned at the group's start — checkpoint frozen, crash re-ingests the window, idle-close blocked. The STAGE-1 sibling — an endless CRI P-fragment run whose F never arrives, which reaches no FIFO at all while every fragment refreshes the same stamps — is bounded by CONSUMED BYTES in `feedLine` (`streamState.runBytes`): past 2x `MaxEntryBytes` the crossing fragment's tag is rewritten to F (`forceFinal` — the raw line, not just the parse: with a run pending the stage classifies by re-splitting raw), so the stage closes the run itself and emits the joined truncated entry synchronously, and the remainder starts a fresh run. At-least-once invariants: exports happen inline in the sweep with retries; per-file offsets are committed only after a successful export and never past lines still buffered in either stage (`watermark` = min of `runStart` and FIFO heads); on a TRANSIENT failure files are rewound to the committed offset and the pipeline is discarded unemitted (the lines get re-read); a PERMANENTLY rejected batch (`otlpexport.IsPermanent` — bad payload, unimplemented, over a receiver's body limit) is the one exception and the one LOSS path: retrying it can never succeed and one sweep goroutine serves every file on the node, so rebuilding it forever would stop ALL log shipping there, pin the fd against logrotate and lose the backlog outright when the file rotates away — so the batch is dropped and the offsets advance (`advanceBatch`, not `commitBatch`: the records were never delivered, so `LogEntries` must not move, and nothing was rewound, so `LogExportFailures` must not either). `obs.LogPermanentDropped` (`kubescrape_log_permanent_dropped_total`) plus the Error log carry it exactly — **it is the tailer's data-loss signal and is worth an alert on any nonzero rate**; `exportWithRetry` short-circuits the retry budget on the same classification. With `-buffer-dir` the tailer's Export returns the ENQUEUE verdict rather than the collector's, so on that configuration this counter moves only for a batch larger than the whole buffer cap and the collector's own permanent rejections land on `kubescrape_buffer_dropped_batches_total{signal="logs"}` + `kubescrape_buffer_dropped_records_total{signal="logs"}` instead — which is where the buffered chain's alert belongs (the batch counter says a loss happened, the records one says how big it was); checkpoint PRUNING is gated on a successful listing (`lastListingOK`) — one save while a glob failed destroyed the offsets of files it merely could not see — and so is the END OF STARTUP: the stored positions (`Tailer.checkpoints`) are consulted by EVERY scan, not just the first, because a startup glob that fails (an unreadable include base, a transient EIO) discovers nothing and the 2s `dirTicker` then finds every file on the node with no checkpoint applied — a node-wide re-ingest from byte 0 with every `Pending` prefix destroyed and no counter moving. An entry is CONSUMED when it is applied and dropped when a SUCCEEDED listing did not see its path (the same proof that lets the store be pruned, so a stale offset can never be applied to a recreated path), and `-logs-unknown-files` governs a checkpoint-less file only while `Tailer.startingUp` — a file appearing after a listing has succeeded is new and is read whole whatever `end` says — and a positions file that failed to DECODE reports `Corrupt()` so `auto` re-reads instead of skipping every file to its end as history (an empty store is otherwise indistinguishable from a first run); committed offsets are checkpointed to disk via the positions store (persisted immediately when a new file is discovered — a crash before a file's first entry would otherwise skip it as history on restart; where a checkpoint-less file starts is `-logs-unknown-files`: auto/end/start, auto = read from start when the store already has entries). A file's metadata is resolved (with server-side wait; failures back off EXPONENTIALLY from `minMetaBackoff` 2s to `maxMetaBackoff` 1m, each delay jittered over `[d, 1.25d)` by `jitterMetaBackoff` — the lookup BLOCKS server-side for the whole `-metadata-wait` and runs on the single sweep goroutine, so a flat short retry lets a few permanently unresolvable files monopolise the tailer, and an unjittered one puts every file on a node — and every node in the fleet — on the same schedule, so a metadata-service rollout recovers into one synchronised burst) before its data is consumed — nothing is read until it can be attributed; a file deleted before it ever resolves is released with the loss COUNTED (`obs.LogUnresolvedLost`), since nothing was read and nothing can be. Idle files close their fd after `-logs-idle-close` (default 0 = never; the file stays tracked and reopens with identity re-verified on activity) — steady-state fds are one per active file, not per tracked file; the reopen is STAT-GATED against the 500ms poll sweep (same inode+size+mtime as at close skips `ensureOpen`; any deviation goes through its identity checks, so rotation-while-closed recovery is unchanged), and eligibility compares `fedEnd()` to `committed`, since never-fed trailing bytes (a blank line, a rate-dropped or oversize-discarded tail) can never commit and would otherwise pin the fd forever. A rotation landing while NO fd is held — the idle-close window, or between a restart's `initFile` (whose stat still saw the old inode) and the first open, a window metadata-resolution backoff widens to minutes — is recovered by `ensureOpen`'s replaced arm: the old identity + committed offset become an open-ended segment (the discover.go `to = -1` shape) instead of a silent committed-to-zero reset. Rotation: identity = inode + head fingerprint (FNV of first `-logs-fingerprint-bytes`; catches inode reuse AND copytruncate — the post-read `read == 0` check catches a same-or-smaller rewrite, and a PRE-read fingerprint re-verify in `readFile` (whenever the file's mtime moved since the last read) catches a copytruncate whose replacement content is LONGER than the read offset. fingerprints EXTEND (shared `extendFingerprint`, called from `saveCheckpoints` AND from readFile after a successful read — without the read-path call a store-less deployment never extends and a file first opened at size 0 keeps the matches-anything empty fp forever) only while the head already hashed still matches — re-hashing unconditionally would adopt a copytruncate replacement's head and blind both guards for every sub-`FingerprintBytes` file; the truncation DECISION in readFile uses the PRE-settle readPos (settle can rewind it and re-evaluating against the shrunken value missed an in-place rewrite sized between committed and readPos); rename rotation drains the old fd before switching and OPENS the new incarnation immediately — `reopen` clears `f.f`/`f.inode`/`f.fp`, so leaving it unopened until the next sweep let a SECOND rotation inside that window find nothing to drain, record no segment, and lose the whole middle incarnation silently; deletion drains before drop. **Segment-qualified offsets** (the decomposition docs/tailer-comparison.md describes — DONE): every buffered/emitted offset is a `pos{seg, off}` where `seg` is a per-file monotonic incarnation id (the live file is the TAIL segment; each rename rotation closes the tail into a `segment` record `{id, inode, fp, committed, to, fd}` on `file.segments` and issues a fresh tail id). A segment's `to` is the last FED line boundary (max `streamState.lastEnd` at the tail), NOT readPos: trailing bytes that never entered the pipeline (torn fragment, blank line, rate-dropped or oversize-discarded lines) can never produce a committing entry, and a `to` covering them pinned the segment below retirement forever. An UNRECOVERABLE segment (findRotated miss, file pruned) is counted (`obs.LogPrefixLost`) AND retired — keeping the record wedges retirement. `segmentsFed` asserts every recorded segment's owed lines are live (pipeline or batch); rotation preserves the incoming value (`wasFed`, vacuously true with no prior segments) rather than overclaiming — a mid-drain rewind purges older segments' re-fed lines, and marking them fed stranded an older rotation's lines until restart. A drain that does not reach the source's END returns false, and the rotation COMPLETES with the un-drained inode recorded as an OPEN-ENDED segment (`to = -1`, `fedTo` at the drain's fed boundary) that `feedSegments` replays across sweeps under `MaxBytesPerSweep`. TWO causes, and the second used to be a silent loss: a mid-drain flush FAILURE (the rewind seeks the very fd being drained back, so continuing was a hot loop burning export attempts on the single sweep goroutine), and the per-drain CAP (`defaultDrainCap`, 1 GiB — a bound on ONE drain call, never on what may be recovered). The cap used to return the same `true` as EOF, so everything past 1 GiB of a rotated incarnation — an agent down for an hour, a source outrunning the per-sweep budget — became unreachable forever with `LogPrefixLost`, `LogDrainErrors`, `LogPermanentDropped` and `LogExportFailures` all flat and one Error line as the only evidence. `fedTo` on that segment is what keeps the cap case from re-delivering the whole unflushed batch (a flush failure floors `fedEnd()` back to `committed`, so it is a no-op there). The same rule holds for a GONE file: a cycle whose drain ended unfinished does NOT stamp `goneEnd`, because settling would close the only handle to the unlinked inode with its remainder unread. The accepted cost is stated at `drainReader`: while a replay is unfinished the live tail is not read, so a source that outruns the drain forever now gates the new incarnation instead of abandoning the old one. Cross-rotation ambiguity is inexpressible by construction: an entry commits against `end.seg`'s record — the tail candidate advances the file checkpoint, an old segment's candidate advances that segment's `committed`, a segment retires (`retire`: fd closed, checkpoint entry gone) when its whole range commits, and a DEAD id (truncated-away incarnation, or the archive-replaced restart's `newTail`) resolves to nothing. This replaced the old rotation-generation protocol (`gen` stamping + apply-time checks) and the `reanchor` offset rewrite wholesale. **Multi-line groups (CRI P/F runs and stack traces) join across a rename rotation**: if data is still buffered after draining the old inode, `reopen` carries the pipeline — buffered items keep their old-segment positions untouched — and the fresh tail id disambiguates the new inode's bytes. Zero-loss across a crash, including multiple rotations: incomplete segments are checkpointed (`positions.Prefix` list, oldest first; identity = inode+fp; `From` is the segment's commit PROGRESS, so a restart re-reads only the owed `[From,To)` remainder; an OVERSIZED line inside an owed range persists its discard progress on the segment — `skipTo`/`discarding`, in-memory only, zeroed together with `fedTo` by `ledger.reset` and carried by `reopen` — because pass-local discard state made every replay pass resume at the identical offset until the stall limit retired the segment with its readable remainder lost, and `chargeStall` counts discard progress as progress; a GONE file's drain shares the same stall budget — `chargeGoneStall`, charged only by cycles whose drain ENDED in a read error with no commit progress — so a regressing error boundary that can never re-reach the rewind-proof `goneEnd` retires the file loudly, `obs.LogPrefixLost`, instead of wedging its entry and fd forever), and `reopen` persists the checkpoint IMMEDIATELY when a segment is recorded — the 10s cadence alone left a crash window that lost the rotated tail outright (discovery persists immediately for the same reason). Each segment RETAINS the rotated inode's fd but the retained fds are CAPPED (`maxCarriedFds`, oldest kept — they prune first) so a long outage across many rotations cannot exhaust fds or pin unbounded disk; `reopen` NEVER resets `segments` (a later rotation must not drop earlier uncommitted ones); on restart (or after a rewind that discarded the buffered group, tracked by `segmentsFed`) `feedSegments` re-reads each incomplete segment's owed range UNDER ITS OWN id (`ledger.feeding`) — `findRotated` (by inode+fp in the resolved target dir) is the post-RESTART fallback (no fd survives a restart); when it too fails the loss is counted (`obs.LogPrefixLost`) and the segment retired. A rotation that happened while the agent was DOWN is recovered too: `initFile` sees the checkpointed identity no longer matching the path and synthesizes an OPEN-ENDED segment (`to = -1`; feedSegments reads the rotated file to EOF and pins the range, or counts + retires when pruned). Caveat: the join only spans rotations the tailer actually **observed** while running (it follows the symlink, not every intermediate rotated file — a rotation so fast the intermediate inode is never opened loses that segment, pre-existing). Truncation/copytruncate still flush-and-reset (content replaced, joining meaningless). **Audited micro-edges (2026-07-30 exhaustive pass; all fail-safe, none worth code)**: an `end`-mode skipped file checkpoints `Offset=size` with inode 0 until its first read, so a crash inside that sub-second window plus a rotation-while-down into a LONGER file can resume mid-file; `LogTornFinalLines` counts rename rotations only — truncation losses are unmeasurable by nature; `LogBytes` excludes segment-replay re-reads. Sweeps are fsnotify-driven (watch the symlink dir + resolved target dirs; files directly in the watched dir are a test-only special case) with the poll ticker as fallback. **Log rules** (`Config.Rules` = `metrics.LineFilter`, config `logs.rules`): ordered keep/drop/sample evaluated in flush AFTER enrich (synthetic `logchain.SeverityKey` = `__severity__` via `logchain.Resolver.RuleFn`, fed by `logchain.LowerSeverity`) and AFTER LogMetrics (metrics see every line); with rules set, records build in a one-record scratch slice and `MoveAndAppendTo` into the batch only when kept; dropped records still advance offsets (an all-dropped batch commits without exporting) and count into `obs.LogRulesDropped`. **Rate limiting** (`Config.RateLimit/RateBurst/RateDrop`, flags `-logs-rate-*`): per-file token bucket in `allowLine`/`consume`; pause mode sets `file.limited` (readFile/readArchive stop reading, pending retried next sweep — for archives BEFORE the archiveDone short-circuit, or an EOF-paused tail wedges), drop mode discards lines; rotation drains bypass the limiter (`consume(..., unlimited=true)`) or the rotated remainder would be lost. Pause mode's no-loss contract holds across EVERY restart path: `reopen` and the archive restart salvage complete pending lines (unlimited) before the reset, and the shared `file.restartAt` clears `limited`/`discarding` with pending everywhere (openArchive included — a wiped pending with `limited` still set wedged the file forever, and the archiveReplaced block once drifted from reopen by omitting exactly these resets). An unterminated fragment at a RENAME rotation whose drain REACHED THE END can never complete and is dropped counted (`obs.LogTornFinalLines`); the counter is gated on `drained && !f.discarding`, because an UNFINISHED drain OWES those bytes through its open-ended segment (counting them reports a loss for a line that is then delivered) and a DISCARDING file's pending is the tail of an oversized line `obs.LogOversizedDropped` already counted — one physical line, one loss counter, which is the rule `drainGone`'s sibling block already applied. An oversized unterminated line (> MaxEntryBytes+4096) discards its prefix AND its eventual remainder (`file.discarding`, `obs.LogOversizedDropped`) — the mid-line suffix must not export as a record. **Status** (`status.go`): `publishStatus` (housekeeping, `statusEvery` 10s) snapshots per-file positions/lag into an atomic pointer read by `Tailer.Status()` → agent `GET /debug/tailer`; gauges `obs.LogLagMaxBytes`/`obs.LogLagTotalBytes` (`kubescrape_log_lag_max_bytes` is the per-file maximum, `kubescrape_log_lag_bytes` the sum — the two were named the other way round, with `_total` on a gauge); compressed files report `Lag = ReadPos − Committed` (Size is compressed bytes, offsets are decompressed — their difference is meaningless). **Withheld commits**: a record exported while ANOTHER stream's multi-line group is buffered has its commit clamped to the build-time watermark (a candidate in a segment NEWER than the watermark's commits nothing, same segment clamps to its offset, older segments are unconstrained); the unclamped high position is remembered (`file.exportedHigh`, via `batchInfo.highs`) and re-offered at the next flush touching the file — without it `committed` froze below `readPos` forever (restart re-reads the tail, idle-close never releases the fd, lag gauges show phantom backlog). **Observation is once per RECORD, not once per PASS** (per record rather than per delivery is exact: a record withheld by a commit clamp and then rewound is DELIVERED twice and counted once — under-claiming only inflates, over-claiming destroys observations invisibly). A failed export rewinds the file and the next sweep re-reads the same bytes — at-least-once by design — but a log-derived metric and `kubescrape_log_rules_dropped_total` are CUMULATIVE, so re-running the chain multiplied them by the number of rewinds an outage spanned (measured on journald's equivalent path: 46 observations for 6 entries). `file.observed` is the set of entries already through the chain, keyed by `obsKey` = the segment-qualified byte RANGE plus a hash of the BODY those bytes produced; a member is rebuilt and re-ruled (a hot-reloaded rule must still be able to change the verdict) but carries `logchain.Input.Observed`, which suppresses the COUNTING half only. **The body hash is load-bearing, not belt-and-braces**: a rewind followed by a truncate-and-rewrite reuses the same offsets in the SAME segment (the rewind already put the read position at 0, so no fresh tail id is issued), and `TestTruncatedFileIsObservedAgainAtTheSameOffsets` reports 2 where 4 is right without it. The set is bounded (`maxObservedEntries`), pruned per touched file per flush, and dies with the file. Recording happens AFTER the export outcome, never before: a range recorded up front asserts things about bytes the reader SKIPPED — a rate-dropped line that a later pass admits then falls below the frontier and is delivered but never counted, which is a silent loss where the bug it replaced was a visible over-count (measured 2 observations for 3 delivered records; the exact sequence is pinned by `TestRateDroppedLineAdmittedLaterIsStillObserved`). Exports are synchronous in the sweep (`flush.go`: `batchInfo` carries build-time per-segment candidates to `commitBatch`/`failBatch`); the former opt-in pipelined-export mode was REMOVED — its settle protocol cost more in invariants than the overlap earned, and `-buffer-dir` provides the same decoupling with at-least-once durability (docs/tailer-comparison.md).
- **Log sources** (`agent/tailer/sources.go`, config `logs` section): the tailer discovers files by `[]Source` (doublestar include/exclude globs, `**` supported) rather than a single dir; empty config = one default containerd source over `-log-dir`. Each source is `containerd` (CRI filename→containerID→metadata→CRI parse) or plain (arbitrary files: no metadata lookup, resource attrs = builder node attrs + the source's static `attributes` + `pathAttributes` captures (per-file path-regex → attribute rules — named groups, or an explicit key→group map for dotted keys — validated at startup and REFUSED on containerd sources), `service.name` defaulting to the source name; per-source `multiline` override; a file's resource is NOT latched at resolve: `refreshNodeAttrs` re-renders it (one pointer compare per resolved file per sweep, `file.nodeInfo` vs what the provider yields) whenever the node-info provider produces a new value, so the placeholder `selfmeta.Poll` serves before the first `GET /v1/nodes/{name}/metadata` lands cannot stick to an early-discovered file — deterministically every plain-source file, which resolves on sweep #1 and takes no lookup — and `-node-metadata-refresh` reaches already-tailed files as it does every other pipeline. Latching produced ONE node exporting two resource shapes at once, so an operator template over `.Node.Labels` was missing from half the streams. The re-render needs no lookup (`file.meta` retains the container metadata) and rebuilds through the ONE renderer, `buildResource` — anything that shapes the resource must live there, which is why the pod annotation's `serviceName`/`attributes` are kept VETTED on the file (`podService`/`podAttrs`) and re-applied rather than re-parsed (re-parsing would re-count `obs.LogPodAttrsRefused` and re-warn once per refresh, forever). The nil-provider deferral in `resolvePlain` survives as a first-value guard only; deferring is deliberately NOT the mechanism, since it would gate log collection on a lookup that can fail forever). **Cheap selection**: a containerd source takes `namespaces`/`excludeNamespaces` (path.Match globs, read from the CRI FILENAME at discovery — a non-matching file is never opened, tracked or read) and `selector` (pod label equality, applied at RESOLVE time since labels are only known then — the file is tracked but no data is ever read) and `ignoreOlder` (mtime cutoff, any source; a file already tracked OR carrying a stored offset is NEVER ignored however stale — dropping it would abandon its unshipped tail and re-ingest the whole file if it were ever appended to again). Both beat a `logs.rules` drop for cost control, which pays read+parse+enrich first and saves only egress. A file is claimed by the first matching source — INCLUDING a containerd source that skips it for a PROHIBITION (global `ExcludeNamespaces`, the source's own `excludeNamespaces`, or an unparseable CRI name): the exclude list is the observability feedback-loop guard and a later catch-all source must not resurrect the file. A source's `namespaces` ALLOWLIST is the one exception — a miss is routing ("prod through source A, the rest through source B"), so the file is deliberately left unclaimed for a later source. `claimPath` therefore tests `deniesNamespace` (the deny half alone) and `wantNamespace` separately: testing the merged `wantNamespace` for the claim silently took the deny with it and lost the guard. Non-regular files (FIFOs, sockets) are never tracked — open/read on a FIFO blocks forever and would wedge the single sweep goroutine node-wide. A non-gzip file matched by a compressed source is quarantined under its current identity (archiveDone + size/mtime; a valid rewrite recovers on its own) instead of warn-looping every sweep. Plain files bypass stage-1 (CRI) — `feedPlainLine` feeds the trace stage directly under a single `plainKey` so **the identical rotation / offset / cross-rotation-multiline machinery applies** (`file.source` selects the path; `newPipeline`/`feedLine`/`resolveMetadata`/`stopPipeline` branch on `source.containerd`, guarding nil `criStage`). The watcher watches every source's fixed include base dirs (`scanDirs`). Per-source `compressed` (gzip): compressed files use a separate one-shot `readArchive`/`openArchive` path (offsets in *decompressed* space; gzip isn't seekable so resume re-decompresses and `io.CopyN`-discards the committed prefix; read whole, not skipped-to-end; `rewind`/`drop` branch on `f.compressed`). The archive's fd is RETAINED past EOF (`archiveEOF`) and across a rewind while its data is uncommitted (`closeArchiveReader` closes only the gzip reader; `openArchive` re-decompresses from the retained fd) — an export can fail and logrotate can prune the `.gz` before the retry, and the fd is then the only handle to it; it is released once everything FED has committed (`committed >= fedEnd()`) and nothing sits in `pending` — never-fed trailing bytes (a blank line, a rate-dropped or oversize-discarded tail) can never commit and must not pin the fd, but an UNTERMINATED final fragment holds it deliberately: deletion turns that fragment into a record (`drainGone` feeds it), and a released fd made the record unrecoverable when the gone drain's flush failed transiently — nothing left to re-read, the tail lost uncounted, `settledGone` pinning the entry forever (the no-handle corner now counts `obs.LogArchiveErrors` and settles instead of wedging). An archive REWRITTEN in place (same inode, new content) is detected by `archiveReplaced` (fingerprint of the held fd, checked each `readArchive`) and restarts the file at zero — without it the reuse path would resume at a stale decompressed offset; and the EOF path only stamps `archiveDone` when the path still names the inode we read, so a replacement is not mistaken for consumed, and a replacement ACROSS A RESTART (a new identity at the path while the old stream had not fully shipped) counts `obs.LogPrefixLost` before the committed-to-zero reset, the plain path's counted equivalent — the incremental containerd/plain path is untouched when `f.compressed` is false. Caveat: `consume` drops empty physical lines, so multi-line formats needing a blank separator (Go panics) don't join for plain files (CRI's blank is a non-empty `…F ` line); indentation-based traces (Python/Java/.NET) join fine. Non-UTF-8 transcoding was intentionally dropped (Linux-only target) — lines are UTF-8/passthrough. **Per-workload annotation config** (`podconfig.go`, pod annotation `kubescrape.io/logs`, one JSON object): `exclude` (self-service opt-out; file stays tracked, skipped in sweep and status; a checkpoint-restored Pending backlog is DROPPED as intent — segments retired, checkpoint pruned, no loss counter — and a deleted excluded file is released without its segments ever being read or exported), `multiline` (overrides the source's stack-trace joining, consulted at pipeline construction — always after resolve), `serviceName`/`attributes` (overwrite resource attrs after Build — the workload is authoritative about itself), `rules` (compiled `logline.LineRule`s evaluated BEFORE the global chain; a pod drop is final, a pod keep still passes the global rules; flush creates the scratch slice when ANY tracked file carries pod rules — `anyPodRules`). Parsed once per file at resolve time; a malformed annotation warns and is IGNORED (must not lose logs). Opt-in `-logs-file-attributes` (`Config.FileAttributes`) stamps `log.file.name` (basename) + `log.file.position` on every record; `entry.start` is the record's start offset (first fragment's, threaded through cri as the entry data / `items[0].start` for trace groups), distinct from `entry.offset` (the post-record commit offset).
- **Scraper** (`agent/promscrape`): hand-written streaming parser for the Prometheus text format, classic + OpenMetrics (constant memory; do NOT replace it with `expfmt`, which buffers whole metric families — the 100k-series requirement is why it exists). The parser classifies samples into roles (`parser.go`); a sample repeating a label NAME is malformed — line dropped and counted, where Prometheus rejects the WHOLE scrape: per-line degradation is this parser's deliberate divergence, and byte-identical duplicate points in one payload are the failure class the refusal prevents; `convert.go` groups histogram/summary component series per family and label set into proper OTLP Histogram/Summary points — grouping state lives only for the current family, so memory stays bounded by the largest family, not the scrape. Exemplars are opt-in (`Config.Exemplars` / `-scrape-exemplars`): enabling them switches the Accept header to OpenMetrics; the parse mode is always detected from the response Content-Type (OM uses float-second timestamps, classic integer milliseconds). **`# HELP`/`# UNIT` become the OTLP `Description`/`Unit`** (the standard Prometheus→OTLP mapping — what an OTLP consumer displays): the parser records them per FAMILY (`Parser.metas`, bounded by `MaxTrackedFamilies` and a `maxMetaBytes` text budget, cleared per exposition like the TYPE table) and stamps them on every `Sample` through `classifyCached`, a per-name memo that also absorbs `classify`'s TYPE probe and suffix walks so the per-sample cost stays flat; UNIT is carried VERBATIM (no UCUM guessing). The batchers apply them where the metric is CREATED (`metricMeta.apply`, once per metric, never per sample) and charge their bytes to the chunk estimate (`metaFieldBytes` covers the field framing) — a split/cadvisor batch repeats every descriptor per described object, so uncharged HELP text would flush past the collector's receive limit. Conversion chunks per export via the `chunker`/`sink` interfaces at whichever of `BatchPoints` data points (10k) or `BatchBytes` estimated bytes (`defaultBatchBytes`, 3 MiB) comes first. **The byte bound is not optional**: a collector's default gRPC receive limit is 4 MiB and applies to the DECOMPRESSED message, and a point count does not bound bytes (10k points of a label-rich family marshal past 5 MiB → every export of that target is rejected = total metric loss). Each sink tracks the estimate (`numberBytes`/`histBytes`/`summBytes` for points, `resourceBytes` + `metricOverheadBytes` charged where a resource/metric is CREATED) and the converter re-checks it BETWEEN the points of a flushing histogram/summary family (`converter.emit`), so one huge family cannot overshoot either bound. **Counting only data points is not enough**: the split and cadvisor batchers emit one ResourceMetrics per DESCRIBED OBJECT, each with a full enriched attribute set plus its own copy of every metric descriptor — a 12k-pod KSM split flushed at an estimated 3 MiB and encoded to 6.7 MiB, i.e. straight past the limit the estimate exists to respect. An aborted parse (sample limit, truncated body, read timeout mid-body) still exports what was converted before the abort — every kind here is cumulative, so a partial scrape costs nothing but the missing series. **Hot-path allocation discipline** (bench_test.go reports it and `pkg/promparse`'s `TestParseAllocationBudget` + promscrape's `TestFilterSessionAllocationBudget` enforce it; ~4→0 allocs/sample): the parser interns metric/label names and label values per scrape (`internName`/`internValue`, capped — `maxInterned*`; `map[string(b)]` lookups don't allocate) and short-circuits even the intern probes with last-seen memcmp caches (`lastMetric`, per-position `lastKV` — consecutive lines of a family are near-identical; `string(b) == s` doesn't allocate), whitespace is skipped with `skipSpaceTab` (NOT `bytes.TrimLeft`, which builds an ASCII set per call), `converter.labelKey` fingerprints into a reused buffer (`keyBuf`/`keyLbl`) with a keyed `map[string(buf)]` lookup, the batcher's `metricByName`/`remember` cache the last family, and `parseAndExport` filters through `MetricFilter.session()` (per-scrape name→rule-bitmask memo plus a per-(matcher,value) label-regex memo — label values repeat heavily; the shared filter stays immutable). The last-seen caches also skip the byte scans: `parseSample`/`parseLabels` match the previous line's name plus terminator in one memcmp, and `parseQuoted` finds the closing quote with `bytes.IndexByte` — keep new per-sample code free of per-call closures and `fmt`. Per-scrape state is pooled across scrapes: `getParser`/`putParser` reuse the parser + its `bufio.Reader` (family `types` cleared per exposition, intern maps kept warm with cap-based clears), and the converter recycles histogram/summary accumulators via `histFree`/`summFree` — a 10k-series scrape parses in ~3 allocs. **Native histograms** (opt-in `-scrape-native-histograms`, `protoparse.go`): targets — splitter-backed ones included (`splitBatcher.addExponential` routes native points through the same groupBy/enrich/dropLabels machinery) — are offered the protobuf exposition (`acceptProto`) and a protobuf response is parsed as delimited MetricFamily messages: classic families flow through the same converter/filter/relabel machinery as text samples, native histograms convert to OTLP EXPONENTIAL histograms (scale = schema, zero bucket carried, span/delta buckets decoded dense with the OTLP offset = first Prometheus index − 1; `decodeSpans` advances past each span's length before applying the next offset — its gap/negative/missing-delta guards cap hostile shapes at `maxExpBuckets`). NHCB (schema −53) is REFUSED rather than converted — `isNHCB` is schema −53 with span-encoded counts and NO classic `bucket` rows, whose bounds live in `custom_values`, a field client_model v0.6.2 (Prometheus' own pin, so Prometheus' protobuf parser does not read NHCB either) does not generate: they are unreachable from the decoded message, and falling through to the classic branch shipped a correct count and sum beside a single bounds-less overflow bucket, i.e. a distribution every `histogram_quantile` reads as nonsense, counted nowhere. It counts `obs.ScrapeMalformed` standalone and `obs.ScrapeHistogramMixed{dropped="nhcb"}` for a child inside a native family (`TestProtoNHCBIsRefusedRatherThanShippedBucketless`). A message that ALSO carries classic `bucket` rows is not NHCB by that test — those bounds ARE readable — and converts through the classic path; a family with both native and classic data uses native. The protobuf path carries **exemplars** under the same `Config.Exemplars` gate as the text path (`Counter.Exemplar`, `Bucket.Exemplar` → `Sample.Exemplar`; a native histogram's family-level `Histogram.Exemplars` → the exponential point, capped at `maxExemplarsPerPoint`) — it must, or `-scrape-native-histograms` would silently switch `-scrape-exemplars` off for every target honouring the protobuf Accept. Prometheus 3.x quoted UTF-8 names ARE supported (`parseQuotedNameSample`/`familyToken` in `pkg/promparse`): the metric name as the first brace entry (`{"my.metric",code="200"} 1`), quoted label names, and quoted families on `# TYPE`/`# HELP`/`# UNIT` all unescape to the same strings so classification and metadata line up; the quoted paths are deliberately COLD branches that skip the last-seen caches, keeping the classic hot path's allocation discipline intact (bench-pinned).

Detecting only `container="POD"` meant the fold had not fired on any cluster since dockershim was removed in 1.24: a live containerd node emits ZERO such rows, so every pod grew a phantom third resource carrying `pause` as its image. The fold is POSITIVE-evidence only and both arms require the row's own `namespace`+`pod` labels — a cgroup cadvisor could not attribute (a conmon or shim scope, a failed CRI lookup) keeps its own resource rather than being merged, because `scope()` fills a resource from the FIRST ident seen and an impostor creating it would strip the pod's real series of `k8s.pod.name`, the namespace and the Prometheus `job`. Keeping its own resource KEY is only half the defence, and the other half is `lookupContainerID`, which decides what FILLS it: an unattributed row's container id comes from the cgroup PATH, and CRI-O's `crio-conmon-<containerID>.scope` — the supervisor's cgroup, mandatory under `conmon_cgroup = "pod"` — carries the SUPERVISED container's id, which `cgroupid.Parse` extracts on purpose (it says so, and hands the exclusion problem here). Resolving it built the impostor a byte-identical twin of the real container's resource, carrying the same cumulative `container_*` families with the supervisor's values: one Prometheus series taking two conflicting samples per scrape, so `rate()` fabricated a counter reset on every one of them, and `-cadvisor-rollups=false` did not reach it. So a container id is LOOKED UP only when the row proves it names that container (its own namespace+pod, or a container name); `FillContainerResource` vouches for its path explicitly (`pathVouched`), since `internal/agent/cgroupstats` collapses supervisor scopes onto the container's own scope itself. The cost is that a row whose CRI lookup inside cadvisor failed keeps its path identity unenriched — the path cannot tell it from conmon, and the other direction corrupts a real container's series. Their cgroup names the pause container — never look that ID up; `ident.image` is cleared too, it names the pause image; a folded row keeps its `id` on the data points, its only distinguisher from the pod-cgroup point — and so does EVERY row whose identity came from the cgroup path alone (`keepsCgroupID`), because an unattributable child of a pod slice whose name yields no container id (kata's `kata_<sandbox-id>`) shares the pod's resource key and, with `id` elided, rendered an attribute-less point identical to the pod-cgroup point's. On pod/container-identified rows (`ident.podScoped()`) the redundant `id`/`name`/`image` labels are elided from data points (`redundantOnPodRow` in `putFilteredLabels`; unresolved resources keep the image as `container.image.name`); rollup rows keep `id` — their only distinguisher on the shared node resource. Lookups share a 1-minute TTL cache. `-cadvisor-rollups=false` drops above-pod-level cgroup series AND pod-level rows of container-scoped families — the folded sandbox row included, deliberately: it is a COMPONENT of the pod's sum rather than a duplicate of it, so the pause container's own cpu/memory/fs is not reported in that mode; `podScopedFamily` (container_network_*) is the keep-list of families with no per-container breakdown. `Config.HealthMetrics` exports per-target `up`/`scrape_duration_seconds`/`scrape_samples_scraped` gauges after each cycle (`scrapeOutcome` collected in `cycle()`, `exportHealth()`). **A metadata outage costs ATTRIBUTION, not data** (`metabudget.go`): every enriched pipeline's per-object lookups share a per-scrape allowance of HALF the scrape timeout (`otlpingest`'s `lookupWaitBudgetFactor` shape — charged by measured ELAPSED time, no single lookup past what remains, and past it lookups are not ISSUED, which is the refused case reached by the clock instead of an RST). The two outage shapes are not alike and only one was survivable: a REFUSED metadata service fails lookups instantly and the scrape gets faster, while a HANGING one (partition, dropping firewall, blackhole) consumed the whole scrape budget and took BOTH kubelet pipelines down — measured live, 23 consecutive cycles of `context deadline exceeded` with ~3300 summary and ~6100 cadvisor samples parsed and then discarded, while `/metrics`, the one pipeline that resolves nothing, kept succeeding. The allowance is HALF because the other half is what the conversion and the EXPORT run in; giving the export its own context was rejected because `cycle()` waits for every scrape it starts, so an export outliving the budget stretches the node's cadence. Counted `obs.ScrapeMetaBudgetExhausted{pipeline}` ONCE PER SCRAPE (not per shed object, so a rate is comparable with `kubescrape_scrapes_total`) — and it is the ONLY signal for an object never asked about, since no request means `kubescrape_metadata_requests_total` cannot move and `SummaryUnresolved` covers only the summary pipeline. **The kubelet's THIRD endpoint** (`summary.go`/`summarybatch.go`, opt-in `-kubelet-summary`) is `/stats/summary`, which is JSON rather than exposition: it lives in `promscrape` anyway, not a sibling package, so it shares `kubeletGet`, the token, the TLS, `kubeletTimeout`, the `dueNow`/`spawn` scheduling and — the load-bearing one — `fillIdentityResource`, since a second exported seam beside `FillContainerResource` is how the identity would drift. It is decoded with `lightning/pkg/json` against a fixed path table (the `azurediag/decode.go` idiom) rather than `encoding/json` into a copy of the upstream schema: no new dependency, only the ~20 leaves that are exported are touched, and — the reason that matters — **an absent path is a NIL SLOT, so "the kubelet did not report it" cannot collapse into a real 0**, which a struct field would. Every point is a GAUGE carrying the STAT's own timestamp, not the scrape's: the kubelet refreshes volume stats on its own jittered cycle and the jitter COMPOUNDS, so stamping scrape time would fabricate freshness — measured on a live 12-pod node, n=72: min 6s, median 56s, p90 107s, max 167s, 42% older than the ~1m refresh period, so size a staleness alert against the p90 rather than the period (an unrefreshed stat re-sends an identical (series, timestamp, value) triple, which Prometheus accepts as idempotent). Inode counts take unit `{inode}` and NOT `1`, because a bare `1` on a gauge makes the OTLP→Prometheus rewrite append `_ratio` — a silent name corruption. **What only this endpoint has**: per-pod ephemeral-storage usage (the eviction quantity), per-container log bytes, inodes-USED anywhere, and every measurable volume including `emptyDir`/`configMap`/`secret`. What OVERLAPS is written down in `docs/CONFIGURATION.md` rather than denied — cadvisor is not silent about filesystems, and `k8s.container.ephemeral_storage.usage{fs.type=rootfs}` in particular is the same ground as `container_fs_usage_bytes`, separately computed, so the two can legitimately disagree. **STATIC PODS are the subtle part.** A kubelet mints a static pod's UID from its manifest, so it matches no API-server pod and a UID lookup misses forever — leaving the control plane (kube-apiserver, etcd, scheduler, controller-manager) permanently unattributed on the node likeliest to fill its disk. A bare namespace/name fallback fixes that and breaks something worse: a pod REUSING a name would lend its identity to its predecessor's statistics. So the UID cross-check is REDIRECTED, not dropped (`podAnswersFor`/`isMirrorOf` in `cadvisorbatch.go`): the kubelet stamps the same UID on the mirror pod as `kubernetes.io/config.hash`, copied to `kubernetes.io/config.mirror`, and a by-name answer is accepted ONLY when one of those equals the reported UID. A name-reusing pod carries neither and stays unresolved — exported with its payload identity, counted `obs.SummaryUnresolved{level}` once per OBJECT per scrape, losing the join and nothing else. OFF by default for RBAC, not cost: `/stats/*` authorizes against `nodes/stats` while the two Prometheus endpoints go through `nodes/metrics`, so a binary ahead of its ClusterRole 403s fleet-wide; the chart and manifests grant `nodes/stats` UNCONDITIONALLY, since enabling this through `extraArgs` is a thing people do. All pipelines toggle independently: `-logs`, `-metrics`, `-cadvisor`, `-node-metrics`, plus opt-in `-journald` and `-cgroup-stats`.
- **High-frequency cgroup sampling** (`internal/agent/cgroupstats`, opt-in `-cgroup-stats`): reads each container's `cpu.stat`, `memory.current` and `memory.stat` DIRECTLY every `-cgroup-stats-interval` (1s) and exports the DISTRIBUTION of each `-scrape-interval` window as ten gauges — `container_cpu_usage_{stddev,max,min,mean,samples}` (CORES, from the rate; the `_seconds` suffix is dropped because these are not a cumulative second count) and `container_memory_working_set_bytes_{stddev,max,min,mean,samples}`. `_samples` is THIS window's reading count and below 2 marks the four statistics beside it as the previous window's, re-stated; `_mean` exists because an agent running `-cadvisor=false`, or a node whose kubelet scrape fails, otherwise ships a distribution with no average anywhere to centre it. Prometheus-underscore names on purpose, so they sit beside the cadvisor series they annotate — the same deliberate divergence from OTLP-dotted naming that servicegraph makes for Tempo. **Why it exists**: cadvisor is scraped on `-scrape-interval`, so a container spiking to 4 cores for 2s inside a 60s window reports ~0.13. Measured on a real burst workload: sampler max 2.000 cores against cadvisor's 30s average of 0.394, a **5.1x gap**; on memory, cadvisor's single sample per scrape landed on the 67.7 MiB floor in 15 of 22 windows and caught the 260 MiB peak in 7, while the sampler's max/min bracketed a known 192 MiB allocation to +0.26%. Cost at 200 containers: **0.48% of one core (0.43-0.51%) and +5.5 MiB RSS (+4.7 to +6.3)**, A/B'd as the same binary over the same hierarchy with the sampler not started, ONE ARM PER PROCESS (RSS does not come back down, so two arms in one process measure the first one's high-water mark twice), CPU from `getrusage`, memory from VmRSS — quote the RANGE, not the mean, and size a DaemonSet with room above it rather than to it. The sweep is 0 allocs/op. The retired `0.255% / +0.9 MiB` was wrong twice over: it timed the sweep, the walk and the export in ISOLATION, and it read a Go heap number rather than the process's RSS — which is what evicts a pod. **The resource is the CADVISOR pipeline's, not one of its own**, so `resourceAttributes.pipelines.cadvisor` governs both; that coupling is the feature, since a join holds only while both resources are byte-identical for the same `container.id`, and a per-cgroup attribute pipeline would be a way to break the thing the gauges exist for.
  **This is the argued exception to `internal/metrics/series.go`'s closed aggregation set**, which says stddev "belongs in backend recording rules, which re-aggregate freely". That is right for log-derived metrics and wrong here for one reason: a recording rule can only re-aggregate what REACHED the backend, and these 1s readings never leave the node — `stddev_over_time` on a 15-60s series is the stddev of the averages, which is the very thing being hidden. WELFORD, explicitly, for the reason CLAUDE.md already gives (catastrophic cancellation on a large mean with small variance — exactly the CPU case; the naive sum-of-squares returns 0 at a 1e9 mean where Welford returns the right answer). POPULATION stddev, which is what Prometheus' own `stddev_over_time` computes, so the two are comparable; the in-repo test pins Welford against a hand-computed population stddev to 1e-12 so the two are comparable.
  Three rules carry the design. **Identity is rebuilt PER EXPORT through the same `Scraper.FillContainerResource` the cadvisor batcher uses** — one identity path, not a copy — so the resource is byte-identical to the cadvisor row's (observed on a live cluster across all 18 attributes for every resolvable container, and pinned in-repo by a fixture comparing the two paths attribute for attribute) and a pod label edit propagates exactly as it does there; caching it for the container's lifetime was tried and reverted, because it made the two resources diverge permanently on an in-place label edit. **An UNRESOLVED container is not exported at all**: a cgroup path yields a pod UID and a container ID but never a pod NAME, so unlike the cadvisor path (`service.name = ident.pod`) there is nothing to fall back to, and a series with no `job` cannot join anything — which is also, for free, what keeps the pod SANDBOX out, since a pause container's ID is in no pod's `containerStatuses`. **A sparse window holds the last value at most twice, per signal**; a vanished container flushes its final window for real (never held) and retires, because an OOM-killed container's last burst is the case the feature exists for. cgroup v1 DISABLES this pipeline alone and logs an ERROR — the version is a node property, and one flag must not take the log pipeline down across a mixed fleet — while an explicit `-cgroup-stats-root` that is not a v2 hierarchy stays fatal. Needs `/sys/fs/cgroup` mounted read-only: the chart does it behind `agent.cgroupStats.enabled` (with `mountPath` following `agent.cgroupStats.root`), `deploy/agent.yaml` carries flag, mount and volume commented out together, and an enabled agent that finds no pod cgroups WARNS periodically and publishes `kubescrape_cgroup_containers` at 0 — registered exactly when the sampler runs, so 0 means "on and finding nothing", never "off".
- **journald** (`agent/journald`, opt-in `-journald`, **cgo**): reads the journal natively via `github.com/coreos/go-systemd/v22/sdjournal` (libsystemd) — no journalctl subprocess. **This is deliberately IN scope** (unlike host `/proc` metrics, which are out — see the out-of-scope notes in README/COMPARISON): node/system *logs* (kubelet, containerd, systemd units) are how a node's Kubernetes plane is debugged and on many distros live only in the journal, so they are worth the cgo cost; host *metrics* (node_exporter's job) are not. journald is the SOLE reason the agent is CGO_ENABLED=1 / non-static, and that trade is now an OPERATOR's rather than a build-time given: it sits behind the `journald` build tag (Commands, above), which the Makefile's `TAGS` sets by default, so the shipped agent is unchanged — but `make build TAGS=azure` compiles the reader out and yields a CGO-free, fully static agent that needs neither libsystemd nor its six transitive `.so` files (`Dockerfile.static`/`make image-static` puts that pair on `distroless/static`). The tag is the WHOLE mechanism: `cmd/kubescrape-agent/journald_disabled.go` simply does not import this package. Anything that would re-introduce the cgo dependency elsewhere in the agent breaks `make verify-tags` (which builds `CGO_ENABLED=0 -tags azure`), and that is deliberate — the static build is only worth having while journald remains the single reason to give it up. One resource per unit (identity attrs pre-put, then `Attrs.Build` with the `journal` pipeline). The reader is decoupled behind a `source` interface (`next`/`close`) opened by `Reader.open` (default `openJournal` in `source_sdjournal.go`; tests inject a `fakeSource`), so `journald.go` (batch/convert/cursor/flush) has no cgo and is fully unit-tested. A MESSAGE over `MaxEntryBytes` is truncated on a rune boundary and the record carries `log.truncated`+`log.original_length`, counted `obs.JournalTruncated` (never a silent cut; the attribute keys are `logchain.AttrTruncated`/`AttrOriginalLength`, shared with the tailer's flush — which sets only the former, the pre-cut length being unknowable there). sdjournal seek: resume via `SeekCursor` then skip the (still-present) cursor entry once; tail via `SeekTail`+`Previous`; `next` loops `Next`/`Wait(1s)` honoring ctx. At-least-once via the cursor: committed only after successful export. A READER error closes and reopens the source from the committed cursor with backoff; an EXPORT failure does NOT — `flushRetry` keeps the batch and retries the SAME payload in place until it settles or ctx dies, counting `kubescrape_journal_export_failures_total` (ATTEMPTS, not lost entries; deliberately not the tailer's files-rewound counter, which cannot apply to a producer that rewinds no file and usually runs `-logs=false`). Re-reading would rebuild the batch, and REBUILDING RE-RUNS THE PER-RECORD CHAIN: measured across an outage spanning 8 restarts, 46 log-metric observations for 6 entries and 9 rule-drops for 1. Delivery is at-least-once; OBSERVATION is once per delivery. Holding the batch is affordable and safe — it is bounded by `BatchSize`/`MaxBatchBytes`, the journal itself is the buffer behind it (the reader goroutine simply blocks), and a crash loses nothing because the cursor commits only on success. The retry is unbounded on purpose: a genuinely undeliverable payload is the PERMANENT case, which `flush` settles itself. **This SUBSUMES the old cursor-less-first-run special case** — a reopen with an empty cursor seeks to the journal TAIL, so no batch may be discarded for an export failure, cursor or not; that is the invariant the old "do not simplify this into an unconditional restart" warning protected, now held generally rather than in one branch. `-journald-flush-interval` is measured from the LAST FLUSH (`ticker.Reset` after every flush): the old fixed-period tick plus a `time.Since(lastFlush)` guard could never pass on the tick it was sized for, so the flush slid to the next one and delivery ran at 2.00x the configured interval (a 10s setting delivered at ~20s). Fixing it doubles the export RPC rate at a given entry rate — that is the configured cadence finally being honoured, not a regression. Because the agent links libsystemd it is built **CGO_ENABLED=1** (the metadata service stays CGO_ENABLED=0 static); the image is `distroless/base` + copied libsystemd (+ libcap/libgcrypt/libgpg-error/liblz4/liblzma/libzstd), not `distroless/static` — all of which is true only of a build carrying the `journald` tag, which is what `make image` (`TAGS ?= journald,azure`) renders and `make image-static` does not.
- **Kubernetes events** (`internal/agent/events` + `internal/leader`, opt-in `-events`): a CLUSTER-SINGLETON pipeline — the agent binary run as its own single-replica Deployment (`charts/kubescrape/templates/events.yaml`, `deploy/events.yaml`) with every per-node pipeline off, deliberately NOT in the DaemonSet: that would put cluster-wide `events` read plus lease/configmap write on every node (the DaemonSet's SA holds only `nodes/metrics: get`) and cost one Lease poll per node per retry period. The singleton's own namespaced Role scopes `get`/`update` on the position ConfigMap and the election Lease with `resourceNames` (`create` stays unscoped — RBAC ignores `resourceNames` there, and create alone cannot touch an existing object), so code execution in the events pod cannot rewrite the agent-config ConfigMap sharing its namespace; `internal/chartcheck` asserts the names track `-events-lease`/`-events-position-configmap`, since a flag changed without the Role is a pod that starts and then cannot persist a position. `leader.Run` wraps client-go `leaderelection` in a re-entry loop (its `Run` returns on lease LOSS and never re-acquires; `OnStoppedLeading` fires even if this candidate never led, and it dispatches `OnStartedLeading`/`OnNewLeader` asynchronously, so no callback can prove the work goroutine exists: an `acquireLatch` on the resource lock latches a successful acquisition SYNCHRONOUSLY, `elect` joins the work goroutine whenever acquisition happened — even when ctx cancels before it was scheduled — and the leading gauge reports down only after that join). `Reader.Run` is the leader-only work: batch → export → and only after the collector ACKS, advance and persist the position. **The position is a ConfigMap, not a node-local file** (`ConfigMapStore`): the leader moves, so the successor of a killed pod must read where its predecessor stopped; a written position is only ever a LOWER BOUND on what was delivered, which is what makes a zombie writer harmless (worst case a replay) and why no fencing is needed. Position = watch `resourceVersion` + a timestamp `Watermark`: the RV resumes exactly, but only while inside the API server's watch window (minutes) — past that the watch fails Gone and `expire` arms `relist`: the backlog is replayed as a PAGINATED LIST (`replayBacklog`, 500/page, watermark filtering what was already shipped) and the replay is secured by a fact THIS PROCESS observes — the last page read and every listed entry exported — never by a watch BOOKMARK: kube-apiserver serves the core/v1 events watch straight from etcd and sends no bookmark for it, so the old `secureReplay` hold was permanent after the first relist and the position ConfigMap stopped advancing for the process' life (a bookmark, where a cluster does send one, still secures — it is a strictly stronger statement). The walk blocks the single reader goroutine and services no ticker, so its count trigger is clamped to the retained-batch cap and it flushes its tail BEFORE opening the watch — unclamped, an `-events-batch-size` above that cap made the trigger unreachable and shed the whole backlog into `obs.EventsOverflowDropped` (measured: 13,696 of 30,000 events lost) before the watch even opened. Accepted trade: the watch is positioned at a snapshot revision taken before the walk, so a long walk can age it out; recovery is another relist, bounded by the committed watermark — while the replay is UNSECURED, `settle` HOLDS the position (RV and watermark; the exported high-water accumulates in `heldWatermark` and folds in on securing), because the backlog arrives in STORE order and a commit of a rendered prefix's maximum positioned a restarted stream PAST undelivered lower-RV backlog — silent loss on exactly the recovery path; the cost of a death mid-replay is a full re-replay (duplicates, which at-least-once tolerates). A stream that redelivers (committed resume, relist, cold `start`) first DROPS the retained batch — the entries re-arrive, and keeping them duplicated the backlog once per restart and grew memory without bound across a collector outage; only the cold skip-backlog path, whose List revision is past the buffered entries, retains them. Taking the cold-start policy there instead would skip to the current revision and silently lose the gap the relist exists to cover — but only once something has been exported (a zero watermark cannot filter, so a cold `-events-start=end` expiry honours the start mode). A BOOKMARK (`AllowWatchBookmarks`) applies immediately only when the batch is EMPTY; otherwise it is ahead of unexported records and defers to the flush covering them (the tailer's watermark discipline). `Modified` IS an occurrence — Kubernetes aggregates repeats into one object with a growing `count`, so handling only `Added` loses "BackOff x47"; `Deleted` is TTL expiry and ignored. The RESOURCE is the INVOLVED OBJECT's (a Pod resolves through `metaclient.PodByName` with the UID cross-checked, so a recreated pod of the same name cannot lend its identity to an event about its predecessor), which is what makes events correlate with that pod's logs; `actx.Node` is deliberately left NIL — the node an event is about is the object's property, never the singleton reader's. The full chain applies in the tailer's order (scrub → logAttributes → enrich → logMetrics → rules), and `-events-position-interval` bounds the REPLAY after a hard kill (never loss; a graceful stop always writes a final position from a detached context).
- **Azure diagnostics** (`internal/agent/azurediag`, opt-in `-azure-diagnostics`): consumes diagnostic-settings output (resource logs AND platform metrics) from an Event Hubs namespace over its KAFKA surface (franz-go, port 9093, TLS). Cluster-scoped like `-events` — same singleton Deployment (`azure.enabled` renders into the events template; either section's enabled creates the Deployment) — but with NO leader election: the Kafka consumer-group protocol IS the coordination, and the group's committed offsets ARE the resume position (no ConfigMap; replicas > 1 share partitions). Delivery is ack-gated at-least-once: a poll's records convert to plog+pmetric, and `source.commit` (CommitUncommittedOffsets) runs only after BOTH signals are acked (`Reader.deliver`); a permanent rejection or an undecodable message is counted and committed past (poison must not wedge the partition), a transient failure retries in place without committing. The kgo client sits behind the journald-style `source` interface (`poll`/`commit`/`close`), so the loop is unit-tested with a fake and `kafka_test.go` runs a REAL kgo group against `kfake` (join, `^insights-.*` regex topics, commit, resume-past-committed). **A connection string may be NAMESPACE- or ENTITY-scoped** (`parseConnectionString` — one parser for `Endpoint=`/`EntityPath=`, matching keys case-insensitively as the Azure SDKs do; each part is cut at its FIRST `=`, which is free insurance for a future `=`-bearing field rather than a fix for a live bug, since neither field read today has one — `TestParseConnectionString` says so explicitly so the cut is not mistaken for load-bearing): an `EntityPath` both names a hub and BOUNDS the credential (SAS scope is the resource the rule was created on), so `Resolve` makes it the topic when none is configured (`applyEntityPath`). Two reasons of different strength, kept apart deliberately because one is evidence and one is inference: CERTAIN — the `^insights-.*` default is a PATTERN and an entity is rarely named `insights-...`, so it matches nothing and the consumer joins the group then reads no topic, indistinguishable from a quiet hub; CONTESTED — being a pattern it also requests namespace-wide metadata, which azure-event-hubs-for-kafka#159 (open, entity-level OAuth) has the broker force-closing, knative#2692 reproduces with an entity-scoped SAS key, and one tester says SAS does not hit; naming the topic means never asking the question. Explicit `-azure-eventhub-topics` still win; a list omitting the entity is WARNED at startup (every fetch would fail authorization with the reason only in kgo's error log). **Several hubs = one client per CREDENTIAL, not per hub** (`sources.go`, `ResolveSources`): a Kafka connection authenticates exactly once, so a namespace-scoped string or managed identity consumes any number of hubs over ONE client (`-azure-eventhub-topics`), while N entity-scoped strings are N clients — hence both `-azure-eventhub-namespace` and `-azure-eventhub-connection-string-file` take comma lists, and `startAzure` spawns a Reader per resolved source (each owning its kgo client, offsets and readiness gate, named `azure-eventhub[ns/topics]` once there is more than one so an unreadable hub is identified rather than masked). A namespace alongside connection strings stays the single Endpoint OVERRIDE; more than one is REFUSED (no positional rule the flag surface suggests), shape-checked in `validateAzureFlags` so `-check-config` catches it without reading the files. Duplicate (namespace, topics) pairs are refused. **Groups are auto-disambiguated** (`disambiguateGroups`): Event Hubs' Kafka groups span a NAMESPACE, and a group's LEADER computes the assignment from the union of members' subscriptions using its OWN metadata — which an entity-scoped credential lacks for its siblings' hubs, so it assigns them nothing and starves them invisibly. A namespace holding more than one client therefore gives each `<group>.<topics>`, while a namespace with one client keeps the name verbatim (and clients in DIFFERENT namespaces always do, since their groups cannot collide). There is no same-subscription exemption because that case cannot arise — a namespace fixes the brokers, so two clients with the same topics are the duplicate `rejectDuplicateSources` refuses first; relaxing that refusal would need the exemption back, since members deliberately sharing one subscription SHOULD share a group. The cost, documented for operators: growing a namespace from one client to several renames the first's group, and the committed offsets ARE the resume position, so that transition restarts per `-azure-start`. The password is the string VERBATIM and **stripping `EntityPath` is the wrong instinct** — scope follows the rule the key was created on so stripping cannot widen access, while an entity-level rule NAME is only unique within its entity; the 2018 quickstart text claiming entity strings "will not work" was posted beside a promise to enable them and never revisited. **Auth** (`auth.go`): connection string → SASL PLAIN (user `$ConnectionString`, file re-read per session, password the string VERBATIM — a credential is never rewritten in flight); managed identity → OAUTHBEARER with a hand-rolled Entra token source (workload identity's client_assertion exchange when `$AZURE_FEDERATED_TOKEN_FILE`+client/tenant are present, else IMDS; cached, refreshed `refreshMargin` ahead of expiry, stale-but-valid served on refresh failure) — deliberately NO Azure SDK, same trade as rejecting OAuth2/SigV4 in otlpexport. **Decode** (`decode.go`): the `{"records":[...]}` envelope is walked with lightning `ArrayEach` (>= v0.0.62 — extracted from the hand-rolled splitter that used to live here; STRICT syntax, so a malformed envelope is one decode error at the split, never elements silently fused, and the callback form materializes no per-poll [][]byte); per record one lightning `GetPaths` pass extracts only the envelope fields; classification is per RECORD (`metricName` + ≥1 aggregation → metric), since one hub may carry both. Logs keep the verbatim record JSON as the body and run the full chain in the tailer's order (scrub → logAttributes → enrich → logMetrics → rules; `resultDescription` is scrubbed too — the one attribute copied from free text). The enrich-derived `cloud.resource_id` and `azure.resource_group.id` are then ELIDED from each record (`redundantOnAzureResource`, the `redundantOnPodRow` move): the converter is authoritative for identity here — it parses the ARM id from the envelope's own `resourceId` — while enrich re-derives one from the body TEXT, so keeping both shipped two values under one key (the resource's verbatim, enrich's lowercased, and a backend that flattens the two picks the winner) plus `azure.resource_group.id` as the group's full ARM ID beside the resource's `azure.resource_group.name`. That `.id` suffix is load-bearing: the key was `azure.resource_group` until a semconv v1.44.0 audit found the registry defines `azure.resource_group.name` and nothing else in that namespace, so the bare key sat one dot from a real attribute while holding a DIFFERENT SHAPE of its value — semconv's naming guidance warns about exactly that, since a future OTel definition of the bare key would conflict silently rather than coexist (wire-visible rename; anything selecting the old key must be updated). NOT unified with it: `azure.category` (the converter's, from the envelope's `category`) and `azure.event_category` (enrich's, from an `eventCategory` key in the body) are DIFFERENT SOURCE FIELDS carrying different values — a resource log's `category` is the diagnostic-setting category (`SQLSecurityAuditEvents`), an activity log's `eventCategory` is `Administrative` — and merging them would both conflate them and let enrich (which runs AFTER `Stamp` with overwriting semantics) clobber the authoritative envelope value. Measured against a live Event Hub: 286 B on every record, 1 MB per 3,500-record payload. It runs AFTER the chain, so log-metrics and the keep/drop rules still see the attributes, and it is GATED on the resource actually having identity — an envelope with no readable `resourceId` leaves enrich's copy as the only carrier, and dropping it there would lose the identity rather than de-duplicate it. Scoped to this path: the tailer, journald and ingest have no ARM resource, so for them the record attribute is the only carrier and `logenrich` still emits it; metrics become GAUGES `<prefix><metricname>.<agg>` (count/total/minimum/maximum/average, `azure.metric.timegrain` as a dp attribute) — gauges because each value is one closed pre-aggregated window (the webdevops-exporter shape), NOT delta sums (Mimir rejects delta) and NOT cumulative (would need per-series state). The ARM resource is the OTLP resource (`resourceid.go` parses the UPPERCASED id): cloud.resource_id verbatim, subscription/rg/type/name lowercased, service.name=resource name, service.namespace=resource group, service.instance.id=lowercased id (two same-named resources must not merge). - **PII scrubbing** (`agent/logscrub`, config `logScrubbing` section, shared by tailer/journald/ingest): curated built-in patterns (`builtin: [defaults]` = bearer/basic-auth/secret-kv/aws-key/private-key/**url-userinfo**; `email`/`credit-card` opt-in by name — the AUTHORITATIVE list is `defaultSet`, and this prose plus README plus CONFIGURATION.md all said "five" for as long as it had six, so an operator pinning the documented names instead of `defaults` silently lost DSN-password redaction; `TestDefaultSetIsDocumented` pins all three now) plus user regex rules, applied to log BODIES **before** logattrs/enrich/log-metrics copy from them (enrich's exception.stacktrace and lifted attributes must not carry secrets). Every built-in carries a prefilter so the no-match path is 0 allocs (~0.4µs/line for the default set, BenchmarkScrubNoMatch). **A prefilter's job is to admit only what the regex can MATCH, not what contains its keyword**: `secret-kv`'s scanned for the bare words key/secret/passw/pwd/token anywhere, and a 1 MiB record containing "token" then cost 100 ms of the SINGLE sweep goroutine that serves every log file on the node — the admission IS the cost. It now checks the regex's own tail shape in one pass with a first-byte dispatch (`secretKVCandidate`: keyword, optional `keySuffix`, `["']?\s*[:=]\s*["']?`, one value byte), which is 19x faster on that line (117ms → 6.1ms/MiB, BenchmarkScrubHostileLongLine) and 30% faster on ordinary lines. It must stay a strict SUPERSET of the regex — narrower means a secret ships unredacted, which `TestPrefilterIsNotNarrowerThanItsRegex`, `TestSecretKVPrefilterCoversEveryMatchingShape` and `FuzzSecretKVPrefilterNotNarrower` exist to catch (Go's `\s` is `[\t\n\f\r ]` and does NOT include `\v`, so treating `\v` as whitespace in the value class alone made it narrower). Unknown pattern names and bad regexes fail startup. Counts `obs.LogScrubbed{pattern}`. Log-metrics see the SCRUBBED line. The value branches decode ONE level of escaping, and the plain and escaped forms use OPPOSITE rules for `\"` — inside `\"…\"` it TERMINATES, inside `"…"` it is CONTENT — selected by the opening quote, escaped pair tried first. That asymmetry is the whole fix for the worst failure this control can have: `{"msg":"password=\"hunter2\" tail"}` used to emit `password=[REDACTED]"hunter2\"`, a line that CLAIMS a redaction and still carries the secret, which `kubescrape_log_scrubbed_total` cannot distinguish from a clean one and which a reviewer's eye stops reading at `[REDACTED]`. `url-userinfo` redacts to the LAST `@` in the token for the same reason (`svc:p@ss@db-1`). What remains PARTIAL is named and pinned rather than left to be rediscovered (`TestKnownPartialRedactions`: an unquoted value containing its own delimiters, and more than one level of escaping), and the accepted OVER-redactions likewise (`TestKnownOverRedactionsAreAccepted`) — `TestQuotedCredentialsAreRemovedWhole` is the cross product that keeps the core guarantee from being re-asserted over a corpus curated around its holes, which is the exact defect a review found in this test's predecessor. LIMITATION: scrubbing is per-record, so a multi-line PEM key logged line-by-line (tailer/journald) only has its BEGIN line redacted — the base64 body lines are separate records lacking the telltale; a whole-key-in-one-record (JSON-embedded, or the ingest path) redacts fully.
- **Log-line attribute lifting** (`agent/logattrs`, config `logAttributes` section, shared by `-logs` and `-journald`): ordered rules map a JSON/logfmt key in the line to a resource/scope/log attribute. JSON is scanned once for all rule paths via `github.com/JohanLindvall/lightning/pkg/json` `GetPaths`+`DecodeAny` (dotted keys descend into nested objects); logfmt via the `logfmt` reader; do NOT reintroduce `encoding/json`. **`key= value` reads as an EMPTY value** since logfmt v0.0.10 (it yields `("key","")` and then the bare key `("value","true")`, go-logfmt's reading); v0.0.9 and earlier skipped the whitespace and read it as `("key","value")`, so a line written that way lifts an empty attribute — and mints an empty label in `internal/logline`, which shares the reader. `Iterate` still yields RAW values (quotes stripped, escapes intact): unescape with `AppendUnescape` (the pre-v0.0.10 name was `Unescape`), guarded by `NeedsUnescape` to skip the copy. Resource/scope attributes participate in the flush grouping key (`logGrouper` in the tailer, the `unit\x01res\x01scope` key in journald `convert`) so records with different line-derived resource/scope attrs split into distinct ResourceLogs/ScopeLogs; log-target attrs go on the record. Typed: JSON numbers with no fraction → PutInt, else PutDouble; bool → PutBool.
- **Unified positions** (`agent/positions`, flag `-positions-file`): one JSON file holding both the tailer's per-file `LogPos` map and the journald cursor. The `Store` keeps both sections in memory and rewrites the whole doc atomically under a mutex, so the tailer and journald (different goroutines, independent sections) never clobber each other. It is the ONLY offset persistence (the legacy standalone `-checkpoint-file` was removed); the tailer's `checkpoint` type is a `positions.LogPos` alias. **journald has no standalone cursor file** — its cursor persists only through `positions.Store` (`journald.Config.Positions`); without a positions store it starts at the journal tail each run.
- **OTLP ingest** (`agent/otlpingest`, opt-in `-ingest`): a gRPC (`:4317`) + OTLP/HTTP-protobuf (`:4318`, `/v1/logs`+`/v1/metrics`) receiver for LOGS AND METRICS apps push to the local agent. **TRACES ARE NOT HERE** — they are received by the `-service-graph` trace tier, because pairing an edge and sampling a trace both need every span of that trace in ONE process and a per-node receiver holds an arbitrary subset by construction; `ServerConfig.Exporter == nil` disables the logs/metrics services and routes entirely (traces-only mode, which is what the tier runs), and `Traces == nil` does the same for traces, so a sender aimed at the wrong receiver gets Unimplemented/404 rather than an ack for telemetry nothing will use. `ServerConfig.Ready` fires once every configured listener is BOUND (the HTTP arm is `net.Listen`ed explicitly rather than `ListenAndServe`d, so a bind failure is known before a readiness gate clears). `Enricher` finds a container id (`container.id`/`k8s.container.id`, configurable) or pod uid (`k8s.pod.uid`) on a resource, resolves via `metaclient` (Container = exact incarnation, else `PodByUID`), and merges the `attrs.Builders.Ingest` k8s attributes with the sender authoritative about ITSELF — **except the RESOLVED-IDENTITY keys** (`mergeAttrs`/`Enricher.resolvedWins`: `attrs.ReservedIdentity` minus this enricher's lookup keys minus `senderControlledIdentity`, i.e. `k8s.namespace.name`, `k8s.pod.name`, `k8s.pod.ip`, `k8s.node.name`, `k8s.container.name`, `container.name`), which this receiver just read from the API server FOR THAT RESOURCE and which therefore OVERWRITE whatever the sender claimed. That overwrite is the security half: `route.match` keys tenancy on `k8s.namespace.name`, so on a resolvable resource a forged one cannot reach the router (the receipt-time strip below is the same rule for the resources that DO NOT resolve, where there is nothing to correct with). Everything descriptive the sender declared is left alone, and the two exemptions this carves (the lookup keys, `senderControlledIdentity`) are exactly the strip's below — `service.name` sitting outside `ReservedIdentity` for both — so the two seams say ONE thing about what a sender owns. Metrics mode (`-ingest-metrics-mode`): `resource` (id on the resource), `datapoint` (id per point → `split.go` regroups every point into per-object ResourceMetrics, all 5 metric types; points with no id fall back to the resource-level id), or `auto` (resource if every RM has an id, else split). In a split group the resolved identity **overwrites** the copied sender attributes (`overwriteAttrs`) rather than merging: the sender is authoritative about ITSELF, not about the other objects it describes, so its own `k8s.pod.name`/`service.name` would otherwise mislabel every split point. `EnrichTraces` still exists and is used by the tier's entry path. **Peer-IP fallback** (`-ingest-peer-ip-fallback`, opt-in): a resource with NO id resolves via the connection's SOURCE address (`peer.go`: gRPC `peer.FromContext` / HTTP RemoteAddr → ctx; `Enricher.peerAttrs` → `metaclient.PodByIP` → `GET /v1/pod-ips/{ip}`; the store's `byPodIP` indexes LIVE, running-phase, non-hostNetwork pods only — deleted and Succeeded/Failed pods drop out immediately since pod IPs recycle); counts as `obs.Ingested{peer_ip}`; the splitter's ""-group applies the same fallback. **It is only correct at FIRST RECEIPT** — the address names the sender exactly once, on the hop the sender opened — which is why `Config.PeerReject` exists: a resolution the receiver vetoes (the tier vetoes its OWN workload's pods) is counted `obs.Ingested{peer_ip_rejected}`, warned once per minute and left UNENRICHED, and `peerAttrs` returns `(map, rejected)` so the caller does not also tally `unresolved` (the counter is per RESOURCE). **A sender's IDENTITY CLAIM dies at the door** (`reserved.go`, `Enricher.SenderIdentityStrip` wired as `ReservedAttrs.Identity` beside `route.ScriptMarker` by `cmd/kubescrape-agent`'s `ingestReservedAttrs` and installed on the DaemonSet's `-ingest` listeners AND the tier's application ports — never on the tier's internal hop, which is authenticated and terminal): the application-facing receivers strip the Kubernetes identity keys a sender declares about ITSELF (`attrs.ReservedIdentityKeys()` minus THIS enricher's lookup keys, minus the sender's own service triple) at first receipt, not just the plumbing markers. `internal/agent/route` keys TENANCY on `k8s.namespace.name`, so on a listener with no credentials a pod declaring someone else's namespace has its records exported to that tenant's endpoint under that tenant's headers — the same attack `attrs.ReservedIdentity` refuses on the pod-annotation surface, reached here through a door that asks for nothing — and the `k8s.pod.*`/`k8s.node.name`/`container.*` siblings ride along because they are exactly what a RESOLVED lookup overwrites (so on a resolvable resource the strip changes nothing) while on an unresolvable one they would name someone else's pod on every series and every log-derived metric bound to the resource. Enrichment CANNOT stand in for it: it owns those keys for a resource it RESOLVES, but a resource with no resolvable id has no correction available and there the declaration was the only namespace there was. **The two strips are two EVENTS**: the identity half counts `obs.IngestIdentityStripped{key}` and logs at DEBUG (throttled per key), because every conformant SDK names its own pod — an OpenTelemetry-Operator-instrumented workload ships five of these keys on every push — so folding it into `obs.IngestReservedStripped`, whose help says "reserved for kubescrape's own plumbing", gave a healthy cluster a forever-climbing counter, an unclearable alert written from that help, and a throttled Warn accusing honest senders; the plumbing half keeps the Warn, where a single occurrence is a sender worth finding. Three deliberate exclusions: `service.name`, which `ReservedIdentity` leaves out because it is DESCRIPTIVE and naming its own service is the point of a sender; `service.namespace`/`service.instance.id` (`senderControlledIdentity`), for the SAME argument applied honestly — kubescrape reads neither, a masquerade only needs the sender-controlled `service.name`, and deleting them costs a plain-SDK sender half of its job+instance pair with no replacement. **`Enricher.resolvedWins` exempts the SAME two**, so the exemption means one thing on both paths: it briefly did not, and the strip preserving them while the resolved-wins overwrite destroyed them for every sender the lookup succeeded on — excused as "mergeAttrs corrects them anyway" when neither key steers any kubescrape behaviour — silently renamed every resolved sender's Prometheus job to `<k8s-namespace>/<service.name>` and pinned its instance to the container ID, which changes on every restart and mints a fresh series each time. The DESCRIBING arm (`split.go`) still overwrites all three, because there the resource names an object other than the sender; and the LOOKUP KEYS (`-ingest-container-id-keys`/`-ingest-pod-uid-keys`), because the strip runs BEFORE enrichment and stripping what the attribution is MADE BY turns the receiver into one that resolves nothing — which is the trap in "just strip every identity key", and why this is `SenderIdentityStrip` rather than `attrs.ReservedIdentityKeys()` at the call site. **That exclusion leaves a RESIDUAL, and the strip must not be read as closing the tenancy question**: the metadata service's `/v1/pods/{ns}/{name}` is unauthenticated and serves each container's id plus the pod UID, and the store's container index is CLUSTER-wide rather than node-scoped, so a pod that can reach both services reads a victim's `container.id`, pushes it while declaring NO `k8s.namespace.name` of its own, and `mergeAttrs` derives the victim's namespace — which `route.match` then keys tenancy on, sending the payload to that tenant's endpoint and `X-Scope-OrgID`. The strip removes nothing on that path because nothing is forged on the wire: the value is DERIVED, correctly, from a stolen input, so `kubescrape_ingest_identity_stripped_total` does not move either. It is documented rather than closed because the obvious closure fails on both axes — refusing a resolved object on another NODE (`Config.NodeInfo`) would cost legitimate attribution (the datapoint/split path exists so a sender can describe objects across the cluster, the trace tier receives from every node by design, and a DaemonSet receiver fronted by a Service round-robins away from the sender's own node) and would still not close it, a co-located victim being the common case in a cluster that spreads namespaces across nodes. Narrowing the victim set while silently un-attributing honest senders is the worse bargain. What closes it is authenticating the listener or the metadata service. `TestStolenLookupIDStillResolvesTheVictimsNamespace` pins the current answer, so this paragraph and the code cannot drift apart. The COST, stated so it is a decision: a sender this receiver cannot resolve LOSES its own honestly-declared `k8s.pod.name` and the rest of the Kubernetes half, because nothing at an unauthenticated door can tell an honest declaration from a forgery — on the trace tier that is an application whose spans carry k8s attributes but no `container.id`/`k8s.pod.uid` and no working peer-IP fallback; it keeps its service triple, so it is still named, just no longer placed. Payloads are forwarded as received — deliberately NO agent-side ingest batching (an earlier `otlpbatch` layer got cut: it duplicated the collector's batch processor one hop early and was the only layer that traded a guarantee away; batch in the sender's SDK or the downstream collector, and every forward keeps the sender's own retry semantics). Log bodies additionally run `logenrich.ApplyBody` (non-overwrite variant) when `-enrich` — and the OPERATOR'S COST LEVERS reach pushed logs too (`logchain.go` in this package, `ServerConfig.Rules`/`LogMetrics`/`LogAttrs`): after enrichment, ingested records run the same compiled `logs.rules`, feed the same `logMetrics` set and take the same `logAttributes` lifts as the four producers, observe-and-filter-IN-PLACE rather than through `logchain.Chain` (which BUILDS records; these already exist in the sender's grouping) but through the same Resolver/LowerSeverity/LineFilter/Bind/Prune primitives, so one config selects identically however the line arrived. Only the `target: log` half of `logAttributes` is WRITTEN here: a producer applies a resource/scope lift by GROUPING records into a resource (or a ScopeLogs) that carries it, and a pushed record already lives in the SENDER's grouping, so writing there would stamp one record's value onto every record beside it. The two unwritten halves are NOT alike, and reading them as one is what this bullet used to do: the RESOURCE half still RESOLVES (`Resolver.SetLifted`, exactly as `logchain.Chain.Emit` ranks it) for rule keys and metric labels, which is where the divergence was visible; the SCOPE half is DROPPED on this path — `logattrs.Result.Scope` is never read here, so a `target: scope` lift a tailed line stamps onto its ScopeLogs simply does not exist on a pushed one. It resolves for nothing on any path (no producer passes `Lifted.Scope` to `SetLifted` either), so the divergence is stamping alone, and a `logs.rules` key or `logMetrics` label naming a scope-lifted attribute selects on nothing everywhere — but only on ingest does the attribute also fail to be EXPORTED. Metrics observe every record before the rules; a dropped record is still ACKED (counted `obs.LogRulesDropped`); an all-dropped payload acks without a send. **THE COUNTING UNITS DIVERGE HERE, and this is the ONE place in the repo where they do**: a log-derived metric OBSERVATION on the ingest path is once per RECEIVE ATTEMPT — a NACKed push that the sender retransmits runs the chain again and observes again — while `obs.LogRulesDropped` is once per DELIVERY (counted when the push ACKS), so a lost ack still redelivers and recounts and no receiver can dedupe that. It is the mirror image of journald's promise (delivery at-least-once, observation once per delivery) and it follows from the shape: these records arrive already built in someone else's grouping, so there is no positional proof to hang `logchain.Input.Observed` on. `obs.LogScrubbed` is in the first class too — `EnrichLogs` bumps it per receive attempt — so it inflates across a sender's retries as well. The adversarial review hardened this seam: line enrichment now runs HERE too (`logenrich.ApplyBodyText`; EnrichLogs only scrubs), over ONE bounded text rendering per body shared by enrich/metrics/rules — a STRUCTURED body renders via AsString (it used to skip enrichment entirely, so the same JSON line selected differently pushed vs tailed) with its size ESTIMATED first (a materialization-free walk; AsString costs 14-18x wire bytes in transient heap), and `__severity__` falls back to the OTLP severity-NUMBER band for text-less records (`logchain.RecordSeverity`, both call sites). Sender-bounded: bodies over 1 MiB, resources wider than 64 attrs (the store retains a per-series serialization of the WHOLE resource — width is retained heap) and resources past the first 256 of a push skip line-derived processing/observation, counted `obs.IngestChainSkipped{reason}`, data still forwarded; duplicate resource KEYS (legal on the wire, impossible from any agent-built resource) are deduped last-wins before Bind. **It is no longer the store's identity that depends on it** — `metrics.resourceAccum` proves key-uniqueness before it takes its one-pass shortcut, so an undeduped resource keys as the identity it renders whether or not this ran (it used to fold `{k=v,k=v}` to the EMPTY resource's accumulator and merge with every attribute-less one, which is what made this call load-bearing). It stays for the two readers the store cannot speak for: `logchain.Resolver` resolves a metric label or rule key off the resource with `Get`, i.e. FIRST-wins against the store's LAST-wins render, and the payload FORWARDED to the collector would otherwise carry the same ambiguity onward. Counts into `obs.Ingested{enriched,unresolved,peer_ip,peer_ip_rejected,split_capped}`. **A pushed metric carrying NO data points dies at receipt** (`emptymetrics.go`, `dropEmptyMetrics` on both transports, after the `ingest:` admit hook and before the all-rejected check, so an all-empty push is acked without a send; emptied scopes and resources go with it, as do ones that arrived empty). An empty metric is LEGAL OTLP, which is exactly the problem: nothing downstream rejects one, so it would ride enrichment, the split regrouping (whose `metricGrouper.route` deliberately PRESERVES a point-less descriptor — right for a regrouper, wrong for the wire), the scripts, the router, the buffer and the wire, spending its name/description/unit/framing against the send cap on every push and delivering no measurement, with no counter anywhere moving. kubescrape's OWN producers cannot emit one — every metric-building path in this repo appends a metric's first data point in the SAME function that creates its shell, and the two places where a shell could outlive its points are gated far from the render (`cgroupstats`' `if cpu.emit || mem.emit` snapshot gate plus `export`'s `DataPointCount() == 0` short-circuit; `transform`'s `pruneDataPoints` returning `empty` so the metric is removed with its last point — its UNTYPED arm answered `false`, i.e. "no points to drop" read as "nothing to report", so an untyped metric survived every prune; and `cumagg.Store.Render` now drops the shells an aggregator left empty, because `SumMetric`/`HistMetric` append a shell BEFORE the caller knows whether it has points and the contract was kept only by each caller's own precomputation — right in both today, enforced in neither) — so a rate on `kubescrape_ingest_empty_metrics_dropped_total` is always a SENDER creating descriptors it never records into, and that counter plus its throttled warn is the only report of it that exists. `internal/pdatacheck.EmptyMetrics` is the assertion that keeps the by-construction half honest as producers are added; `pkg/otlpsplit` has its own inlined copy rather than importing internal/ from a pkg/ test. **The splitter's memory is bounded separately from the byte budget** (`maxSplitGroups`): each split group is a full COPY of the sender's resource, so the cost scales with a push's DATA-POINT count rather than its bytes — a small payload naming a thousand objects inflates into a thousand enriched resources — and past the cap the remainder shares the source resource unenriched, counted `split_capped` — as are the byte budget's mid-push refusals, INCLUDING for an already-grouped id whose further descriptor copies it refuses (those points fold to the stripped overflow resource; exempting existing groups was rejected because descriptor-copy cost would then be quadratic in the payload and sender-controlled). Two identity rules the split path gets right and a string comparison did not: tokens are KIND-TAGGED, so a point naming a container id and a resource naming that container's pod uid are the SAME object (`sameObject` resolves both through the per-request cache rather than comparing token strings, which used to overwrite the sender's own resource with derived identity); and before `overwriteAttrs` the sender's OWN identity is stripped (`stripSenderIdentity`), since overwrite only replaces keys the builder emits and any identity key the described object lacks otherwise survived from the EXPORTER onto the object it describes; the stripped set is `attrs.SenderIdentityKeys()` — every fixed identity key the builder can emit, `container.name` included, pinned bidirectionally by test — so a new owner kind or builder emission reaches it automatically. Note it strips `service.name`/`service.namespace`/`service.instance.id` too, where the SELF-describing seam (`Enricher.resolvedWins`, above) deliberately leaves them to the sender: there the resource IS the sender's, here it names an object the sender merely describes, and leaving an exporter's instance on a described object puts every described object's series on the exporter's instance — the collision `attrs.PrefixInstance` exists to prevent one level up. **Concurrency is BOUNDED** (`-ingest-max-in-flight`, `Server.inFlight` semaphore, `defaultMaxInFlight` 32, also fed to `grpc.MaxConcurrentStreams`): the listeners are unauthenticated and every in-flight request holds its body plus the inflated pdata, so an unbounded count is an OOM the process cannot defend against. Over the bound `acquire` refuses WITHOUT waiting (queueing would turn back-pressure into latency the sender cannot see) and the refusal is RETRYABLE so the sender keeps the payload: HTTP `429` + `Retry-After: 1`, gRPC `ResourceExhausted` **with an `errdetails.RetryInfo` detail** — the code alone reads as PERMANENT to conformant senders (OTLP makes it retryable only with RetryInfo, and both the OTel SDK and the Collector drop the batch without it), so a shed that loses the data would be worse than the OOM it prevents. **Memory is bounded SEPARATELY from the count** (`admit.go`, `byteBudget`, `maxBufferBytes` = 4 x the 16 MiB body cap, raised in step when `-ingest-grpc-max-recv-bytes` lifts the per-message gRPC cap past it — the flag is the counterpart of a collector's `max_recv_msg_size`, applies to the trace tier's application ports too, and the tap's reservation is whatever it resolves to): the count bounds PROCESSING and cannot bound BUFFERING, because the HTTP handlers read the whole body BEFORE taking a slot (holding one across a trickled 16 MiB upload let a few senders shed the whole node for a `ReadTimeout` — that is why the acquire moved after the read and must not move back) and grpc-go decodes a message before the interceptor runs (with connections uncapped, `MaxConcurrentStreams` bounds nothing server-wide). So the raw payload bytes get their own global, both-transports budget: an HTTP body is charged as it is READ (`budgetReader`, in `budgetGranule` steps), and the destination is pre-sized by `readAllCapped` from a BOUNDED head (`maxPresizeBytes`) rather than from the declared `Content-Length` — the declaration is the sender's claim, not a fact, and crediting it let four idle sockets declaring 16 MiB each add 64 MiB of heap while sending nothing and held until the handler returns; a gRPC push reserves `MaxRecvMsgSize` in `grpc.InTapHandle` — the only pre-decode hook — released by whichever of THREE comes first, since a leaked reservation would shed the listener for the process' life: the interceptor (decode done, the count takes over), the stream ctx's `context.AfterFunc` (every abort path the peer or the transport drives), and `grpcReserveWindow` (10s) elapsing. **The last is not belt-and-braces**: a peer that opens a stream and then sends NOTHING reaches neither of the other two, so sixteen headers-only streams from one unauthenticated socket pinned the whole budget for the process' life — at zero cost in bytes, shedding gRPC AND HTTP ingest with it. Expiry (`reservation.expire`) releases, cancels the stream, and counts `kubescrape_ingest_reserve_expired_total`, kept apart from `obs.IngestRejected` because the budget had room and nobody was refused. A tap CAN carry the RetryInfo (`writeEarlyAbort` forwards status details), which an earlier comment here denied. **And the raw bytes do not bound what they INFLATE INTO, so there is a THIRD budget** (`decodedBudget`, `decodedBudgetFactor` = 2, i.e. twice the raw one): this file used to claim the COUNT covered that ("the far more expensive resource, inflated pdata"), which a count structurally cannot — a legal 15.99 MiB logs body of 578 000 minimal ResourceLogs is ~40 KiB gzipped, inflates 16x to ~256 MiB of live heap, and the raw budget deliberately admits FOUR full-size bodies, so the shape it is designed to allow is ~1 GiB of heap on a pod the chart limits to 512Mi — an OOM-kill of the node's whole agent bought with ~160 KiB of unauthenticated traffic, repeatable into CrashLoopBackOff. The same 16 MiB carrying a realistic 60k-record batch inflates 1.12x: the hazard is SHAPE. `decodedSize` charges STRUCTURE only (512 B/resource, 256 B/scope, 256 B/record-point-span, measured against pdata) and deliberately NOT the strings a decode copies out, which are bounded transitively (HTTP: the raw body is charged for the same lifetime; gRPC: in-flight count x per-message cap) and would shed honest senders if charged twice. Its stated cost: a SINGLE push whose structure alone estimates past the whole budget can NEVER be admitted (~130k resources or ~500k records) and is answered the same retryable refusal — there is no safe permanent answer, a shed that loses data being worse than the OOM it prevents — with a once-a-minute warn naming the estimate, because "always 429" is otherwise indistinguishable from back-pressure. Both refusals count `obs.IngestRejected`. **A body's SHAPE is refused before the decode** (`depth.go`, `maxNestingDepth` 100, `checkNesting` on the HTTP arm via `BodyReader` and on the gRPC arm via `NestingGuardOption`, which hooks the CODEC because that is the only place ahead of pdata's decoder): the generated decoder recurses without a limit of its own — an `AnyValue` holding an `ArrayValue` calls back into `AnyValue`, and neither side counts — so ~1.6 MiB of legal body inside every cap here peaks at 128 MiB of goroutine stack for ONE decode, several of which fit inside the byte budget and the in-flight count at once, and the OOM-kill moves no counter because nothing survives the decode to move one. The walk is O(len(body)), allocation-free and schema-less (it cannot tell a nested message from a string that parses as one — which only makes it stricter, and the bound is far above where real strings sit); the refusal is PERMANENT (400 / gRPC Internal) since no retry of the same bytes is shallower, and counts `obs.IngestBodyRejected{too_deep}`. 100 WIRE levels is ~31 levels of nested attribute structure (an OTLP log body already sits 5 down, each further map/array level costing three) and is protobuf's own C++ recursion limit, so a deeper payload is already undecodable by a conformant consumer. The tier's INTERNAL receiver builds its own `grpc.Server` and takes `NestingGuardOption(nil)` — the same guard with no counting, since that hop is bearer-authenticated and the counter means "an application push was refused". Attribution WAIT is bounded per push too (`lookupWaitBudgetFactor`: a push's lookups may block at most 4×`-ingest-metadata-wait` in total, charged by measured elapsed time, the remainder proceeding wait-0): `maxLookupsPerRequest` bounds COUNT only, so one push naming thousands of DISTINCT fabricated ids otherwise held its in-flight slot — and, on HTTP, its body-budget charge — for count×wait.
- **Span metrics** (`agent/spanmetrics`, opt-in `-ingest-span-metrics`, on the `-service-graph` TRACE TIER): RED metrics derived from received spans, following the OpenTelemetry spanmetrics conventions — a monotonic `traces.span.metrics.calls` counter, a `traces.span.metrics.size` byte counter, and a `traces.span.metrics.duration` histogram (seconds, with per-bucket trace-id **exemplars**), dimensioned by `service.name`/`span.name`/`span.kind`/`status.code` plus configurable extra span-then-resource attribute keys (`traceMetrics` config section: `namePrefix`/`buckets`/`dimensions`/`maxCardinality`/`exemplars`). Each span is aggregated INDEPENDENTLY, so the cumulative counters sum across shards — but the tap runs on the OWNING shard only (inside `buildOwnerChain`, below the pairing tap and above the sampler), so a span that took the internal re-shard hop is counted ONCE, not once per hop. It plugs in as a `TracesExporter` **tap** (`Generator.Tap`) wrapping the raw trace exporter: enrichment happened at the tier's entry, so the tap sees enriched spans (service.name populated); the tap forwards FIRST and aggregates only on success — a transient failure surfaces retryable all the way back to the application, whose re-push must not double-count. Consume runs on the concurrent receiver goroutines (each RPC owns its payload; the series map is mutex-guarded). The batch is forwarded UNCHANGED. The generator is a **self-contained cumulative aggregator** (`spanSeries` map keyed by the length-prefixed dimension tuple), NOT `metrics.Registry` — exemplars are a histogram-data-point feature the Registry cannot express, and owning the aggregation also gives the size counter and OTLP units a single home. The state machine UNDER it is `internal/agent/cumagg` (see its own bullet), shared with `agent/servicegraph`: `Generator` keeps the names, the dimension set, the three metric shells and the per-span aggregate, and `cumagg.Store[*spanSeries]` keeps the map, the cap, the eviction and the export loop. A **cardinality cap** (`maxCardinality`, default 20000) bounds the data-driven label sets: a new tuple over the cap is dropped and counted (`obs.SpanMetricsDropped`), existing tuples always keep reporting (cumulative). **Stale series are evicted at render** (`staleAfter`, default 15m, `"0"` disables, a NEGATIVE value is now REFUSED rather than clamped to 0 — clamping landed on the disable branch; `obs.SpanMetricsEvicted`) — without eviction the cap is a ONE-WAY LATCH, so one burst of high-cardinality span names permanently blinds RED metrics for every service that starts afterwards, and dead series render into every export forever. A series is evictable only once a DELIVERED export carried its current values (`cumagg.Meta.State` observed→rendered→delivered, marked in the store's `afterDelivered` beside the exemplar reset), so an export interval longer than `staleAfter` — or a failed export — never destroys observations unseen; a re-created series gets a FRESH per-series start timestamp, which is how OTLP spells the cumulative reset. The clock is read ONCE per `Consume` batch (injectable `Generator.now`), never per span. **Zero-alloc warm path**: `observe` builds the map key on a stack buffer and looks up via `map[string(key)]` (Go elides the copy for the read), materializing the dimension slice only when a genuinely new series is admitted — `BenchmarkConsume` is 0 allocs/op (`TestConsumeAllocationBudget` guards it; the benchmark only reports it). Exemplars are one-per-latency-bucket, reset after each DELIVERED export (a failed send keeps them for the retry), and skip spans with no trace id; `exemplars: false` disables them. **`cumagg.MaxLabelBytes` bounds RETAINED BYTES, so a retained value is CUT WITH A COPY** (`cumagg.Retain` in `dims()`; `cumagg.Trunc` stays a bare reslice for the stack key, which the map copies on insert): slicing a Go string keeps the whole original alive, so a 256-byte label was pinning a sender's 4 MiB `span.name` for `staleAfter` — 33 MB measured at 8 series — which is exactly the bound the constant's comment promises. Cloning only on the truncating branch keeps the warm path at 0 allocs. `spanSize` is a cheap allocation-free byte estimate (name + ids + attributes + events + links), not the exact proto size. Exported on `-ingest-span-metrics-interval` (default 1m) via the shared metrics exporter, under the tier's own resource identity (`service.name=kubescrape-agent`+node, `agentSelfResource`) — the described service is a data-point dimension (`service_name` a label, not the metric's job). Naming follows the OTel Collector connector, NOT Grafana Tempo's metrics-generator (`traces_spanmetrics_*`/`SPAN_KIND_SERVER`); the values differ from Tempo in metric name and kind/status casing.
- **The trace tier / service graph** (`agent/servicegraph`, opt-in `-service-graph`, and the ONE pipeline that needs its own WORKLOAD): the workload that RECEIVES the cluster's OTLP traces and, from them, emits Grafana-Tempo-wire-compatible EDGE metrics — `traces_service_graph_request_total`, `_request_failed_total` (emitted at zero too, so the error ratio is defined before the first failure — Tempo creates it lazily) and the SEPARATE histograms `_request_server_seconds`/`_request_client_seconds` (two unsynchronised clocks measure them; their difference is the operator's to take), labels `client`/`server`/`connection_type` (`""`|`messaging_system`|`database`|`virtual_node`)/`virtual_node` plus configured dimensions as `client_<dim>`/`server_<dim>`. Both histograms carry per-latency-bucket **exemplars** (`serviceGraph.exemplars`, default true), following spanmetrics' rules — one per bucket, latest wins, cleared only after a DELIVERED export (a failed send keeps them for the retry), skipped for a span with no trace id. The trace id is the same on both halves BY CONSTRUCTION (it is half the pairing key, `edgeKey`); the SPAN id is each half's own (`Edge.ClientSpanID`/`ServerSpanID` — for the server half its own id, NOT the parent id it paired on), so each side's exemplar points at the span that measured that side. The exemplar timestamp is the shard's clock at pairing time (Tempo's behaviour). `Edge.Dimensions` is an ORDERED `[]EdgeDimension` whose order is canonical by construction (the client half's dimensions in the configured order, then the server half's — `joinDims`), because the metric layer keys a series on that sequence: an arrival-ordered one would give one edge two keys and render a byte-identical label set twice in one payload. It is also BORROWED — it aliases the pairing store's recycled buffers, so the sink runs before `retire` and a sink that retains an Edge must copy — which is what makes a dimensioned edge cost ZERO allocations (`BenchmarkConsumePairWithDimensions`/`TestConsumeWithDimensionsIsAllocationFree`). Its VALUES are cut by `cumagg.Retain` wherever something keeps them (the processor, whose half-edges live a whole `Wait`, and `edgeLabels`, whose labels live as long as the series) because truncating a Go string is a reslice that pins the whole original — a 256-byte label holding a sender's 4 MiB `peer.service`; `cumagg.Trunc` stays a bare reslice only for `Record`'s stack key, which the map copies on insert. Same defect and same fix as `agent/spanmetrics` — and now literally the same function: the two had it separately, under two names, and each had the bug fixed on its own. The names are Tempo's VERBATIM and spelled so BOTH the suffixes-on and suffixes-off OTLP→Prometheus translations reproduce them (the deliberate exception to the repo's OTel-dotted naming): Grafana's Service Graph view queries those exact strings. **Pairing cannot happen in the DaemonSet**: a request's two halves are emitted by two pods on two different NODES, so a per-node aggregator holds half of every edge by construction (the opposite of spanmetrics, where every span aggregates INDEPENDENTLY and the cumulative counters sum). **TWO LISTENERS, and the port decides the treatment** (`cmd/kubescrape-agent/servicegraph.go`): the APPLICATION ports (`-service-graph-ingest-grpc`/`-http`, `:4317`/`:4318`, an `otlpingest.Server` with `Exporter: nil` so it serves traces only) are UNAUTHENTICATED — every instrumented pod is a sender and a per-app credential is not a bargain most fleets can make — and the INTERNAL port (`-service-graph-listen=:4319`, `sgReceiver`) is bearer-authenticated because what arrives there is TERMINAL: already enriched, already routed. The RECEIVER is its own (auth, no in-flight semaphore, traces-only registration) but it borrows the two shared wire guards rather than re-implementing them: its gRPC server takes `otlpingest.NestingGuardOption(nil)` — the codec-level wire-shape check every other OTLP gRPC listener gets from `otlpingest.Server`, `nil` because this hop is bearer-authenticated and `obs.IngestBodyRejected` means "an APPLICATION push was refused" — and its HTTP body reading is `otlpingest.BodyReader` with a 4 MiB cap — it used to be a copy, and the fix that makes an over-cap GZIP answer 413 rather than 400 "malformed" landed only in the original, on the one hop whose sender is another kubescrape and reads 400 as PERMANENT. Loop-freedom is therefore STRUCTURAL, not a check that could be wrong (one directed edge, ingest port → internal port, and no edge out of the internal port; the internal path holds no Enricher and no Resharder at all) — a port cannot be forged by a payload the way an attribute can. `ForwardedMarker` (`kubescrape.service_graph.forwarded`) is the SECOND line, for the one easy misconfiguration (an internal hop addressed to `:4317`): the application path REFUSES a marked payload with `codes.InvalidArgument` (permanent, so the sender does not retry it forever) and counts `obs.ServiceGraphReshardStat.LoopsBlocked`; the owner STRIPS it on arrival (`StripForwarded`) so kubescrape plumbing never reaches the collector. **Enrichment happens at FIRST RECEIPT, never on the owner** — the connection's source address names the sender exactly once, on the hop the sender opened, and on the internal hop the peer is a SIBLING SHARD; `pipelines.peerIsOurOwnWorkload` (`sameWorkload`/`topOwner` over `selfmeta`'s pod) vetoes a peer-IP attribution resolving to this tier's own workload, counted `obs.Ingested{peer_ip_rejected}`, because an application's traces labelled with a kubescrape pod render perfectly and are wrong on every span. **`Resharder`** (`reshard.go`) splits a push by ring owner (`ring.go`, Tempo's FNV-1 32-bit `TokenFor`, tokens derived deterministically from the shard NAME rather than gossip-registered, so every shard computes the identical ring from the identical config), sends each remote share and returns the LOCAL one; `Self` (`-service-graph-shard-name`, default `$POD_NAME`) is what keeps 1/N of the traffic off the wire, and `singleOwner` passes a one-owner payload through with NO copy at all (a one-shard tier costs nothing). Trace-id-less spans stay LOCAL (unhashable, and every zero id shares one token) and count `SpansUnkeyed`. **The hop is SYNCHRONOUS and FAILABLE** — the entry shard holds the ONLY copy, so a dropped hop is a lost SPAN, not a lost edge: a failed send fails the application's push (`sgForwardStatus` maps the owner chain's error to a gRPC status / HTTP code the sender classifies correctly) and the sender's retry is the recovery. No queue, no `-buffer-dir`, `RetryAttempts: 1`; the bound on concurrent hops is the entry listener's in-flight semaphore. A part-way fan-out is at-least-once (the split is a pure function of the trace id, so the retry re-splits identically), which is safe precisely because both taps count only after a SUCCESSFUL export. **The owner chain** (`buildOwnerChain`) is `sgPairTap → spanmetrics.Tap → tracesample → collector`, forward-first-act-on-success at every layer, with the sampler at the BOTTOM so the graph and the RED metrics see 100% of spans (an edge is one request and the graph counts requests; a sampled chain would report 10% of the traffic as if that were the traffic). **Deployment surface** (`charts/kubescrape/templates/servicegraph.yaml` + `deploy/servicegraph.yaml`, values `serviceGraph.*`, off by default): a **StatefulSet**, never a Deployment — the ring addresses shards by stable ordinal DNS (`<sts>-<i>.<svc>.<ns>.svc`) behind a **headless** Service (`clusterIP: None`, `publishNotReadyAddresses: true`) for the internal hop, PLUS a ClusterIP `<release>-traces` Service that is where applications point their SDKs (round-robin is fine and wanted there; the internal hop is what undoes it). No volumeClaimTemplate (pairing state is in-memory by design — the StatefulSet buys NAMES, not storage), no ServiceAccount and no RBAC (the tier reads no Kubernetes API; it uses the metadata service over HTTP like any agent), `podManagementPolicy: Parallel`, every per-node pipeline off INCLUDING `-ingest` (that flag is the DaemonSet's logs-and-metrics receiver). `serviceGraph.replicas` renders BOTH the StatefulSet size and `-service-graph-shards` — the count is part of the ring's DEFINITION, so scaling is a `helm upgrade`, never a `kubectl scale`. `serviceGraph.ingest.allowFrom` is the NetworkPolicy `from` for the trace ports; EMPTY MEANS ANY POD MAY PUSH TRACES with no credential, which the template says in as many words. **Rendering does not hold the series lock**: `Registry.snapshot` copies each series' values out under the store's mutex — in `snapChunk`-sized chunks, walking a pointer slice taken in one cheap pass because a map cannot be walked across lock releases — and the pdata payload is built from that copy with the lock free. `Record` is called by the pairing store from INSIDE its own mutex (`upsert → emit → sink.Record`), so every millisecond the series lock is held is a millisecond in which no goroutine can Consume a span: at the 20k cardinality cap the build is ~50 ms and a probe measured a 46.7 ms `Record` stall inside a 46.7 ms render, now 1.6 ms (`TestRenderDoesNotStallRecord`). The scratch (`snap`/`snapPtrs`) is reused across renders under `renderMu`, taken in `renderEdges` (lock order: `renderMu` before the store's mutex) and sized outside the lock; the snapshot keeps only the SET exemplars, since copying every bucket slot was 34 MB of memcpy under the mutex. The delivery-gated state machine is `cumagg`'s — `EvictLocked` and `MarkRenderedLocked` still happen under the store's mutex, and the store's `afterDelivered` still promotes and clears the ORIGINALS. Tuning bounds all trade completeness for memory and all count when they bind (`obs.ServiceGraphExpired`/`ServiceGraphStoreFull`/`ServiceGraphDropped`/`ServiceGraphEvicted`) — a missing edge looks exactly like a call that never happened. **Honest downsides of this topology**: the tier is a hard cluster-wide dependency for traces (no per-node fallback), every span crosses the network twice at full fidelity, and one noisy service shares the shards with everyone else.
- **One cumulative-aggregator state machine** (`internal/agent/cumagg`): `agent/spanmetrics` and `agent/servicegraph` are two aggregators of the same SHAPE — a map of cumulative series keyed by a length-prefixed label tuple, admitted under a cardinality cap, evicted when they go unobserved, exported whole on an interval — and they were written twice and DRIFTED TWICE. `cumagg.Store[S]` now owns the map, the mutex, admission (`AdmitLocked`, cap refusal counted through the caller's OWN counter), the observed→rendered→delivered gate (`cumagg.Meta`, embedded in each aggregate), stale eviction, the render/send/mark-delivered order, `ClampStart` (the stamp-time bound both renders apply so a series admitted between `Export`'s single clock read and the render's first lock hold cannot emit `StartTimestamp > Timestamp` on its first export — `Meta.Start` is untouched, so the true start renders from the next one), the exemplar reset on DELIVERY, and `Run`'s loop plus its final DETACHED export; `Options.Render` is the one callback, and it writes the caller's own shells and label sets. (2) the built-in-label collision guard existed twice; `cumagg.Builtins` owns the rule (a colliding dimension is DROPPED: the attributes are one `pcommon.Map`, so a collision would blank the real label and two series would render byte-identical label sets — a duplicate point in one payload) and both packages call it where their label NAMES become known, which is `Filter` at construction for spanmetrics' configured list and `Has` per Edge for servicegraph's, whose names only exist at record time and whose hand-built Edges would walk past a constructor check. **What deliberately did NOT move**: servicegraph's Tempo-verbatim metric NAMES and the naming essay above them, its two-histograms-per-series shape, the two separate `obs` counter pairs (an operator must see WHICH cap bound), spanmetrics' dimension set and size counter, and the two RENDER SCRATCHES (each aggregator keeps its own `snap`/`snapPtrs` reuse buffers) — but the LOCK STRATEGY is now shared: BOTH snapshot the series' values under the store mutex in chunks and build pdata lock-free (servicegraph `TestRenderDoesNotStallRecord`, spanmetrics `TestRenderDoesNotStallConsume`). spanmetrics used to build under one hold, and that was a receive-path stall, not just a slow export: its tap calls `Consume` with the ingest RPC waiting on it, and `Consume` takes the same series lock the render did, so at the cardinality cap every trace push on the tier blocked for the whole ~89 ms build once per interval — the same defect servicegraph had already chunked away. Warm paths stay 0 allocs/op, ASSERTED by `spanmetrics.TestConsumeAllocationBudget` and `servicegraph.TestRecordIsAllocationFree`/`TestConsumeUnpairedIsAllocationFree` beside the reporting benchmarks (`BenchmarkConsume`, `BenchmarkConsumeBatch`, `BenchmarkRecord`): the store's mutex is exported as `Lock`/`Unlock` precisely so the per-span fold stays straight-line code — a per-call closure would be an allocation per request.

Known asymmetry, documented at both lists: `DefaultPeerAttributes` stays Tempo-verbatim (`peer.service`/`db.name`/`db.system`), so a client naming its database ONLY via the 1.30 keys classifies as `database` but mints no virtual node unless `serviceGraph.virtualNodePeerAttributes` adds them. Incremental expiry's budget SCALES WITH THE BATCH's span count — total `min(SpanCount()+sweepFloorPerBatch, maxSweepBudgetPerBatch)` (16384), SPENT in passes of at most `maxSweepPerBatch` (1024) per lock hold and stopping at the first short pass, since `expire` returning fewer than asked means nothing more is due at `now`: a fixed per-Consume budget is a per-BATCH rate, and the batch size is the sender's choice — 1000 half-edges/s drained fine at 20-span pushes and dropped 54% at 200-span ones. `maxSweepPerBatch` is the PER-LOCK-HOLD ceiling and NOT the total, which this sentence had backwards for as long as the code did: truncating the batch-scaled budget to 1024 made the scaling a lie, so a batch carrying more than 1024 unpairable half-edges expired fewer than it added, occupancy climbed past the honest rate x wait working set, pinned at `MaxItems`, and the store began refusing arriving spans. `TestConsumeSweepsItsWholeBatchBudget` (3072 half-edges drained by one batch) is what fails if the total cap is "restored". A CLIENT/PRODUCER span with a ZERO span id is refused as unkeyable: its key would be (trace, zero), exactly where every ROOT SERVER span of that trace keys, so one malformed SDK invented edges between services that never called each other. `serviceGraphShards.port` defaults to `DefaultShardPort` = 4319, pinned against `-service-graph-listen` by a test in `cmd/kubescrape-agent` (it was 4317 — the agents' OWN ingest port, which the shard pods do not serve); with `protocol: http` the derived URL takes `https://` when TLS is asked for in ANY form (`caFile`, `insecureSkipVerify`, an explicit `insecure: false`) — otlpexport ignores `Insecure` for HTTP, so there the scheme IS the TLS decision and a skip-verify-only config used to go plaintext with the bearer token in the clear. `validateConfig` refuses `-service-graph` with BOTH listen flags empty (the runtime refusal existed; `-check-config` passed a config that CrashLooped the StatefulSet). On the CLIENT side of a call (CLIENT and PRODUCER kinds) any `databaseAttrs` attribute overwrites the kind-derived `messaging_system` — the db attributes are authoritative over the span kind, Tempo's rule, and the old `ConnectionUnknown` gate made the answer depend on WHICH attribute spelled database and whether `peer.service` happened to sit beside it (three producer spellings, two answers); a server-side half never takes db classification, since a database emits no spans and a server span carrying `db.*` is a service that talks TO one. A resource with NO `service.name` is skipped for the graph at the resource level (nothing can name its node; Tempo skips them too), counted `kubescrape_service_graph_unnamed_spans_total` — the spans still forward, and spanmetrics still aggregates them under an empty `service_name` LABEL, deliberately different semantics. **Honest limitation, documented as such**: an edge needs BOTH halves, so an uninstrumented callee appears only as a VIRTUAL NODE named from the client span's `peer.service`/`db.name`/`db.system` (and, symmetrically, an expired SERVER half carrying a peer attribute names its uninstrumented CALLER as `virtual_node="client"` — the both-sides scan Tempo does not do), and a party naming none of those yields no edge at all. Two further Tempo divergences, deliberate and listed here so they are not rediscovered as bugs: there is no literal `"user"` virtual client for an expired ROOT server half with no peer attribute (Tempo synthesizes one; kubescrape counts it unpaired rather than minting a node the spans never named), and dimension values resolve span-attribute-first with the resource as fallback (Tempo reads the resource first) — consistent with `spanmetrics`, and visible only when a dimension key exists on both with different values.
- **Trace sampling** (`agent/tracesample`, config `traceSampling` section, on the `-service-graph` trace tier): consistent per-trace-ID probabilistic sampling (`tracehash.Keep` — rapidhash of the trace id vs threshold, deterministic across retries AND across shards, so whole traces are kept; the algorithm is argued in the `internal/agent/tracehash` bullet and nowhere else, because WHICH traces are kept is a property of the hash FUNCTION and naming a stale one here sends anyone reproducing the sampled set to a different answer — this said "xxhash" for as long as the migration to rapidhash had already re-rolled the set) with keep-errors (default true) / keep-slower-than guard rails and a spans/second token-bucket cap (applied last, guard-rail keeps included). Wired near the bottom of `buildOwnerChain`, below both the spanmetrics tap and the pairing tap (and ABOVE tail sampling), so RED metrics and the service graph see 100% of spans while only the sampled subset ships; a payload sampled to nothing is acked without a send. Drops count `obs.TraceSpansDropped{reason=probability|rate}`.
- **Config errors WRAP their cause** (`tailsample.errPolicy`): the helper prepends its `where:` prefix to the FORMAT STRING (`fmt.Errorf("%s: "+format, append([]any{where}, args...)...)`) rather than rendering the args with an inner `Sprintf`. The inner form flattened every argument to text before the outer `Errorf` saw it, so `%w` was structurally impossible and the four call sites carrying a real error (a `regexp.Compile` syntax error, two `config.Duration` parses, a status-code parse) had to spell it `%v` — no linter could see it, because the `%v` was on a local helper. `TestCompileErrorsWrapTheirCause` pins `errors.As` reaching `*regexp/syntax.Error` and the ParseDuration leaf through the compiler. A helper that takes a format string and does not forward it verbatim is the shape to watch for.

- **Tail sampling** (`agent/tailsample` = the policy ENGINE, `agent/tailbuffer` = the BUFFERING/DECISION layer, config `tailSampling` section, opt-in on the `-service-graph` tier): whole-TRACE decisions. `tailbuffer.Buffer` holds a trace's spans keyed by trace id, calls `Evaluator.Decide` once `decisionWait` (5s) has elapsed since the trace was FIRST seen, and exports or discards the trace whole; the two halves meet ONLY at `Decide`, which is why the engine holds no traces and imports no `obs`. The section EMBEDS `tailsample.Config` (so `policies:` stays flat) and every duration is a STRING (`decisionWait`/`decisionCacheTTL`) for the sigs.k8s.io/yaml reason. **THE DELIVERY CONTRACT IS THE THING TO KNOW, and it is this repo's ONE departure from ack-gated at-least-once**: a pushed span is ACKED BEFORE its trace is decided — holding the RPC open for the window would pin an `-ingest-max-in-flight` slot for 5s and stall every sender in the cluster — so BUFFERED-BUT-UNDECIDED SPANS ARE LOST IF THE SHARD IS HARD-KILLED. No sender still holds them (a DECIDED keep is a different case — see below). Bounded three ways: by TIME (`decisionWait`), by SIZE (`maxSpans`), and by SHUTDOWN — `run()` calls `Buffer.Flush` after the receivers have been ASKED to stop (the join budget can expire while a trickled body is still in a handler) and before the exporter closes, and Flush LATCHES the buffer: a straggler push completing afterwards is decided on arrival on the spans it carries, its keeps ride its own UNOWNED ack (the sender still holds them) and the buffer never re-fills for a flush nobody will run again — so a SIGTERM/rolling update loses nothing and only a SIGKILL/OOM/node failure does; and it is VISIBLE before it is spent (`kubescrape_tail_sampling_buffered_spans`/`_buffered_traces` are exactly what a hard kill would lose). **`maxSpans` is sized against REAL memory** (`memory.go`): the rule is `maxSpans x 1 KiB` must fit a QUARTER of the container's cgroup limit (or MemTotal when uncapped); `New` LOWERS an unset default that does not fit, warns above the share, and REFUSES an explicit ceiling whose spans alone need the whole limit. The loss mode is self-correlated — the likeliest hard kill is the OOM this buffer causes — so early decisions are the relief valve and the OOM is the failure. Kept out of `Config.Validate`, which stays shape-only for `-check-config`. **Bounds decide EARLY, never drop blind** (`enforce`): `maxSpansPerTrace` decides that trace on the spans present (its remainder then follows the verdict through the cache), `maxTraces` and `maxSpans` decide the OLDEST — the one closest to its natural decision, and picking the LARGEST would need a heap keyed by a count that changes per span and would systematically punish deep traces. The engine treats a partial trace as a LOWER BOUND (a slow trace can be missed, a fast one is never invented), which is what makes an early decision degrade gracefully where an eviction does not; each is counted `obs.TailSampleEarly{reason=spans_per_trace|max_traces|max_spans|shutdown}`. **The decision CACHE** (`cache.go`, bounded by entries AND TTL) is what a late span is measured against: forwarded immediately on a keep, dropped on a drop (`obs.TailSampleLate{outcome}`, BOTH outcomes tallied only when the carrying push ACKS — a NACKed push is retransmitted whole, and per-attempt counting inflated the drop side); the entry has TWO lifetimes — the VERDICT expires at `decisionCacheTTL` (a later straggler starts a FRESH window) while the record that the trace was DECIDED AT ALL survives to the SIZE cap, and `decide` passes it as `tailsample.Trace.Charged` — a PER-BUCKET mask (`tailsample.ChargedMask`, one bit per rate bucket in compile order), so the re-decision PEEKS exactly the `rateLimiting`/`composite` buckets this trace paid (`bucket.peek`) and still CHARGES one it never did (a single bit let a composite's refused share be peeked free on re-decision). Eviction under the size cap is the only remaining double-charge, and `obs.TailSampleCacheEvicted` counts it — only for a still-LIVE verdict, since reclaiming an expired tombstone is the cache working; the map now sits at its cap rather than also draining by age. One mutex guards the map, the arrival FIFO, the tallies, the cache and the two receive-path grouping scratch maps; NO export ever runs under it (a slow collector would serialise every sender). The arrival FIFO is deadline-ordered by construction (one wait for all), so "oldest" is O(1) and removal from the middle is a `gone` flag skipped at the front — with `compact()`, because an ever-growing slice is the same bug as an unbounded map. **Composition** (`buildOwnerChain`, bottom-up): `sgPairTap → spanmetrics.Tap → tracesample → tailbuffer → collector`. Tail sampling is LAST because the graph and the RED metrics count REQUESTS; and it NESTS with the head sampler rather than compounding — both hash the trace id UNSALTED against the same threshold arithmetic, so a 50% tail policy keeps exactly what `probability: 0.5` passed (cross-package tests on both sides pin it). Caveat, now SAID OUT LOUD (`configWarnings` in `cmd/kubescrape-agent/config.go`, emitted by `-check-config` and every start): `traceSampling`'s guard rails are per SPAN, so `keepErrors`/`keepSlowerThan` deliver trace FRAGMENTS to a layer that judges whole traces and can export a trace that never existed. WARNED rather than refused because `keepErrors` DEFAULTS to true — refusing would reject `probability` + `tailSampling`, the most natural composition, and make the same effective config legal or illegal depending on whether the default was spelled out. `probability` (nests) and `maxSpansPerSecond` (overload valve) are the supported half. **A DECIDED keep is DURABLE with `-buffer-dir`**: `drain` marks its payload `otlpexport.Own(ctx)` (and `ExportTraces` marks a push whose `mine > 0` carries early-decided spans), so `Buffered` SPOOLS it instead of passing it through — a collector outage becomes a backlog, and `{outcome=lost}` then moves only if the spool itself refuses. Without a spool it is retried (`sendAttempts`, ctx-aware, permanent errors not retried) and then dropped + counted `obs.TailSampleSpans{outcome=lost}`. Spooling at BUFFER time instead was rejected: an fsync in the ack path is what the ack-first design exists to avoid, it writes 100% of spans to protect the ~1-10% kept, and the queue's in-order cursor could not retire a payload until every trace in it was decided (a restart would re-buffer already-exported traces). a failed forward of already-decided spans instead FAILS THE PUSH, since those are in the payload the sender still holds (its retry re-buffers the still-assembling spans of that payload — at-least-once, the same trade the re-shard hop makes). The receive path is allocation-disciplined (`bench_test.go`): the decided-drop path is 0 allocs/op (asserted by `TestReceiveLateDropAllocationBudget` — the assertion used to sit INSIDE `BenchmarkReceiveLateDrop`, where `go test` never reached it), a buffered span costs the pdata copy and nothing else — no per-call maps, no per-span slices, counters and policy label values resolved at `New` from `Evaluator.Names()` so a policy that never fired reads as 0 rather than as an absent series.
- Tailer tests are timing-based: use `startTailer` (guarantees file creation happens after the initial scan — files present at startup are skipped to their end) and `tl.retryBackoff` to keep retry tests fast. A multi-line group that must survive across sweeps (e.g. straddling a rotation) needs **current** CRI timestamps on its lines (`timeNowCRI()`), not the usual hard-coded `2026-07-05`: the multiline stage's age-out (`FlushBefore`) runs against the real clock, so stale line timestamps flush the group before the continuation arrives.

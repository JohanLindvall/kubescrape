# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
make build              # build to bin/kubescrape
make test               # go test ./...
go test ./internal/store/ -run TestWaitIsPerContainer -v   # single test
make vet fmt tidy
make lint               # golangci-lint v2 (auto-installed to GOPATH/bin; config .golangci.yml)
make image              # docker build; service is CGO_ENABLED=0 static, agent is CGO_ENABLED=1 (libsystemd/journald) on distroless/base; release binaries strip -s -w (~30% smaller; panic traces unaffected — the runtime reads pclntab). `make build` stays unstripped for delve/gdb.
```

`CGO_ENABLED=1 go test -race ./...` works (gcc is available); run it for concurrency-touching changes (store, metaclient cache, otlpingest). The concurrency tests in `internal/store` and `TestEnricherConcurrent` are the targeted exercises.

### End-to-end verification (kind)

Changes to informer wiring, the store, or the HTTP API should be verified against a real cluster, not just unit tests:

```sh
make cluster-up         # 3-node kind cluster; downloads kind/kubectl into hack/bin; deploys hack/test-workloads.yaml
go run ./cmd/kubescrape # uses the kind kubeconfig context
make image && hack/bin/kind load docker-image ghcr.io/johanlindvall/kubescrape:latest --name kubescrape
kubectl apply -f deploy/kubernetes.yaml   # in-cluster deployment (namespace: monitoring)
make cluster-down
```

`hack/test-workloads.yaml` intentionally exercises every code path: a pod-annotated Deployment (ReplicaSet→Deployment chain, pod-source targets), a non-annotated Deployment behind an annotated Service with a named `targetPort` (service-source targets), a CronJob (Job→CronJob chain), plus a StatefulSet and a DaemonSet (direct-owner chains).

## Public packages (`pkg/`)

`pkg/promparse` (the exposition parser — `internal/agent/promscrape` aliases its types in `promparse.go`), `pkg/kubemeta`, `pkg/metaclient`, `pkg/logattrs`, `pkg/otlpsplit` (size-bounded OTLP payload splitting) and `pkg/cgroupid` (cgroup path → pod/container identity) are importable by other modules. **They must never import `internal/`** (Go would allow it inside this module but break every external consumer) — the boundary is worth re-checking when adding code there. `metaclient` deliberately has no metrics dependency: the agent installs `Client.Observe` to bump `obs.MetadataRequests`.

## Architecture

Two binaries: `cmd/kubescrape` (metadata service) and `cmd/kubescrape-agent` (per-node DaemonSet: log tailer + Prometheus scraper exporting OTLP). Both live in one image; the DaemonSet overrides `command: ["/kubescrape-agent"]`.

### Metadata service

`cmd/kubescrape` serves Kubernetes pod/container metadata over HTTP. Everything is driven by one initial LIST + WATCH per resource (client-go informers); there is **no per-request API-server traffic**.

Data flow:

- **Pod informer** (full objects) → `internal/store.Store`: pods keyed by UID, with two derived indexes — normalized container-ID → entry, and nodeName → pods. `managedFields` are stripped by an informer transform before caching.
- **Service informer** (full objects) → `internal/services.Index`: selector-based matching of Services to pods, for service-annotation scrape discovery.
- **Metadata-only informers** (`PartialObjectMetadata`, cheap) for ReplicaSets, Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, Namespaces, Nodes → `internal/owners.Resolver`. StatefulSets and DaemonSets own their pods DIRECTLY (no intermediate object), so they are cached for their labels/annotations, not for a chain to follow. Owner chains and namespace metadata are resolved **lazily at request time** from these caches, never stored on the pod record. Adding a new owner kind means extending `owners.AllGVRs` + `kindGVR` and the ClusterRole in `deploy/kubernetes.yaml`. **Readiness gates on the HANDLER REGISTRATIONS' `HasSynced`, never the informer's** (`registerCoreInformers` returns `podReg.HasSynced`/`svcReg.HasSynced`): the informer's flips when its DeltaFIFO drains, which says nothing about whether OUR handlers have run, and the store and service index are filled from inside those handlers — so gating on the informer let `/readyz` report 200 while the store was still filling and an agent's first poll got a half-built target list. Owner informers are the exception and legitimately use the informer's, since their lister reads the informer's own indexer. The ServiceMonitor/PodMonitor informers are BOTH gated (`startServiceMonitors` returns a combined func); the PodMonitor one was created and started but never awaited, so a missing `podmonitors` RBAC rule 403-looped forever behind a green `/readyz`. A discovery error is now FATAL rather than read as "the CRD is absent" (`serviceMonitorCRDPresent` returns `(bool, error)`): one 503 from a rolling API server used to disable an explicitly-requested `-servicemonitors` for the process lifetime. `-monitor-namespaces` restricts WHICH namespaces' monitors are honoured (empty = all, the historical default): a monitor is an instruction to every agent to issue a GET, and without an admin-owned gate anyone who can create a ServiceMonitor in their own namespace can point `selector: {}` + `namespaceSelector.any: true` at an arbitrary path cluster-wide. The gate applies at INDEXING time so a refused monitor never widens `AuthSecretRefs`.
- **ServiceMonitor CRDs** (opt-in `-servicemonitors`, dynamic informer over unstructured) → `internal/servicemonitors.Index`. A discovery pre-check disables the feature gracefully when the CRD group is absent. Targets resolve monitor → Services (label selector over `services.All(m.ServiceNamespaces())`) → pods (the existing service selector matching), so scraping stays node-local; `scrape.MonitorTargets` handles endpoint `port` (service-port name) / `targetPort` (pod port) / `path` / `scheme` and stamps `Source: "servicemonitor"` + `Monitor: "ns/name"`; an endpoint naming NEITHER port nor targetPort resolves to nothing (an empty `port` must not match a Service's unnamed port by `""==""` and fabricate a phantom target, as prometheus-operator emits no config for it). **PodMonitors** select PODS directly (same `-servicemonitors` gate; watched when the CRD is served): `scrape.PodMonitorTargets` resolves endpoint `port` (container port NAME) / `targetPort` (number or name), `Source: "podmonitor"`. **Endpoint auth/TLS/relabelings** interpreted: `basicAuth` (username/password secret refs), `authorization` (type + credentials), `tlsConfig` `ca`/`cert`/`keySecret` (SECRET-backed only — the configMap arm is reported as ignored, since the agent reads secret keys through one channel) and `serverName`, plus the keep/drop relabel subset: `tlsConfig.insecureSkipVerify` → per-target skip-verify client; every credential rides as a `"ns/name/key"` ref (namespaced with the MONITOR's namespace, so a monitor can only name secrets in its own namespace — that is what bounds `AuthSecretRefs`, the allowlist keeping `-scrape-auth-secrets` from being a general secret-read API), resolved by agents via `GET /v1/scrape-auth/...`; the scraper builds a per-target `http.Client` from the resolved CA/cert/serverName (`targetauth.go`, cached by the resolved MATERIAL so targets sharing a CA share a connection pool and a rotated secret yields a new client, bounded by `maxTLSClients`) — served ONLY when the service runs `-scrape-auth-secrets` (needs secrets get RBAC; 1-min caches on both sides, responses no-store). `/v1/scrape-auth` is the ONE AUTHENTICATED route (`internal/server/auth.go`): callers present the shared `-scrape-auth-token-file` token as `Authorization: Bearer <token>`, compared with `subtle.ConstantTimeCompare` (every candidate compared, no early exit), checked BEFORE the AuthSecretRefs allowlist (so an anonymous caller cannot probe 403-vs-404 either), and `-scrape-auth-secrets` without a token file FAILS STARTUP (`server.Config.Validate` + `loadScrapeAuthToken`); the token file is RE-READ per minute and a rotated token keeps its predecessor accepted for a 5-minute grace (`rotatingToken` in the service main + `server.Config.ScrapeAuthTokens`), so rotation never needs a restart or lockstep flip with the agents' own per-minute re-read — the service holds cluster-wide `secrets: get`, so a forgotten flag must not leave a read-any-referenced-secret endpoint open to every pod. The other `/v1` routes stay open by design (agents poll them; no secret material); `metricRelabelings` keep/drop rules (sourceLabels joined by ';', anchored regex, `__name__` = name) ship on the target and are applied per sample by the agent (`relabel.go`, compiled chains cached by fingerprint; a bad regex FAILS the scrape rather than exporting what the user asked to drop). **Per-target cadence IS interpreted**: an endpoint's `interval`/`scrapeTimeout` ride on `kubemeta.ScrapeTarget` and the scraper schedules that target on its own period (`Scraper.due`/`targetIntervals`, ticker sized to the finest requested cadence). EVERY target is scheduled (defaulting to `-scrape-interval`) and only an EXPLICIT interval may speed the loop's tick up — scheduling just the explicit ones made one `interval: 10s` monitor re-clock every other target AND both kubelet scrapes to 10s; jitter between the ticker and a due time is absorbed by slack in the due check; an unparseable value warns once and falls back rather than dropping the target, and a timeout is clamped to its own interval. Remaining uninterpreted endpoint fields (`basicAuth`, `authorization`, `oauth2`, `proxyUrl`, `params`, `honorLabels`, `relabelings`, non-keep/drop `metricRelabelings`, `tlsConfig.ca/cert/keySecret/serverName`) are no longer SILENT: they are collected into `Endpoint.Ignored`, and the metadata service logs them once per monitor upsert and counts `obs.MonitorFieldsIgnored{kind}` — a documented subset is fine, a partially-applied CR with no signal is not.
- `internal/server` composes the above per request; `internal/scrape` is pure functions deriving targets from `prometheus.io/*` annotations and ServiceMonitor endpoints; `pkg/kubemeta` holds the JSON model and the corev1.Pod → model conversion (`kubeconvert.FromPod`). Annotations pass through `kubemeta.FilterAnnotations`, which drops `kubectl.kubernetes.io/last-applied-configuration` from pods, owners and namespaces alike: the metadata routes are unauthenticated by design and that annotation is a verbatim copy of the whole applied object, so anything a user inlined into a spec was served to any caller that could reach the port — and stamped onto downstream telemetry. Pods are also resolvable by UID via `GET /v1/pod-uids/{uid}` (`store.GetPodByUID`, tombstone-aware) and by pod IP via `GET /v1/pod-ips/{ip}` (`store.GetPodByIP`, deliberately NOT tombstone-aware — IPs recycle; hostNetwork and Succeeded/Failed pods excluded, a finished pod's retained status.podIP must never shadow the live owner; a TERMINATING pod — `record.terminating`, set from `p.DeletionTimestamp` — yields its IP claim to a live incumbent, since a drained pod keeps phase Running and still reports its now-recycled PodIP, while every live pod claims (last-write-wins), INCLUDING a late-scheduled older pod legitimately taking a freed IP. Creation time was the wrong signal — a pod's age says nothing about who currently holds the address) — the agent's OTLP-ingest enricher uses these. `GET /v1/self` is the pod-IP lookup applied to the CALLER's own connection (`server.peerIP` over `r.RemoteAddr`, zone-stripped; a header is never consulted — `X-Forwarded-For` is caller-controlled and this route hands out whatever pod owns the address it is given), cached PRIVATE (`Cache-Control: private, max-age=<-metadata-cache-ttl>` + ETag, `server.cachePolicy`/`writeCached`): the response names its CALLER, so a per-client cache — metaclient, one per process, always asking about the same pod — may hold and revalidate it while a shared cache must not store it at all, which is what makes re-reading it for changed pod/namespace labels a conditional GET (304) rather than a full document; it exists so a process can learn its own pod without a downward-API env var in every deployment that runs the binary (the agent's `-self-attributes`).
- **Self-metrics are OTLP-pushed, not scraped**: `internal/obs` defines every internal metric on `metrics.Registry` (`internal/metrics/registry.go` — a prometheus-shaped API over the same `series` storage; no expiry/cardinality caps, `GaugeFunc` evaluated at export; `WithLabelValues` caches typed wrappers per label-value key, so hot-path counter bumps are zero-alloc). Both binaries run `obs.Registry.Run` on `-self-metrics-interval` (default 1m, 0 disables) with their own resource identity (agent: `service.name=kubescrape-agent`+node; service: `service.name=kubescrape`+hostname). **Three separate listeners** (both binaries): `-listen` (health + `/debug`), `-metrics-listen` (default `:9090`, Prometheus `GET /metrics` via `obs.ServeMetrics` — Go runtime/process metrics `go_*`/`process_*` from `client_golang`'s collectors, ALWAYS; plus the `kubescrape_*` Registry metrics exactly when `-self-metrics-interval=0`) and `-pprof-listen` (empty by default, `net/http/pprof` via `obs.ServePprof`). Separate ports because they have different exposure profiles: profiles carry goroutine stacks and heap contents, so that port is the one to firewall. The Go/process metrics are deliberately NOT on the OTLP push — they are operator-facing process diagnostics consumed by a scrape. `kubescrape_*` defaults to the OTLP push and rides the scrape instead when the push is off: ONE knob (`-self-metrics-interval`) selects the delivery modality, so the two paths can never double-deliver the same series (with the push off, the service needs no OTLP endpoint at all). The scrape reads through `metrics.Registry.Dump` (`internal/metrics/dump.go`) + the `registryCollector` const-metric bridge in `obs/runtime.go` — Dump is NON-MUTATING by contract (`TestDumpNonMutating`): it never seals windows, clears `initial` flags or spends counter-func deltas, so serving it beside a push could never steal samples from the exporter (`Registry.snapshot()`, which DOES consume that state, stays the push path's private read). The chart stamps `prometheus.io/*` annotations on both pods (`metrics.scrapeAnnotations`), which kubescrape's own discovery picks up, so the agents scrape their own runtime metrics. `GET /readyz` on the agent is a REAL readiness check (`readiness` in `cmd/kubescrape-agent/config.go`): gates are registered at startup and `/readyz` is 200 only when none are pending, listing the pending ones in the body — a DaemonSet rolling update advances on it, and it previously returned the same static `ok` as `/healthz`, so a broken rollout marched across every node. The `metadata-service` gate is satisfied by the first successful node-metadata fetch. `-check-config` compiles every config section via `validateConfig` (which a real start ALSO calls, so the dry-run cannot drift) and exits without acquiring any resource — adding a config surface means adding it to `validateConfig` too. New failure paths should count into an existing `obs` metric or add one there; tests read values via the `Value()` accessor. Every metric is catalogued in `docs/METRICS.md`, GENERATED from the registrations (`obs.ParseMetricDocs` over `obs.go`); regenerate with `go test ./internal/obs/ -run TestMetricsDocIsCurrent -update-metrics-doc`. `TestDocumentedMetricsExist` fails if prose in README/CONFIGURATION/METRICS/CLAUDE.md names a metric or LABEL that is not registered — README documented the transform-reload counter with a `result` label while the code registers it as `outcome`, so every alert copied out of it silently matched nothing.
- **HTTP metadata caching**: the service stamps metadata 200s (container/pod/pod-uid/node AND node-targets — deliberately NOT pod-ips, whose index exists for recycled-IP immediacy) with `Cache-Control: max-age` + `ETag` (`server.writeCached`, TTL `-metadata-cache-ttl`, default 10s, 0 disables); the targets response is SORTED (URL, then monitor/source) before hashing — `PodsOnNode` iterates a map, and a per-request order would mint a fresh ETag every time, defeating the 304 path on the one route that re-sends every pod document on the node each scrape cycle; `metaclient` caches by URL (stripping the transient `?wait=`), serving fresh entries locally and revalidating stale ones with `If-None-Match` → 304. This cuts repeat lookups on the concurrent ingest and cadvisor paths (`obs.MetadataRequests{cached,not_modified}`). The client cache is mutex-guarded (`metaclient` is shared across concurrent ingest handlers) and stores ONLY the decoded value — no raw body beside it: hits and 304s shallow-copy it out instead of re-unmarshaling (maps/slices shared under the store's treat-as-immutable contract), an entry whose decoded type is not the caller's result type is dropped and re-fetched unconditionally (`lookupEntry`; unreachable in practice, since every caller of an endpoint asks for the same type), and an undecodable 200 is an error and never cached (like 404s). `Client.now` is injectable for tests.

### Invariants the API guarantees (user requirements — do not regress)

- **Container lookups block per container ID.** An unknown ID registers a waiter channel keyed by that exact ID; the pod-upsert path wakes only those waiters. Multiple concurrent requests for the same ID are all released. Waiting is bounded by `-wait-timeout` (client can shorten via `?wait=`, never lengthen). Requests may legitimately arrive ~1s before the kubelet posts the container ID to the API server — this wait covers that gap.
- **Deleted pods stay resolvable via the container endpoint for `-cache-ttl`** (tombstone: `expireAt` + `deletedAt` stamped, swept periodically). Container IDs replaced by restarts get the same TTL; `lastState.terminated` IDs are indexed while the pod lives.
- **Scrape targets never include deleted, finished or TERMINATING pods**: `DeletePod` removes the pod from the node index immediately, before tombstoning. `Succeeded`/`Failed` pods and pods with a `deletionTimestamp` (`kubemeta.Pod.DeletionTimestamp`, filled by `kubeconvert.FromPod` and the single source of truth for the store's `record.terminating`) are excluded by `scrape.Scrapeable` — a draining pod stays `Running` for its whole grace period, so scraping it is pure `up=0` churn, and Prometheus' endpoints SD drops those too. They all remain resolvable by container ID / UID / name: a draining pod's last logs must stay attributable. `kubemeta.Pod.Ready` (PodReady condition) is metadata only — a not-ready pod IS still scraped.
- **`prometheus.io/port` is a comma-separated list** (numbers and/or port names) on both pods and Services; service ports translate to pod ports via `targetPort`. Duplicate endpoints reachable via both pod and service annotations are deduped by URL (pod source wins).

### Concurrency model

One `sync.RWMutex` in `store.Store` (plus one in `services.Index`) guards everything; there are no goroutines besides HTTP handlers, the informer callbacks, and the sweeper (`Store.Run`). Stored `kubemeta.Pod` values are never mutated in place — upserts replace whole records — so returning shallow copies under RLock is safe. `FromPod` deep-copies everything it takes from informer objects; never retain or mutate an informer-owned object.

Store tests use an injectable clock (`s.now`); follow that pattern for any time-dependent behavior instead of sleeping.

### Node agent (`internal/agent/...`)

The agent talks only to the metadata service (`metaclient`) and an OTLP gRPC collector (`otlpexport`, built on `go.opentelemetry.io/collector/pdata`) — no Kubernetes API, no RBAC (except `nodes/metrics` for the kubelet scrapes). Resource-attribute building lives in `agent/attrs`: `attrs.Builder` (nil = defaults) runs defaults → static → config templates (funcs: env/coalesce/default/regexMatch/regexReplace; context: Node/Pod/Container/Service) → `attrs.Filter`, driven ENTIRELY by the config's `resourceAttributes` section (the former `-resource-attrs-static`/`-enable`/`-disable` flags are gone: static duplicated `resourceAttributes.static`, and enable/disable are now `enable:`/`disable:` LISTS there — lists because the comma-separated flag form could not express a pattern containing a comma, which silently fragmented into literal-brace regexes. The filter is global, so a `pipelines:` section setting enable/disable is REJECTED, not ignored); `attrs.Builders` holds one per pipeline (logs/targets/cadvisor/node/journal/ingest/self) merged from the section's `pipelines:` subsection. The defaults set `k8s.pod.ip` (from `Pod.PodIP`) as a resource attribute and derive `service.name` via `attrs.ServiceName` (workload owner → pod name), then finish with `attrs.Identity(res)`, which reads whatever identity attrs are on the resource to derive `service.namespace` (= k8s namespace) and `service.instance.id` (fallback: container.id, pod-uid[/container], namespace/pod[/container], node) for Mimir job/instance — neither overwritten if a template set it; it works for pod/container/node AND pre-populated (KSM splitter, ingest, log-metric) resources. **Instance-collision avoidance** (`attrs.PrefixInstance`, cmb-alloy `instance_prefix`): an exporter that DESCRIBES other objects (cadvisor, a KSM splitter) shares the described pod's `service.name`/namespace, so its `service.instance.id` would collide with the pod's own self-scraped metrics (same job+instance, different resource attrs → flapping target_info). The config's `instancePrefix` prepends `prefix-` to the derived instance; it defaults per pipeline via `defaultInstancePrefix` (cadvisor → `"cadvisor"`, others none), precedence **explicit pipeline section > built-in default > top-level base** (so a global base can't strip cadvisor's protection); split rules default it to the describing target's `service.name` (`splitBatcher.defaultPrefix`), overridable per rule (`SplitRule.InstancePrefix`, `""` disables). Split rules also take `dropLabels` (anchored name regex, labels omitted from data points in `putSplitLabels`) and `attributes` (set-if-absent resource fallbacks applied after `Build` in `fillSplitResource`); several groupBy labels may map to one attribute — applied in sorted label order, non-empty overwrites, giving a deterministic coalesce. On KSM/split resources the rule's `datapointAttributes` (config `datapointAttributes`, default `["k8s.node.name"]`, `defaultDatapointAttrs`) are moved off the resource onto the data points (cmb-alloy placement — a described object's node is a property of the object, not the exporter's identity): `splitBatcher.route` removes them from each split resource into `dpAttrs`, and `putSplitLabels` stamps them on every data point (regular self/scrape/cadvisor/node resources keep them as resource attributes). `[]` keeps everything on the resource. It is invoked at every point a final resource is built — tailer metadata resolution, both single-resource batchers, the cadvisor per-pod resources and the splitter resources (which may pre-put identity attrs before Build). New resource-producing code paths must call `Attrs.Build`. `.Node` metadata comes from `GET /v1/nodes/{name}/metadata` via the agent's `startNodeInfo` provider. **Self-describing metrics carry the emitting process's OWN pod** (`-self-attributes`, default true on BOTH binaries; shared machinery in `internal/selfmeta` — generic `Poll` (background resolve, retries backing off from 5s to the refresh, last-good kept on a failed refresh, `Final` stopping it for good) + `StartPod` + `Wrap` (export-time fill-if-absent stamping via `attrs.FillAbsent`, the same merge the ingest enricher uses) + `Namespace` ($POD_NAMESPACE or the SA projection; `leader.Namespace` delegates here so wanting your own namespace costs no dependency on leader election), with each binary supplying its own resolve func and `Build` in its `selfattrs.go`; `startNodeInfo` runs on the same `Poll`, which is what makes the readiness gate clear seconds — not a refresh period — after the service becomes reachable). The identity half — `k8s.namespace.name`, hence `attrs.Identity`'s `service.namespace`, hence half the Prometheus job — is set at STARTUP from `selfmeta.Namespace()`, never by the stamp: learning it when the lookup lands would rename the job of already-running CUMULATIVE series, on some nodes and not others. A cluster-singleton (`-events`/`-azure-diagnostics`) takes its POD as `service.instance.id` instead of the node, or it collides with that node's DaemonSet agent on one (job, instance). The self chain also BYPASSES the namespace router (`preRoute` + `transform.Wrapper.Fork`, which shares the reloaded program): routing fans out by `k8s.namespace.name`, which these resources only acquired when this feature started stamping it, so a route glob covering the agent's own namespace would have moved the fleet's health signal off the durable buffered chain onto an unbuffered tenant destination. The pod is RE-READ on `-self-attributes-refresh` (1m) so an edited pod/namespace label reaches the metrics it stamps, which the `private` caching makes nearly free (fresh entry served locally, stale one revalidated as a 304); a mis-resolution — realistically a pod IP recycled from a predecessor the store has not dropped yet — heals on the next read rather than lasting until a restart. `selfmeta.verified` (pod name == container hostname) is REPORTED on the resolution log line (`confirmed=`) rather than gating anything: a custom `spec.hostname` is legitimate, but it is the thing to look at if the attributes ever look like someone else's. `obs.RegisterSelfMetadata` publishes `kubescrape_self_metadata_resolved` on both binaries — registered exactly when the lookup RUNS, so a published 0 always means unresolved and never "disabled" — and `kubescrape_self_metadata_lookups_total{outcome}` counts the lookups SEPARATELY from `kubescrape_metadata_requests_total`, whose `not_found` is the container-attribution health signal and would otherwise carry a permanent stream from a fleet that cannot resolve. The stamp's Build runs even with a NIL pod: the operator's static attributes (a cluster name) are what an alert on `resolved == 0` selects by, so they cannot be conditional on the lookup working. The agent (`cmd/kubescrape-agent/selfattrs.go`) resolves over `GET /v1/self` (metaclient `Self`; the service attributes the caller by its CONNECTION's source address — never a header — through the same live-only pod-IP index, so hostNetwork callers and address-rewriting hops get a 404 instead of someone else's identity; a 404 FALLS BACK to `PodByName($POD_NAMESPACE-or-SA-projection, $POD_NAME-or-hostname)`, which is what covers hostNetwork, SNAT and dual-stack agents, and metaclient sets `Proxy: nil` because a proxy hop REPLACES the address the attribution depends on), and wraps the exporter used by `obs.Registry.Run`/`FinalExport` and `spanmetrics.Generator.Run`/final `Export` (ALL of them — the last data point of a series must not carry a different resource than the rest); the METADATA SERVICE (`cmd/kubescrape/selfattrs.go`) needs no HTTP hop and no downward API for the same thing: every pod is already in its store, its pod name is `os.Hostname()` and its namespace comes from `leader.Namespace()` ($POD_NAMESPACE or the ServiceAccount projection it already mounts for in-cluster credentials), so `GetPodByName` + the server's own owner/namespace enrichment is the whole resolve. Stamping is a wrapper, not a resource built once at startup, because a process and the metadata it needs come up together: the attributes must appear without a restart when the store (or the service) fills in second, and nothing may WAIT on the lookup (self-metrics are how such an outage is diagnosed). Fill-if-absent — via the `self` pipeline builder on the agent, the built-in `attrs.Pod`+`Identity` mapping on the service (which has no `resourceAttributes` surface): `service.name` stays `kubescrape-agent`/`kubescrape` and `service.instance.id` stays the NODE / the hostname (stable across restarts, unlike the pod UID `Identity` would otherwise derive) while `service.namespace` newly becomes the pod's namespace — i.e. the job reads `<namespace>/kubescrape-agent`. `.Container` is deliberately nil: which container of the pod this process is cannot be known (sidecar injection makes "the only one" a guess).
- **Series filtering & splitting** (`agent/promscrape/filter.go`, `split.go`, config `metrics` section): ordered first-match-wins keep/drop rules per pipeline applied in `parseAndExport` before conversion (so partial histogram families are possible, as with Prometheus relabeling); splitters route KSM-style targets into per-object resources via `splitBatcher` (groupBy label → attribute mapping + optional metadata enrichment; requires `Kubelet.Meta` even without kubelet scrapes; the shared `podCache` is mutex-guarded because splitters run on concurrent scrape goroutines).
- **Exporter** (`agent/otlpexport`): gRPC or OTLP/HTTP (protobuf POST to /v1/logs, /v1/metrics), bearer token file re-read per minute, TLS CA/skip-verify, bounded retries for metrics only — log retries/rewind belong to the tailer. **Size-bounded sending** (`pkg/otlpsplit` + `Config.MaxSendBytes`, `-otlp-max-send-bytes`, default ≈3.75 MiB under the 4 MiB gRPC limit): every send measures the exact proto size (`plog/pmetric/ptrace ProtoMarshaler.*Size`, attributes+framing included, not just bodies) and splits an over-cap payload into parts each within the cap, preserving resource/scope grouping (`otlpsplit.Logs`/`Metrics`/`Traces`; an over-cap resource splits by record/metric/span, an over-cap METRIC FAMILY splits further by DATA POINT — all five types, preserving the metric shell plus per-point exemplars/quantiles/exponential scale — and a single leaf over the cap goes alone). This is the ONE hard guarantee against wholesale rejection for producers that batch by count (journald, tailer) or forward sender-sized pushes (the ingest server) rather than pre-chunking (promscrape stays under the cap and never trips it). A part-send failure returns immediately and the caller retries the whole payload — at-least-once tolerates the re-sent parts, and nothing commits until every part lands. A non-empty input never yields zero parts (an over-cap record-less resource is sent whole, rejected+counted at the collector, never silently reported delivered); an empty scope's identity is preserved across a big-resource split. Payloads are gzip-compressed by default (`Config.Compression`, `-otlp-compression=gzip|none`) via klauspost/compress: `gzip.go` registers a klauspost-backed gRPC "gzip" codec (do NOT import grpc/encoding/gzip too — last init wins) and gzips HTTP bodies with pooled writers into `github.com/JohanLindvall/bufpool` buffers — the pooled buffer IS the request body (the transport's Close RELEASES it back to the pool; never set `req.GetBody`, a replay would read reused memory).
- **Disk buffer** (`github.com/JohanLindvall/diskqueue` + `otlpexport.Buffered`, opt-in `-buffer-dir`/`-buffer-max-bytes`): a Fluent-Bit-style filesystem write-ahead buffer. The queue is the external diskqueue library (one `Queue[[]byte]` per signal with an identity codec — the sink owns the pdata (un)marshaling): durable FIFO of checksummed records in preallocated segments, headers publishing the cursors (data-before-header, each fsync'd), corruption degrading to REPORTED loss (never a wedged queue, never silent), reopen resuming from the committed cursor (at-least-once across restarts), flock on the directory, `Stats()` as a plain struct. `otlpexport.OpenBuffer` sets `MaxBytes` from the flag with `MaxSegments: -1` — MaxBytes is the ONE operator knob, and the default 32-segment cap would bind behind its back at 256 MiB — and `MaxOpenFiles: 8` so a deep backlog does not hold an fd per segment. The drain runs on `Reader.Reserve(ctx)` (blocking; the queue's own wakeup replaced the old signal channel) with `Commit(offset)` only after the collector acks; commits are a CURSOR (in-order), so a stuck head batch goes back via `Rewind` and rotates to the back via `Requeue` — which is EXEMPT from the capacity caps as of diskqueue v0.0.4, because a poison head at a FULL queue was precisely the wedge `spool.AppendForce` existed for (nothing behind the head can retire first; the rotation is backlog-neutral once its commit lands). A reserved payload ALIASES the reader's buffer (valid until its next read): the sink hashes it for stuck-tracking BEFORE any queue operation — `Requeue` in particular clobbers that buffer. A latched I/O failure (diskqueue latches a failed fsync: every later Add/commit returns `ErrIO`, since a retried fsync can claim success over dropped pages) is recovered by `Buffer.recover` — guarded close-and-reopen keyed on the observed handle, so enqueue and drain goroutines never double-reopen; the affected batch redelivers. `ErrRecordTooLarge` (one batch over the whole cap — refused outright, unlike the transient `ErrFull`) counts into `obs.BufferFull` like a full-queue refusal, while EVERY other enqueue refusal (a latched I/O error, a closed queue, the raw `*os.PathError` diskqueue returns when segment preallocation hits ENOSPC) counts SEPARATELY into `obs.BufferEnqueueErrors` (`kubescrape_buffer_enqueue_errors_total{signal}`) — those used to return bare, so a full disk made a node go dark with every buffer metric flat: `_full_total` is the wrong class, `_dropped_total` is drain-side, and `obs.Exports` sits BELOW the buffer and is never reached. `Buffered` wraps the client with one queue per signal (generic `sink[T]` over plog/pmetric/**ptrace**), implements the shared `otlpexport.Exporter` (ExportLogs+ExportMetrics), enqueues on Export and drains in `Run` with retries (single-attempt inner sends; the backoff persists across cycles to the 30s cap) — commit only after the collector acks (at-least-once across restarts). `IsPermanent` classifies definitive rejections (dropped + counted); auth failures and 404 are deliberately transient — a rotating token or a collector rollout must not drain the backlog into drops. A batch whose TRANSIENT rejection is in fact permanent for that payload (an over-limit message comes back as `ResourceExhausted`) would otherwise circle the queue forever: it is dropped + counted after `maxDrainCycles` (3) accountable failed cycles (`sink.stuckTooLong`, keyed by payload hash into `sink.stuck`, bounded by `maxStuckTracked`). A cycle is accountable only when BOTH hold: the collector delivered some OTHER batch since THIS payload's OWN previous failed cycle (`s.delivered > stuckBatch.lastDelivered`, re-established EVERY lap and never latched — latching it once, "it delivered something at some point, so every later responded lap counts", spent the whole budget during a pure back-pressure event and destroyed good data in exactly the outage the buffer exists to survive; deliveries banked before the payload got stuck, or while it merely sat behind in the queue during a recovery, advance `s.delivered` without a failed lap of ours spanning them and so cannot count), AND the cycle's final error was a collector RESPONSE (`sink.stuckResponded`, set by `trySend` from `respondedError`: an HTTP status other than 408/429/5xx, or a non-Unavailable/DeadlineExceeded/Canceled gRPC status — the retryable statuses OTLP defines are back-pressure, not a rejection of this payload) rather than a transport failure. So a blip delivery followed by a resumed outage spends nothing, and a collector rejecting EVERYTHING (a memory-limiter overload) never arms. Only a live collector repeatedly refusing THIS payload while accepting others is poison evidence. Keying by content hash means the count RESETS on restart, deliberately: a fresh process should re-offer the batch, the collector may have been fixed. A recovered stuck payload is `forget`-ten on success (and on a later permanent rejection) so the tracking map cannot leak. When enabled, main routes ALL consumers (tailer, journald, scrape, log-metrics, ingest) through the single `out` value; the buffer's inner is the raw client. **Traces are PASS-THROUGH except when the payload is OWNED** (`otlpexport/owned.go`, `Own(ctx)`/`Owned(ctx)`): a forwarded trace is still held by the pushing SDK, whose retry IS the durability, so spooling it would ack a sender for data that has not shipped — but a tail-sampling DECISION (`agent/tailbuffer`) acked its senders when it BUFFERED the spans, seconds earlier, and nobody else holds them. The distinction is per PAYLOAD and rides the CALL rather than the wiring, because the layers in between (transform wrapper, router) are shared by both classes and must not know which they carry; `NewBuffered` takes a third `traceBuf` and main opens `traces/` ONLY under `*serviceGraphOn && fileCfg.TailSampling.Enabled()` (elsewhere it would be a flock and a preallocated segment that never take a record). With no traces spool an owned payload still passes through — the marker asks for durability, it does not require it. Physical disk can exceed the cap by up to one 8 MiB segment (delivered-but-unreclaimed records retire whole-segment; `Stats().DiskBytes` reports the real footprint). **Occupancy is observable before anything is lost**: `obs.RegisterBufferStats(buffered.Stats)` publishes `kubescrape_buffer_backlog_bytes`/`_max_bytes`/`_segments` per signal as `Registry.GaugeFuncVec` (a one-label func gauge added for this), so `backlog/max` alerts on a degrading collector — every other buffer metric is a counter that only moves once data is ALREADY being dropped or refused.

- **Tailer performance** (`bench_test.go`): the multiline package (>= v0.0.4) prefilters its start-state regexes with literals derived from the patterns — lines containing no literal skip all start regexes (~12x less per-line CPU). If a pattern change makes the literal set unprovable the matcher silently falls back to full regex evaluation (correct, slower); `TestPrefilterEnabled` (via `patterns.StartLiterals()`) is the alarm. `feedLine` parses the CRI header once and feeds the result to `cri.AddParsed` (multiline >= v0.0.6; the stage's internals never re-parse — the single `cri.Parse` per line is feedLine's), uses precomputed `file.keyStdout`/`keyStderr` (no per-line key concat), and the ledger's offset accounting lives in per-stream `streamState` structs reached via pointers cached on the file (`stStdout`/`stStderr`/`stPlain`, re-derived after every `reset()`) — no map operations per line. The `streamState` fifo of buffered offset ranges is consumed by advancing `fifoHead` (`live`/`push`/`pop`), never by re-slicing: re-slicing walked the backing array forward until its capacity ran out and then, since the steady state is one line pushed and one popped, reallocated a one-element array for EVERY line — that was the tailer's entire per-line allocation. **The line path is now zero-alloc** (BenchmarkIngestLine: 0 allocs/op; keep it there). The same re-slicing trap applied one level up, to the per-file carry buffer: `consume` advances `f.pending` by re-slicing, so `ingestChunk` appending the next 64 KiB read into its drained-to-zero spare capacity allocated a fresh array per READ. `file.pendingBase` pins ONE array per file and `appendPending` memmoves the unconsumed remainder back to its front (`TestPendingBufferIsReusedAcrossChunks`: the only per-chunk allocations left are `consume`'s per-line `string(line)`); a buffer grown past `maxIdlePendingBytes` by one over-long line is released once the file drains, so a node tracking thousands of files cannot pin a megabyte each. BenchmarkIngestLine/BenchmarkIngestFlush track the per-line budget (~0.2µs pipeline, ~0.8µs with enrich); BenchmarkIngestChunk covers the read path (~130 B/line, down from ~260).
- **Tailer** (`agent/tailer`): single sweep goroutine over the configured log sources (see the Log sources bullet; default `/var/log/containers`). Log lines flow through the two-stage `github.com/JohanLindvall/multiline` pipeline, per file: `multiline/cri` parses the CRI format and rejoins P/F fragment runs (non-CRI lines pass through rather than being dropped), then `multiline` joins stack traces. Offset mapping relies on stage emission being synchronous inside `Add`/`Flush*`: `lastEnd[key]` is exact because the line completing a run is always the line currently being fed, and `Entry.Lines` (which counts even limit-dropped lines) pops the per-key FIFO of logical-line offset ranges. At-least-once invariants: exports happen inline in the sweep with retries; per-file offsets are committed only after a successful export and never past lines still buffered in either stage (`watermark` = min of `runStart` and FIFO heads); on a TRANSIENT failure files are rewound to the committed offset and the pipeline is discarded unemitted (the lines get re-read); a PERMANENTLY rejected batch (`otlpexport.IsPermanent` — bad payload, unimplemented, over a receiver's body limit) is the one exception and the one LOSS path: retrying it can never succeed and one sweep goroutine serves every file on the node, so rebuilding it forever would stop ALL log shipping there, pin the fd against logrotate and lose the backlog outright when the file rotates away — so the batch is dropped and the offsets advance (`advanceBatch`, not `commitBatch`: the records were never delivered, so `LogEntries` must not move, and nothing was rewound, so `LogExportFailures` must not either). `obs.LogPermanentDropped` (`kubescrape_log_permanent_dropped_total`) plus the Error log carry it exactly — **it is the tailer's data-loss signal and is worth an alert on any nonzero rate**; `exportWithRetry` short-circuits the retry budget on the same classification. With `-buffer-dir` the tailer's Export returns the ENQUEUE verdict rather than the collector's, so on that configuration this counter moves only for a batch larger than the whole buffer cap and the collector's own permanent rejections land on `kubescrape_buffer_dropped_batches_total{signal="logs"}` + `kubescrape_buffer_dropped_records_total{signal="logs"}` instead — which is where the buffered chain's alert belongs (the batch counter says a loss happened, the records one says how big it was); checkpoint PRUNING is gated on a successful listing (`lastListingOK`) — one save while a glob failed destroyed the offsets of files it merely could not see — and so is the END OF STARTUP: the stored positions (`Tailer.checkpoints`) are consulted by EVERY scan, not just the first, because a startup glob that fails (an unreadable include base, a transient EIO) discovers nothing and the 2s `dirTicker` then finds every file on the node with no checkpoint applied — a node-wide re-ingest from byte 0 with every `Pending` prefix destroyed and no counter moving. An entry is CONSUMED when it is applied and dropped when a SUCCEEDED listing did not see its path (the same proof that lets the store be pruned, so a stale offset can never be applied to a recreated path), and `-logs-unknown-files` governs a checkpoint-less file only while `Tailer.startingUp` — a file appearing after a listing has succeeded is new and is read whole whatever `end` says — and a positions file that failed to DECODE reports `Corrupt()` so `auto` re-reads instead of skipping every file to its end as history (an empty store is otherwise indistinguishable from a first run); committed offsets are checkpointed to disk via the positions store (persisted immediately when a new file is discovered — a crash before a file's first entry would otherwise skip it as history on restart; where a checkpoint-less file starts is `-logs-unknown-files`: auto/end/start, auto = read from start when the store already has entries). A file's metadata is resolved (with server-side wait; failures back off EXPONENTIALLY from `minMetaBackoff` 2s to `maxMetaBackoff` 1m, each delay jittered over `[d, 1.25d)` by `jitterMetaBackoff` — the lookup BLOCKS server-side for the whole `-metadata-wait` and runs on the single sweep goroutine, so a flat short retry lets a few permanently unresolvable files monopolise the tailer, and an unjittered one puts every file on a node — and every node in the fleet — on the same schedule, so a metadata-service rollout recovers into one synchronised burst) before its data is consumed — nothing is read until it can be attributed; a file deleted before it ever resolves is released with the loss COUNTED (`obs.LogUnresolvedLost`), since nothing was read and nothing can be. Idle files close their fd after `-logs-idle-close` (default 0 = never; the file stays tracked and reopens with identity re-verified on activity) — steady-state fds are one per active file, not per tracked file. Rotation: identity = inode + head fingerprint (FNV of first `-logs-fingerprint-bytes`; catches inode reuse AND copytruncate — the post-read `read == 0` check catches a same-or-smaller rewrite, and a PRE-read fingerprint re-verify in `readFile` (whenever the file's mtime moved since the last read) catches a copytruncate whose replacement content is LONGER than the read offset. fingerprints EXTEND (shared `extendFingerprint`, called from `saveCheckpoints` AND from readFile after a successful read — without the read-path call a store-less deployment never extends and a file first opened at size 0 keeps the matches-anything empty fp forever) only while the head already hashed still matches — re-hashing unconditionally would adopt a copytruncate replacement's head and blind both guards for every sub-`FingerprintBytes` file; the truncation DECISION in readFile uses the PRE-settle readPos (settle can rewind it and re-evaluating against the shrunken value missed an in-place rewrite sized between committed and readPos); rename rotation drains the old fd before switching and OPENS the new incarnation immediately — `reopen` clears `f.f`/`f.inode`/`f.fp`, so leaving it unopened until the next sweep let a SECOND rotation inside that window find nothing to drain, record no segment, and lose the whole middle incarnation silently; deletion drains before drop. **Segment-qualified offsets** (the decomposition docs/tailer-comparison.md describes — DONE): every buffered/emitted offset is a `pos{seg, off}` where `seg` is a per-file monotonic incarnation id (the live file is the TAIL segment; each rename rotation closes the tail into a `segment` record `{id, inode, fp, committed, to, fd}` on `file.segments` and issues a fresh tail id). A segment's `to` is the last FED line boundary (max `streamState.lastEnd` at the tail), NOT readPos: trailing bytes that never entered the pipeline (torn fragment, blank line, rate-dropped or oversize-discarded lines) can never produce a committing entry, and a `to` covering them pinned the segment below retirement forever. An UNRECOVERABLE segment (findRotated miss, file pruned) is counted (`obs.LogPrefixLost`) AND retired — keeping the record wedges retirement. `segmentsFed` asserts every recorded segment's owed lines are live (pipeline or batch); rotation preserves the incoming value (`wasFed`, vacuously true with no prior segments) rather than overclaiming — a mid-drain rewind purges older segments' re-fed lines, and marking them fed stranded an older rotation's lines until restart. A mid-drain flush FAILURE aborts the drain (`drainReader` returns false — the rewind seeks the very fd being drained back, and continuing was a hot loop burning export attempts on the single sweep goroutine); the rotation is retried next sweep with the fd held. Cross-rotation ambiguity is inexpressible by construction: an entry commits against `end.seg`'s record — the tail candidate advances the file checkpoint, an old segment's candidate advances that segment's `committed`, a segment retires (`retire`: fd closed, checkpoint entry gone) when its whole range commits, and a DEAD id (truncated-away incarnation, or the archive-replaced restart's `newTail`) resolves to nothing. This replaced the old rotation-generation protocol (`gen` stamping + apply-time checks) and the `reanchor` offset rewrite wholesale. **Multi-line groups (CRI P/F runs and stack traces) join across a rename rotation**: if data is still buffered after draining the old inode, `reopen` carries the pipeline — buffered items keep their old-segment positions untouched — and the fresh tail id disambiguates the new inode's bytes. Zero-loss across a crash, including multiple rotations: incomplete segments are checkpointed (`positions.Prefix` list, oldest first; identity = inode+fp; `From` is the segment's commit PROGRESS, so a restart re-reads only the owed `[From,To)` remainder), and `reopen` persists the checkpoint IMMEDIATELY when a segment is recorded — the 10s cadence alone left a crash window that lost the rotated tail outright (discovery persists immediately for the same reason). Each segment RETAINS the rotated inode's fd but the retained fds are CAPPED (`maxCarriedFds`, oldest kept — they prune first) so a long outage across many rotations cannot exhaust fds or pin unbounded disk; `reopen` NEVER resets `segments` (a later rotation must not drop earlier uncommitted ones); on restart (or after a rewind that discarded the buffered group, tracked by `segmentsFed`) `feedSegments` re-reads each incomplete segment's owed range UNDER ITS OWN id (`ledger.feeding`) — `findRotated` (by inode+fp in the resolved target dir) is the post-RESTART fallback (no fd survives a restart); when it too fails the loss is counted (`obs.LogPrefixLost`) and the segment retired. A rotation that happened while the agent was DOWN is recovered too: `initFile` sees the checkpointed identity no longer matching the path and synthesizes an OPEN-ENDED segment (`to = -1`; feedSegments reads the rotated file to EOF and pins the range, or counts + retires when pruned). Caveat: the join only spans rotations the tailer actually **observed** while running (it follows the symlink, not every intermediate rotated file — a rotation so fast the intermediate inode is never opened loses that segment, pre-existing). Truncation/copytruncate still flush-and-reset (content replaced, joining meaningless). **Audited micro-edges (2026-07-30 exhaustive pass; all fail-safe, none worth code)**: the FIFO orphan-drop uses strict `Before`, so a cap-dropped line sharing its exact nanosecond with the surviving entry's first line under-commits until later pops self-heal it (duplicates, never loss); an `end`-mode skipped file checkpoints `Offset=size` with inode 0 until its first read, so a crash inside that sub-second window plus a rotation-while-down into a LONGER file can resume mid-file; `LogTornFinalLines` counts rename rotations only — truncation losses are unmeasurable by nature; `LogBytes` excludes segment-replay re-reads. Sweeps are fsnotify-driven (watch the symlink dir + resolved target dirs; files directly in the watched dir are a test-only special case) with the poll ticker as fallback. **Log rules** (`Config.Rules` = `metrics.LineFilter`, config `logs.rules`): ordered keep/drop/sample evaluated in flush AFTER enrich (synthetic `logchain.SeverityKey` = `__severity__` via `logchain.Resolver.RuleFn`, fed by `logchain.LowerSeverity`) and AFTER LogMetrics (metrics see every line); with rules set, records build in a one-record scratch slice and `MoveAndAppendTo` into the batch only when kept; dropped records still advance offsets (an all-dropped batch commits without exporting) and count into `obs.LogRulesDropped`. **Rate limiting** (`Config.RateLimit/RateBurst/RateDrop`, flags `-logs-rate-*`): per-file token bucket in `allowLine`/`consume`; pause mode sets `file.limited` (readFile/readArchive stop reading, pending retried next sweep — for archives BEFORE the archiveDone short-circuit, or an EOF-paused tail wedges), drop mode discards lines; rotation drains bypass the limiter (`consume(..., unlimited=true)`) or the rotated remainder would be lost. Pause mode's no-loss contract holds across EVERY restart path: `reopen` and the archive restart salvage complete pending lines (unlimited) before the reset, and the shared `file.restartAt` clears `limited`/`discarding` with pending everywhere (openArchive included — a wiped pending with `limited` still set wedged the file forever, and the archiveReplaced block once drifted from reopen by omitting exactly these resets). An unterminated fragment at a RENAME rotation can never complete and is dropped counted (`obs.LogTornFinalLines`); an oversized unterminated line (> MaxEntryBytes+4096) discards its prefix AND its eventual remainder (`file.discarding`, `obs.LogOversizedDropped`) — the mid-line suffix must not export as a record. **Status** (`status.go`): `publishStatus` (housekeeping, `statusEvery` 10s) snapshots per-file positions/lag into an atomic pointer read by `Tailer.Status()` → agent `GET /debug/tailer`; gauges `obs.LogLagMaxBytes`/`obs.LogLagTotalBytes` (`kubescrape_log_lag_max_bytes` is the per-file maximum, `kubescrape_log_lag_bytes` the sum — the two were named the other way round, with `_total` on a gauge); compressed files report `Lag = ReadPos − Committed` (Size is compressed bytes, offsets are decompressed — their difference is meaningless). **Withheld commits**: a record exported while ANOTHER stream's multi-line group is buffered has its commit clamped to the build-time watermark (a candidate in a segment NEWER than the watermark's commits nothing, same segment clamps to its offset, older segments are unconstrained); the unclamped high position is remembered (`file.exportedHigh`, via `batchInfo.highs`) and re-offered at the next flush touching the file — without it `committed` froze below `readPos` forever (restart re-reads the tail, idle-close never releases the fd, lag gauges show phantom backlog). Exports are synchronous in the sweep (`flush.go`: `batchInfo` carries build-time per-segment candidates to `commitBatch`/`failBatch`); the former opt-in pipelined-export mode was REMOVED — its settle protocol cost more in invariants than the overlap earned, and `-buffer-dir` provides the same decoupling with at-least-once durability (docs/tailer-comparison.md).
- **Log sources** (`agent/tailer/sources.go`, config `logs` section): the tailer discovers files by `[]Source` (doublestar include/exclude globs, `**` supported) rather than a single dir; empty config = one default containerd source over `-log-dir`. Each source is `containerd` (CRI filename→containerID→metadata→CRI parse) or plain (arbitrary files: no metadata lookup, resource attrs = builder node attrs + the source's static `attributes`, `service.name` defaulting to the source name; per-source `multiline` override). **Cheap selection**: a containerd source takes `namespaces`/`excludeNamespaces` (path.Match globs, read from the CRI FILENAME at discovery — a non-matching file is never opened, tracked or read) and `selector` (pod label equality, applied at RESOLVE time since labels are only known then — the file is tracked but no data is ever read) and `ignoreOlder` (mtime cutoff, any source; a file already tracked OR carrying a stored offset is NEVER ignored however stale — dropping it would abandon its unshipped tail and re-ingest the whole file if it were ever appended to again). Both beat a `logs.rules` drop for cost control, which pays read+parse+enrich first and saves only egress. A file is claimed by the first matching source — INCLUDING a containerd source that skips it for a PROHIBITION (global `ExcludeNamespaces`, the source's own `excludeNamespaces`, or an unparseable CRI name): the exclude list is the observability feedback-loop guard and a later catch-all source must not resurrect the file. A source's `namespaces` ALLOWLIST is the one exception — a miss is routing ("prod through source A, the rest through source B"), so the file is deliberately left unclaimed for a later source. `claimPath` therefore tests `deniesNamespace` (the deny half alone) and `wantNamespace` separately: testing the merged `wantNamespace` for the claim silently took the deny with it and lost the guard. Non-regular files (FIFOs, sockets) are never tracked — open/read on a FIFO blocks forever and would wedge the single sweep goroutine node-wide. A non-gzip file matched by a compressed source is quarantined under its current identity (archiveDone + size/mtime; a valid rewrite recovers on its own) instead of warn-looping every sweep. Plain files bypass stage-1 (CRI) — `feedPlainLine` feeds the trace stage directly under a single `plainKey` so **the identical rotation / offset / cross-rotation-multiline machinery applies** (`file.source` selects the path; `newPipeline`/`feedLine`/`resolveMetadata`/`stopPipeline` branch on `source.containerd`, guarding nil `criStage`). The watcher watches every source's fixed include base dirs (`scanDirs`). Per-source `compressed` (gzip): compressed files use a separate one-shot `readArchive`/`openArchive` path (offsets in *decompressed* space; gzip isn't seekable so resume re-decompresses and `io.CopyN`-discards the committed prefix; read whole, not skipped-to-end; `rewind`/`drop` branch on `f.compressed`). The archive's fd is RETAINED past EOF (`archiveEOF`) and across a rewind while its data is uncommitted (`closeArchiveReader` closes only the gzip reader; `openArchive` re-decompresses from the retained fd) — an export can fail and logrotate can prune the `.gz` before the retry, and the fd is then the only handle to it; it is released once `committed >= readPos`. An archive REWRITTEN in place (same inode, new content) is detected by `archiveReplaced` (fingerprint of the held fd, checked each `readArchive`) and restarts the file at zero — without it the reuse path would resume at a stale decompressed offset; and the EOF path only stamps `archiveDone` when the path still names the inode we read, so a replacement is not mistaken for consumed — the incremental containerd/plain path is untouched when `f.compressed` is false. Caveat: `consume` drops empty physical lines, so multi-line formats needing a blank separator (Go panics) don't join for plain files (CRI's blank is a non-empty `…F ` line); indentation-based traces (Python/Java/.NET) join fine. Non-UTF-8 transcoding was intentionally dropped (Linux-only target) — lines are UTF-8/passthrough. **Per-workload annotation config** (`podconfig.go`, pod annotation `kubescrape.io/logs`, one JSON object): `exclude` (self-service opt-out; file stays tracked, skipped in sweep and status), `multiline` (overrides the source's stack-trace joining, consulted at pipeline construction — always after resolve), `serviceName`/`attributes` (overwrite resource attrs after Build — the workload is authoritative about itself), `rules` (compiled `logline.LineRule`s evaluated BEFORE the global chain; a pod drop is final, a pod keep still passes the global rules; flush creates the scratch slice when ANY tracked file carries pod rules — `anyPodRules`). Parsed once per file at resolve time; a malformed annotation warns and is IGNORED (must not lose logs). Opt-in `-logs-file-attributes` (`Config.FileAttributes`) stamps `log.file.name` (basename) + `log.file.position` on every record; `entry.start` is the record's start offset (first fragment's, threaded through cri as the entry data / `items[0].start` for trace groups), distinct from `entry.offset` (the post-record commit offset).
- **Scraper** (`agent/promscrape`): hand-written streaming parser for the Prometheus text format, classic + OpenMetrics (constant memory; do NOT replace it with `expfmt`, which buffers whole metric families — the 100k-series requirement is why it exists). The parser classifies samples into roles (`parser.go`); `convert.go` groups histogram/summary component series per family and label set into proper OTLP Histogram/Summary points — grouping state lives only for the current family, so memory stays bounded by the largest family, not the scrape. Exemplars are opt-in (`Config.Exemplars` / `-scrape-exemplars`): enabling them switches the Accept header to OpenMetrics; the parse mode is always detected from the response Content-Type (OM uses float-second timestamps, classic integer milliseconds). **`# HELP`/`# UNIT` become the OTLP `Description`/`Unit`** (the standard Prometheus→OTLP mapping — what an OTLP consumer displays): the parser records them per FAMILY (`Parser.metas`, bounded by `MaxTrackedFamilies` and a `maxMetaBytes` text budget, cleared per exposition like the TYPE table) and stamps them on every `Sample` through `classifyCached`, a per-name memo that also absorbs `classify`'s TYPE probe and suffix walks so the per-sample cost stays flat; UNIT is carried VERBATIM (no UCUM guessing). The batchers apply them where the metric is CREATED (`metricMeta.apply`, once per metric, never per sample) and charge their bytes to the chunk estimate (`metaFieldBytes` covers the field framing) — a split/cadvisor batch repeats every descriptor per described object, so uncharged HELP text would flush past the collector's receive limit. Conversion chunks per export via the `chunker`/`sink` interfaces at whichever of `BatchPoints` data points (10k) or `BatchBytes` estimated bytes (`defaultBatchBytes`, 3 MiB) comes first. **The byte bound is not optional**: a collector's default gRPC receive limit is 4 MiB and applies to the DECOMPRESSED message, and a point count does not bound bytes (10k points of a label-rich family marshal past 5 MiB → every export of that target is rejected = total metric loss). Each sink tracks the estimate (`numberBytes`/`histBytes`/`summBytes` for points, `resourceBytes` + `metricOverheadBytes` charged where a resource/metric is CREATED) and the converter re-checks it BETWEEN the points of a flushing histogram/summary family (`converter.emit`), so one huge family cannot overshoot either bound. **Counting only data points is not enough**: the split and cadvisor batchers emit one ResourceMetrics per DESCRIBED OBJECT, each with a full enriched attribute set plus its own copy of every metric descriptor — a 12k-pod KSM split flushed at an estimated 3 MiB and encoded to 6.7 MiB, i.e. straight past the limit the estimate exists to respect. An aborted parse (sample limit, truncated body, read timeout mid-body) still exports what was converted before the abort — every kind here is cumulative, so a partial scrape costs nothing but the missing series. **Hot-path allocation discipline** (bench_test.go guards it; ~4→0 allocs/sample): the parser interns metric/label names and label values per scrape (`internName`/`internValue`, capped — `maxInterned*`; `map[string(b)]` lookups don't allocate) and short-circuits even the intern probes with last-seen memcmp caches (`lastMetric`, per-position `lastKV` — consecutive lines of a family are near-identical; `string(b) == s` doesn't allocate), whitespace is skipped with `skipSpaceTab` (NOT `bytes.TrimLeft`, which builds an ASCII set per call), `converter.labelKey` fingerprints into a reused buffer (`keyBuf`/`keyLbl`) with a keyed `map[string(buf)]` lookup, the batcher's `metricByName`/`remember` cache the last family, and `parseAndExport` filters through `MetricFilter.session()` (per-scrape name→rule-bitmask memo plus a per-(matcher,value) label-regex memo — label values repeat heavily; the shared filter stays immutable). The last-seen caches also skip the byte scans: `parseSample`/`parseLabels` match the previous line's name plus terminator in one memcmp, and `parseQuoted` finds the closing quote with `bytes.IndexByte` — keep new per-sample code free of per-call closures and `fmt`. Per-scrape state is pooled across scrapes: `getParser`/`putParser` reuse the parser + its `bufio.Reader` (family `types` cleared per exposition, intern maps kept warm with cap-based clears), and the converter recycles histogram/summary accumulators via `histFree`/`summFree` — a 10k-series scrape parses in ~3 allocs. **Native histograms** (opt-in `-scrape-native-histograms`, `protoparse.go`): targets — splitter-backed ones included (`splitBatcher.addExponential` routes native points through the same groupBy/enrich/dropLabels machinery) — are offered the protobuf exposition (`acceptProto`) and a protobuf response is parsed as delimited MetricFamily messages: classic families flow through the same converter/filter/relabel machinery as text samples, native histograms convert to OTLP EXPONENTIAL histograms (scale = schema, zero bucket carried, span/delta buckets decoded dense with the OTLP offset = first Prometheus index − 1; `decodeSpans` advances past each span's length before applying the next offset — its gap/negative/missing-delta guards cap hostile shapes at `maxExpBuckets`). NHCB (schema −53) falls back to classic buckets; a family with both native and classic data uses native. The protobuf path carries **exemplars** under the same `Config.Exemplars` gate as the text path (`Counter.Exemplar`, `Bucket.Exemplar` → `Sample.Exemplar`; a native histogram's family-level `Histogram.Exemplars` → the exponential point, capped at `maxExemplarsPerPoint`) — it must, or `-scrape-native-histograms` would silently switch `-scrape-exemplars` off for every target honouring the protobuf Accept. Prometheus 3.x quoted UTF-8 names ARE supported (`parseQuotedNameSample`/`familyToken` in `pkg/promparse`): the metric name as the first brace entry (`{"my.metric",code="200"} 1`), quoted label names, and quoted families on `# TYPE`/`# HELP`/`# UNIT` all unescape to the same strings so classification and metadata line up; the quoted paths are deliberately COLD branches that skip the last-seen caches, keeping the classic hot path's allocation discipline intact (bench-pinned).
- **Kubelet scrapes** (`agent/promscrape/cadvisor.go`; cgroup-path parsing in `pkg/cgroupid`): with `-kubelet-endpoint` the agent scrapes `/metrics/cadvisor` and `/metrics`, bearer-authenticated with the mounted ServiceAccount token (the agent's ServiceAccount exists ONLY for `nodes/metrics`). cadvisor routing (`cadvisorBatcher`) keys resources by the cgroup path in the `id` label (`cgroupid.Identity` parses both cgroupfs and systemd layouts): container ID → exact incarnation via `/v1/containers/{id}` (non-blocking); pod-level series (e.g. `container_network_*`, which have NO container id) → `/v1/pods/{ns}/{name}` cross-checked against the cgroup pod UID; sandbox rows (`container="POD"`) fold into the pod resource (their cgroup names the pause container — never look that ID up; `ident.image` is cleared too, it names the pause image). On pod/container-identified rows (`ident.podScoped()`) the redundant `id`/`name`/`image` labels are elided from data points (`redundantOnPodRow` in `putFilteredLabels`; unresolved resources keep the image as `container.image.name`); rollup rows keep `id` — their only distinguisher on the shared node resource. Lookups share a 1-minute TTL cache. `-cadvisor-rollups=false` drops above-pod-level cgroup series AND pod-level rows of container-scoped families; `podScopedFamily` (container_network_*) is the keep-list of families with no per-container breakdown. All pipelines toggle independently: `-logs`, `-metrics`, `-cadvisor`, `-node-metrics`, plus opt-in `-journald`. `Config.HealthMetrics` exports per-target `up`/`scrape_duration_seconds`/`scrape_samples_scraped` gauges after each cycle (`scrapeOutcome` collected in `cycle()`, `exportHealth()`).
- **journald** (`agent/journald`, opt-in `-journald`, **cgo**): reads the journal natively via `github.com/coreos/go-systemd/v22/sdjournal` (libsystemd) — no journalctl subprocess. **This is deliberately IN scope** (unlike host `/proc` metrics, which are out — see the out-of-scope notes in README/COMPARISON): node/system *logs* (kubelet, containerd, systemd units) are how a node's Kubernetes plane is debugged and on many distros live only in the journal, so they are worth the cgo cost; host *metrics* (node_exporter's job) are not. journald is the SOLE reason the agent is CGO_ENABLED=1 / non-static — do not drop it to make the agent static without revisiting that trade. One resource per unit (identity attrs pre-put, then `Attrs.Build` with the `journal` pipeline). The reader is decoupled behind a `source` interface (`next`/`close`) opened by `Reader.open` (default `openJournal` in `source_sdjournal.go`; tests inject a `fakeSource`), so `journald.go` (batch/convert/cursor/flush) has no cgo and is fully unit-tested. A MESSAGE over `MaxEntryBytes` is truncated on a rune boundary and the record carries `log.truncated`+`log.original_length`, counted `obs.JournalTruncated` (never a silent cut). sdjournal seek: resume via `SeekCursor` then skip the (still-present) cursor entry once; tail via `SeekTail`+`Previous`; `next` loops `Next`/`Wait(1s)` honoring ctx. At-least-once via the cursor: committed only after successful export; on failure/reader error the source is closed and reopened from the committed cursor with backoff. **While NO cursor has been committed yet** (first run, or no positions store) the restart path cannot recover the buffered entries — a reopen with an empty cursor seeks to the journal TAIL — so `Run` keeps retrying the pending batch's export (with backoff) instead of reopening; the journal itself is the buffer, and the first successful export makes the normal re-read semantics apply. Do not "simplify" that back into an unconditional restart. Because the agent links libsystemd it is built **CGO_ENABLED=1** (the metadata service stays CGO_ENABLED=0 static); the image is `distroless/base` + copied libsystemd (+ libcap/libgcrypt/libgpg-error/liblz4/liblzma/libzstd), not `distroless/static`.
- **Kubernetes events** (`internal/agent/events` + `internal/leader`, opt-in `-events`): a CLUSTER-SINGLETON pipeline — the agent binary run as its own single-replica Deployment (`charts/kubescrape/templates/events.yaml`, `deploy/events.yaml`) with every per-node pipeline off, deliberately NOT in the DaemonSet: that would put cluster-wide `events` read plus lease/configmap write on every node (the DaemonSet's SA holds only `nodes/metrics: get`) and cost one Lease poll per node per retry period. `leader.Run` wraps client-go `leaderelection` in a re-entry loop (its `Run` returns on lease LOSS and never re-acquires; `OnStoppedLeading` fires even if this candidate never led, so an `led atomic.Bool` guards the transition and `OnStartedLeading` — which runs in its own goroutine — is joined before the next round). `Reader.Run` is the leader-only work: batch → export → and only after the collector ACKS, advance and persist the position. **The position is a ConfigMap, not a node-local file** (`ConfigMapStore`): the leader moves, so the successor of a killed pod must read where its predecessor stopped; a written position is only ever a LOWER BOUND on what was delivered, which is what makes a zombie writer harmless (worst case a replay) and why no fencing is needed. Position = watch `resourceVersion` + a timestamp `Watermark`: the RV resumes exactly, but only while inside the API server's watch window (minutes) — past that the watch fails Gone and `expire` arms `relist`: streams start from `""` (the full `--event-ttl` backlog, watermark filtering what was already shipped) until a COMMIT secures the replay (settle/bookmark clears it) — a watch attempt that dies before anything commits must relist again, or the gap is lost after all. A stream that redelivers (committed resume, relist, cold `start`) first DROPS the retained batch — the entries re-arrive, and keeping them duplicated the backlog once per restart and grew memory without bound across a collector outage; only the cold skip-backlog path, whose List revision is past the buffered entries, retains them. Taking the cold-start policy there instead would skip to the current revision and silently lose the gap the relist exists to cover — but only once something has been exported (a zero watermark cannot filter, so a cold `-events-start=end` expiry honours the start mode). A BOOKMARK (`AllowWatchBookmarks`) applies immediately only when the batch is EMPTY; otherwise it is ahead of unexported records and defers to the flush covering them (the tailer's watermark discipline). `Modified` IS an occurrence — Kubernetes aggregates repeats into one object with a growing `count`, so handling only `Added` loses "BackOff x47"; `Deleted` is TTL expiry and ignored. The RESOURCE is the INVOLVED OBJECT's (a Pod resolves through `metaclient.PodByName` with the UID cross-checked, so a recreated pod of the same name cannot lend its identity to an event about its predecessor), which is what makes events correlate with that pod's logs; `actx.Node` is deliberately left NIL — the node an event is about is the object's property, never the singleton reader's. The full chain applies in the tailer's order (scrub → logAttributes → enrich → logMetrics → rules), and `-events-position-interval` bounds the REPLAY after a hard kill (never loss; a graceful stop always writes a final position from a detached context).
- **Azure diagnostics** (`internal/agent/azurediag`, opt-in `-azure-diagnostics`): consumes diagnostic-settings output (resource logs AND platform metrics) from an Event Hubs namespace over its KAFKA surface (franz-go, port 9093, TLS). Cluster-scoped like `-events` — same singleton Deployment (`azure.enabled` renders into the events template; either section's enabled creates the Deployment) — but with NO leader election: the Kafka consumer-group protocol IS the coordination, and the group's committed offsets ARE the resume position (no ConfigMap; replicas > 1 share partitions). Delivery is ack-gated at-least-once: a poll's records convert to plog+pmetric, and `source.commit` (CommitUncommittedOffsets) runs only after BOTH signals are acked (`Reader.deliver`); a permanent rejection or an undecodable message is counted and committed past (poison must not wedge the partition), a transient failure retries in place without committing. The kgo client sits behind the journald-style `source` interface (`poll`/`commit`/`close`), so the loop is unit-tested with a fake and `kafka_test.go` runs a REAL kgo group against `kfake` (join, `^insights-.*` regex topics, commit, resume-past-committed). **Auth** (`auth.go`): connection string → SASL PLAIN (user `$ConnectionString`, file re-read per session); managed identity → OAUTHBEARER with a hand-rolled Entra token source (workload identity's client_assertion exchange when `$AZURE_FEDERATED_TOKEN_FILE`+client/tenant are present, else IMDS; cached, refreshed `refreshMargin` ahead of expiry, stale-but-valid served on refresh failure) — deliberately NO Azure SDK, same trade as rejecting OAuth2/SigV4 in otlpexport. **Decode** (`decode.go`): the `{"records":[...]}` envelope is walked with lightning `ArrayEach` (>= v0.0.62 — extracted from the hand-rolled splitter that used to live here; STRICT syntax, so a malformed envelope is one decode error at the split, never elements silently fused, and the callback form materializes no per-poll [][]byte); per record one lightning `GetPaths` pass extracts only the envelope fields; classification is per RECORD (`metricName` + ≥1 aggregation → metric), since one hub may carry both. Logs keep the verbatim record JSON as the body and run the full chain in the tailer's order (scrub → logAttributes → enrich → logMetrics → rules; `resultDescription` is scrubbed too — the one attribute copied from free text); metrics become GAUGES `<prefix><metricname>.<agg>` (count/total/minimum/maximum/average, `azure.metric.timegrain` as a dp attribute) — gauges because each value is one closed pre-aggregated window (the webdevops-exporter shape), NOT delta sums (Mimir rejects delta) and NOT cumulative (would need per-series state). The ARM resource is the OTLP resource (`resourceid.go` parses the UPPERCASED id): cloud.resource_id verbatim, subscription/rg/type/name lowercased, service.name=resource name, service.namespace=resource group, service.instance.id=lowercased id (two same-named resources must not merge). Readiness gate `azure-eventhub` is satisfied by the first successful poll, empty included.
- **Log enrichment** (`agent/logenrich`, ONE flag `-enrich`, default true, covering the tailer, journald, the events and azurediag converters and the ingest log path alike — it replaced three separate toggles for the same feature that nothing wanted to disagree): `logenrich.Apply(lr, line)` runs `github.com/JohanLindvall/enrich` over each exported line in the tailer/journald/events/azurediag convert paths (events and azurediag use the OVERWRITING `Apply` like the tailer — they build the records themselves — while ingest uses `ApplyBody`, the sender being authoritative). Parsed timestamp overrides the CRI/journal time (ingest time stays in ObservedTimestamp), explicit level overrides severity (enrich's severity numbers ARE the OTLP numbers — cast directly), 32/16-hex IDs (dashes stripped, all-zero rejected) fill the trace/span fields, the rest become record attributes (`log.template`, `exception.*`, `azure.*`, `cloud.resource_id`). `exception.stacktrace` is suppressed for `Format == pattern` (a pattern-parsed trace is a verbatim slice of the body — attribute would double megabyte multiline entries; JSON-carried traces stay, and a substring check does NOT work: single-frame JSON traces contain no escapes and are substrings of the raw line). `Result.Format` feeds `obs.LogEnriched{format}` ("" → "none"). Body is never modified. New log-exporting paths should call `Apply` behind a config toggle.
- **One log chain, one resolver** (`internal/agent/logchain`): the key resolver every log producer needs — record attributes first, then the resource, with the synthetic `__severity__` for RULES only — plus `LowerSeverity`, live in ONE place. There were five copies of the resolver (tailer, journald, events, azurediag, and an open-coded one in `-test-config`) and five spellings of the severity lowering, of which only the tailer's handled `WARNING`: the same line selected differently depending on which pipeline carried it, and `-test-config` proved its own re-implementation rather than production. The tailer's per-line budget is unchanged (BenchmarkIngestLine still 0 allocs/op) because the closures are still bound once and only the record/resource fields move.
- **journald has the SAME cost levers as the tailer**: `logs.rules` (`Config.Rules`) and `logMetrics` (`Config.LogMetrics`) apply to journal entries too, in the tailer's order — metrics observe EVERY entry, rules run after enrichment (so `__severity__` sees the enriched severity) and a dropped entry still advances the cursor. `convert` keys one `logchain.Resolver` per call (record attrs → unit resource attrs, plus `logchain.SeverityKey`); a rules-configured convert builds each record in a one-record scratch and moves it across only when kept, pruning groups left empty. The `logs.rules` chain is compiled in `run()` (not `startLogs`) precisely because journald needs it with `-logs=false`. Previously journald had `logAttributes` and `logScrubbing` but neither, so the only way to sample down a node's kubelet/containerd chatter — which dominates a journal — was a Starlark transform. **The journal's ScopeLogs is now NAMED** (`otel_scope_name=github.com/JohanLindvall/kubescrape/agent/journald`, set in `convert`): every other producer named its scope and journald alone shipped an empty one. It is wire-visible — Loki/Elastic see a label change at the upgrade boundary, so every journal stream SPLITS there; expect a discontinuity in any query that groups on it.
- **PII scrubbing** (`agent/logscrub`, config `logScrubbing` section, shared by tailer/journald/ingest): curated built-in patterns (`builtin: [defaults]` = bearer/basic-auth/secret-kv/aws-key/private-key; `email`/`credit-card` opt-in by name) plus user regex rules, applied to log BODIES **before** logattrs/enrich/log-metrics copy from them (enrich's exception.stacktrace and lifted attributes must not carry secrets). Every built-in carries a prefilter so the no-match path is 0 allocs (~0.4µs/line for the default set, BenchmarkScrubNoMatch). **A prefilter's job is to admit only what the regex can MATCH, not what contains its keyword**: `secret-kv`'s scanned for the bare words key/secret/passw/pwd/token anywhere, and a 1 MiB record containing "token" then cost 100 ms of the SINGLE sweep goroutine that serves every log file on the node — the admission IS the cost. It now checks the regex's own tail shape in one pass with a first-byte dispatch (`secretKVCandidate`: keyword, optional `keySuffix`, `["']?\s*[:=]\s*["']?`, one value byte), which is 19x faster on that line (117ms → 6.1ms/MiB, BenchmarkScrubHostileLongLine) and 30% faster on ordinary lines. It must stay a strict SUPERSET of the regex — narrower means a secret ships unredacted, which `TestPrefilterIsNotNarrowerThanItsRegex`, `TestSecretKVPrefilterCoversEveryMatchingShape` and `FuzzSecretKVPrefilterNotNarrower` exist to catch (Go's `\s` is `[\t\n\f\r ]` and does NOT include `\v`, so treating `\v` as whitespace in the value class alone made it narrower). Unknown pattern names and bad regexes fail startup. Counts `obs.LogScrubbed{pattern}`. Log-metrics see the SCRUBBED line. LIMITATION: scrubbing is per-record, so a multi-line PEM key logged line-by-line (tailer/journald) only has its BEGIN line redacted — the base64 body lines are separate records lacking the telltale; a whole-key-in-one-record (JSON-embedded, or the ingest path) redacts fully.
- **Log-line attribute lifting** (`agent/logattrs`, config `logAttributes` section, shared by `-logs` and `-journald`): ordered rules map a JSON/logfmt key in the line to a resource/scope/log attribute. JSON is scanned once for all rule paths via `github.com/JohanLindvall/lightning/pkg/json` `GetPaths`+`DecodeAny` (dotted keys descend into nested objects); logfmt via the `logfmt` reader; do NOT reintroduce `encoding/json`. **`key= value` reads as an EMPTY value** since logfmt v0.0.10 (it yields `("key","")` and then the bare key `("value","true")`, go-logfmt's reading); v0.0.9 and earlier skipped the whitespace and read it as `("key","value")`, so a line written that way lifts an empty attribute — and mints an empty label in `internal/logline`, which shares the reader. `Iterate` still yields RAW values (quotes stripped, escapes intact): unescape with `AppendUnescape` (the pre-v0.0.10 name was `Unescape`), guarded by `NeedsUnescape` to skip the copy. Resource/scope attributes participate in the flush grouping key (`logGrouper` in the tailer, the `unit\x01res\x01scope` key in journald `convert`) so records with different line-derived resource/scope attrs split into distinct ResourceLogs/ScopeLogs; log-target attrs go on the record. Typed: JSON numbers with no fraction → PutInt, else PutDouble; bool → PutBool.
- **Unified positions** (`agent/positions`, flag `-positions-file`): one JSON file holding both the tailer's per-file `LogPos` map and the journald cursor. The `Store` keeps both sections in memory and rewrites the whole doc atomically under a mutex, so the tailer and journald (different goroutines, independent sections) never clobber each other. It is the ONLY offset persistence (the legacy standalone `-checkpoint-file` was removed); the tailer's `checkpoint` type is a `positions.LogPos` alias. **journald has no standalone cursor file** — its cursor persists only through `positions.Store` (`journald.Config.Positions`); without a positions store it starts at the journal tail each run.
- **OTLP ingest** (`agent/otlpingest`, opt-in `-ingest`): a gRPC (`:4317`) + OTLP/HTTP-protobuf (`:4318`, `/v1/logs`+`/v1/metrics`) receiver for LOGS AND METRICS apps push to the local agent. **TRACES ARE NOT HERE** — they are received by the `-service-graph` trace tier, because pairing an edge and sampling a trace both need every span of that trace in ONE process and a per-node receiver holds an arbitrary subset by construction; `ServerConfig.Exporter == nil` disables the logs/metrics services and routes entirely (traces-only mode, which is what the tier runs), and `Traces == nil` does the same for traces, so a sender aimed at the wrong receiver gets Unimplemented/404 rather than an ack for telemetry nothing will use. `ServerConfig.Ready` fires once every configured listener is BOUND (the HTTP arm is `net.Listen`ed explicitly rather than `ListenAndServe`d, so a bind failure is known before a readiness gate clears). `Enricher` finds a container id (`container.id`/`k8s.container.id`, configurable) or pod uid (`k8s.pod.uid`) on a resource, resolves via `metaclient` (Container = exact incarnation, else `PodByUID`), and merges the `attrs.Builders.Ingest` k8s attributes **without overwriting** anything the sender set. Metrics mode (`-ingest-metrics-mode`): `resource` (id on the resource), `datapoint` (id per point → `split.go` regroups every point into per-object ResourceMetrics, all 5 metric types; points with no id fall back to the resource-level id), or `auto` (resource if every RM has an id, else split). In a split group the resolved identity **overwrites** the copied sender attributes (`overwriteAttrs`) rather than merging: the sender is authoritative about ITSELF, not about the other objects it describes, so its own `k8s.pod.name`/`service.name` would otherwise mislabel every split point. `EnrichTraces` still exists and is used by the tier's entry path. **Peer-IP fallback** (`-ingest-peer-ip-fallback`, opt-in): a resource with NO id resolves via the connection's SOURCE address (`peer.go`: gRPC `peer.FromContext` / HTTP RemoteAddr → ctx; `Enricher.peerAttrs` → `metaclient.PodByIP` → `GET /v1/pod-ips/{ip}`; the store's `byPodIP` indexes LIVE, running-phase, non-hostNetwork pods only — deleted and Succeeded/Failed pods drop out immediately since pod IPs recycle); counts as `obs.Ingested{peer_ip}`; the splitter's ""-group applies the same fallback. **It is only correct at FIRST RECEIPT** — the address names the sender exactly once, on the hop the sender opened — which is why `Config.PeerReject` exists: a resolution the receiver vetoes (the tier vetoes its OWN workload's pods) is counted `obs.Ingested{peer_ip_rejected}`, warned once per minute and left UNENRICHED, and `peerAttrs` returns `(map, rejected)` so the caller does not also tally `unresolved` (the counter is per RESOURCE). Payloads are forwarded as received — deliberately NO agent-side ingest batching (an earlier `otlpbatch` layer got cut: it duplicated the collector's batch processor one hop early and was the only layer that traded a guarantee away; batch in the sender's SDK or the downstream collector, and every forward keeps the sender's own retry semantics). Log bodies additionally run `logenrich.ApplyBody` (non-overwrite variant) when `-enrich`. Counts into `obs.Ingested{enriched,unresolved,peer_ip,peer_ip_rejected}`. **Concurrency is BOUNDED** (`-ingest-max-in-flight`, `Server.inFlight` semaphore, `defaultMaxInFlight` 32, also fed to `grpc.MaxConcurrentStreams`): the listeners are unauthenticated and every in-flight request holds its body plus the inflated pdata, so an unbounded count is an OOM the process cannot defend against. Over the bound `acquire` refuses WITHOUT waiting (queueing would turn back-pressure into latency the sender cannot see) and the refusal is RETRYABLE so the sender keeps the payload: HTTP `429` + `Retry-After: 1`, gRPC `ResourceExhausted` **with an `errdetails.RetryInfo` detail** — the code alone reads as PERMANENT to conformant senders (OTLP makes it retryable only with RetryInfo, and both the OTel SDK and the Collector drop the batch without it), so a shed that loses the data would be worse than the OOM it prevents. **Memory is bounded SEPARATELY from the count** (`admit.go`, `byteBudget`, `maxBufferBytes` = 4 x the 16 MiB body cap): the count bounds PROCESSING and cannot bound BUFFERING, because the HTTP handlers read the whole body BEFORE taking a slot (holding one across a trickled 16 MiB upload let a few senders shed the whole node for a `ReadTimeout` — that is why the acquire moved after the read and must not move back) and grpc-go decodes a message before the interceptor runs (with connections uncapped, `MaxConcurrentStreams` bounds nothing server-wide). So the raw payload bytes get their own global, both-transports budget: an HTTP body is charged as it is READ (`budgetReader`, a declared `Content-Length` reserved before the first byte, `readAllCapped` pre-sizing the destination so the charge is not doubled by `io.ReadAll`'s growth) and held until the handler returns; a gRPC push reserves `MaxRecvMsgSize` in `grpc.InTapHandle` — the only pre-decode hook — released by whichever of the interceptor (decode done, the count takes over) and the stream ctx's `context.AfterFunc` comes first, since a leaked reservation would shed the listener for the process' life. A tap CAN carry the RetryInfo (`writeEarlyAbort` forwards status details), which an earlier comment here denied. Both refusals count `obs.IngestRejected`.
- **Span metrics** (`agent/spanmetrics`, opt-in `-ingest-span-metrics`, on the `-service-graph` TRACE TIER): RED metrics derived from received spans, following the OpenTelemetry spanmetrics conventions — a monotonic `traces.span.metrics.calls` counter, a `traces.span.metrics.size` byte counter, and a `traces.span.metrics.duration` histogram (seconds, with per-bucket trace-id **exemplars**), dimensioned by `service.name`/`span.name`/`span.kind`/`status.code` plus configurable extra span-then-resource attribute keys (`traceMetrics` config section: `namePrefix`/`buckets`/`dimensions`/`maxCardinality`/`exemplars`). Each span is aggregated INDEPENDENTLY, so the cumulative counters sum across shards — but the tap runs on the OWNING shard only (inside `buildOwnerChain`, below the pairing tap and above the sampler), so a span that took the internal re-shard hop is counted ONCE, not once per hop. It plugs in as a `TracesExporter` **tap** (`Generator.Tap`) wrapping the raw trace exporter: enrichment happened at the tier's entry, so the tap sees enriched spans (service.name populated); the tap forwards FIRST and aggregates only on success — a transient failure surfaces retryable all the way back to the application, whose re-push must not double-count. Consume runs on the concurrent receiver goroutines (each RPC owns its payload; the series map is mutex-guarded). The batch is forwarded UNCHANGED. The generator is a **self-contained cumulative aggregator** (`spanSeries` map keyed by the length-prefixed dimension tuple), NOT `metrics.Registry` — exemplars are a histogram-data-point feature the Registry cannot express, and owning the aggregation also gives the size counter and OTLP units a single home. A **cardinality cap** (`maxCardinality`, default 20000) bounds the data-driven label sets: a new tuple over the cap is dropped and counted (`obs.SpanMetricsDropped`), existing tuples always keep reporting (cumulative). **Stale series are evicted at render** (`staleAfter`, default 15m, `"0"` disables; `obs.SpanMetricsEvicted`) — without eviction the cap is a ONE-WAY LATCH, so one burst of high-cardinality span names permanently blinds RED metrics for every service that starts afterwards, and dead series render into every export forever. A series is evictable only once a DELIVERED export carried its current values (`spanSeries.state` observed→rendered→delivered, marked in `afterDelivered` beside the exemplar reset), so an export interval longer than `staleAfter` — or a failed export — never destroys observations unseen; a re-created series gets a FRESH per-series start timestamp, which is how OTLP spells the cumulative reset. The clock is read ONCE per `Consume` batch (injectable `Generator.now`), never per span. **Zero-alloc warm path**: `observe` builds the map key on a stack buffer and looks up via `map[string(key)]` (Go elides the copy for the read), materializing the dimension slice only when a genuinely new series is admitted — `BenchmarkConsume` is 0 allocs/op (`bench_test.go` guards it). Exemplars are one-per-latency-bucket, reset after each DELIVERED export (a failed send keeps them for the retry), and skip spans with no trace id; `exemplars: false` disables them. **`maxDimBytes` bounds RETAINED BYTES, so a retained value is CUT WITH A COPY** (`retainDim` in `dims()`; `truncDim` stays a bare reslice for the stack key, which the map copies on insert): slicing a Go string keeps the whole original alive, so a 256-byte label was pinning a sender's 4 MiB `span.name` for `staleAfter` — 33 MB measured at 8 series — which is exactly the bound the constant's comment promises. Cloning only on the truncating branch keeps the warm path at 0 allocs. `spanSize` is a cheap allocation-free byte estimate (name + ids + attributes + events + links), not the exact proto size. Exported on `-ingest-span-metrics-interval` (default 1m) via the shared metrics exporter, under the tier's own resource identity (`service.name=kubescrape-agent`+node, `agentSelfResource`) — the described service is a data-point dimension (`service_name` a label, not the metric's job). Naming follows the OTel Collector connector, NOT Grafana Tempo's metrics-generator (`traces_spanmetrics_*`/`SPAN_KIND_SERVER`); the values differ from Tempo in metric name and kind/status casing.
- **The trace tier / service graph** (`agent/servicegraph`, opt-in `-service-graph`, and the ONE pipeline that needs its own WORKLOAD): the workload that RECEIVES the cluster's OTLP traces and, from them, emits Grafana-Tempo-wire-compatible EDGE metrics — `traces_service_graph_request_total`, `_request_failed_total` (emitted at zero too, so the error ratio is defined before the first failure — Tempo creates it lazily) and the SEPARATE histograms `_request_server_seconds`/`_request_client_seconds` (two unsynchronised clocks measure them; their difference is the operator's to take), labels `client`/`server`/`connection_type` (`""`|`messaging_system`|`database`|`virtual_node`)/`virtual_node` plus configured dimensions as `client_<dim>`/`server_<dim>`. Both histograms carry per-latency-bucket **exemplars** (`serviceGraph.exemplars`, default true), following spanmetrics' rules — one per bucket, latest wins, cleared only after a DELIVERED export (a failed send keeps them for the retry), skipped for a span with no trace id. The trace id is the same on both halves BY CONSTRUCTION (it is half the pairing key, `edgeKey`); the SPAN id is each half's own (`Edge.ClientSpanID`/`ServerSpanID` — for the server half its own id, NOT the parent id it paired on), so each side's exemplar points at the span that measured that side. The exemplar timestamp is the shard's clock at pairing time (Tempo's behaviour). `Edge.Dimensions` is an ORDERED `[]EdgeDimension` whose order is canonical by construction (the client half's dimensions in the configured order, then the server half's — `joinDims`), because the metric layer keys a series on that sequence: an arrival-ordered one would give one edge two keys and render a byte-identical label set twice in one payload. It is also BORROWED — it aliases the pairing store's recycled buffers, so the sink runs before `retire` and a sink that retains an Edge must copy — which is what makes a dimensioned edge cost ZERO allocations (`BenchmarkConsumePairWithDimensions`/`TestConsumeWithDimensionsIsAllocationFree`). Its VALUES are cut by `retainDimValue` wherever something keeps them (the processor, whose half-edges live a whole `Wait`, and `edgeLabels`, whose labels live as long as the series) because truncating a Go string is a reslice that pins the whole original — a 256-byte label holding a sender's 4 MiB `peer.service`; `truncDimValue` stays a bare reslice only for `Record`'s stack key, which the map copies on insert (same defect and same fix as `agent/spanmetrics`). The names are Tempo's VERBATIM and spelled so BOTH the suffixes-on and suffixes-off OTLP→Prometheus translations reproduce them (the deliberate exception to the repo's OTel-dotted naming): Grafana's Service Graph view queries those exact strings. **Pairing cannot happen in the DaemonSet**: a request's two halves are emitted by two pods on two different NODES, so a per-node aggregator holds half of every edge by construction (the opposite of spanmetrics, where every span aggregates INDEPENDENTLY and the cumulative counters sum). **TWO LISTENERS, and the port decides the treatment** (`cmd/kubescrape-agent/servicegraph.go`): the APPLICATION ports (`-service-graph-ingest-grpc`/`-http`, `:4317`/`:4318`, an `otlpingest.Server` with `Exporter: nil` so it serves traces only) are UNAUTHENTICATED — every instrumented pod is a sender and a per-app credential is not a bargain most fleets can make — and the INTERNAL port (`-service-graph-listen=:4319`, `sgReceiver`) is bearer-authenticated because what arrives there is TERMINAL: already enriched, already routed. Loop-freedom is therefore STRUCTURAL, not a check that could be wrong (one directed edge, ingest port → internal port, and no edge out of the internal port; the internal path holds no Enricher and no Resharder at all) — a port cannot be forged by a payload the way an attribute can. `ForwardedMarker` (`kubescrape.service_graph.forwarded`) is the SECOND line, for the one easy misconfiguration (an internal hop addressed to `:4317`): the application path REFUSES a marked payload with `codes.InvalidArgument` (permanent, so the sender does not retry it forever) and counts `obs.ServiceGraphReshardStat.LoopsBlocked`; the owner STRIPS it on arrival (`StripForwarded`) so kubescrape plumbing never reaches the collector. **Enrichment happens at FIRST RECEIPT, never on the owner** — the connection's source address names the sender exactly once, on the hop the sender opened, and on the internal hop the peer is a SIBLING SHARD; `pipelines.peerIsOurOwnWorkload` (`sameWorkload`/`topOwner` over `selfmeta`'s pod) vetoes a peer-IP attribution resolving to this tier's own workload, counted `obs.Ingested{peer_ip_rejected}`, because an application's traces labelled with a kubescrape pod render perfectly and are wrong on every span. **`Resharder`** (`reshard.go`) splits a push by ring owner (`ring.go`, Tempo's FNV-1 32-bit `TokenFor`, tokens derived deterministically from the shard NAME rather than gossip-registered, so every shard computes the identical ring from the identical config), sends each remote share and returns the LOCAL one; `Self` (`-service-graph-shard-name`, default `$POD_NAME`) is what keeps 1/N of the traffic off the wire, and `singleOwner` passes a one-owner payload through with NO copy at all (a one-shard tier costs nothing). Trace-id-less spans stay LOCAL (unhashable, and every zero id shares one token) and count `SpansUnkeyed`. **The hop is SYNCHRONOUS and FAILABLE** — the entry shard holds the ONLY copy, so a dropped hop is a lost SPAN, not a lost edge: a failed send fails the application's push (`sgForwardStatus` maps the owner chain's error to a gRPC status / HTTP code the sender classifies correctly) and the sender's retry is the recovery. No queue, no `-buffer-dir`, `RetryAttempts: 1`; the bound on concurrent hops is the entry listener's in-flight semaphore. A part-way fan-out is at-least-once (the split is a pure function of the trace id, so the retry re-splits identically), which is safe precisely because both taps count only after a SUCCESSFUL export. **The owner chain** (`buildOwnerChain`) is `sgPairTap → spanmetrics.Tap → tracesample → collector`, forward-first-act-on-success at every layer, with the sampler at the BOTTOM so the graph and the RED metrics see 100% of spans (an edge is one request and the graph counts requests; a sampled chain would report 10% of the traffic as if that were the traffic). **Deployment surface** (`charts/kubescrape/templates/servicegraph.yaml` + `deploy/servicegraph.yaml`, values `serviceGraph.*`, off by default): a **StatefulSet**, never a Deployment — the ring addresses shards by stable ordinal DNS (`<sts>-<i>.<svc>.<ns>.svc`) behind a **headless** Service (`clusterIP: None`, `publishNotReadyAddresses: true`) for the internal hop, PLUS a ClusterIP `<release>-traces` Service that is where applications point their SDKs (round-robin is fine and wanted there; the internal hop is what undoes it). No volumeClaimTemplate (pairing state is in-memory by design — the StatefulSet buys NAMES, not storage), no ServiceAccount and no RBAC (the tier reads no Kubernetes API; it uses the metadata service over HTTP like any agent), `podManagementPolicy: Parallel`, every per-node pipeline off INCLUDING `-ingest` (that flag is the DaemonSet's logs-and-metrics receiver). `serviceGraph.replicas` renders BOTH the StatefulSet size and `-service-graph-shards` — the count is part of the ring's DEFINITION, so scaling is a `helm upgrade`, never a `kubectl scale`. `serviceGraph.ingest.allowFrom` is the NetworkPolicy `from` for the trace ports; EMPTY MEANS ANY POD MAY PUSH TRACES with no credential, which the template says in as many words. **Rendering does not hold the series lock**: `Registry.snapshot` copies each series' values out under `r.mu` — in `snapChunk`-sized chunks, walking a pointer slice taken in one cheap pass because a map cannot be walked across lock releases — and the pdata payload is built from that copy with the lock free. `Record` is called by the pairing store from INSIDE its own mutex (`upsert → emit → sink.Record`), so every millisecond the series lock is held is a millisecond in which no goroutine can Consume a span: at the 20k cardinality cap the build is ~50 ms and a probe measured a 46.7 ms `Record` stall inside a 46.7 ms render, now 1.6 ms (`TestRenderDoesNotStallRecord`). The scratch (`snap`/`snapPtrs`) is reused across renders under `renderMu` (lock order: `renderMu` before `mu`) and sized outside the lock; the snapshot keeps only the SET exemplars, since copying every bucket slot was 34 MB of memcpy under the mutex. The delivery-gated state machine is untouched — `evictLocked` and the `seriesRendered` marking still happen under `mu`, `afterDelivered` still promotes and clears the ORIGINALS. Tuning bounds all trade completeness for memory and all count when they bind (`obs.ServiceGraphExpired`/`ServiceGraphStoreFull`/`ServiceGraphDropped`/`ServiceGraphEvicted`) — a missing edge looks exactly like a call that never happened. **Honest downsides of this topology**: the tier is a hard cluster-wide dependency for traces (no per-node fallback), every span crosses the network twice at full fidelity, and one noisy service shares the shards with everyone else.
- **Service-graph config durations are STRINGS** (`Config.Wait`/`StaleAfter`, parsed by `Config.wait()`/`staleAfter()`): the agent config decodes through sigs.k8s.io/yaml → encoding/json, which takes only a raw nanosecond integer for a `time.Duration`, so the documented `wait: 10s` failed to decode — and `UnmarshalStrict` made that reject the WHOLE file, so both the DaemonSet and the shard StatefulSet failed to start. Same trap and same fix as `spanmetrics.Config.StaleAfter` and `traceSampling.keepSlowerThan`. Empty = the default; `staleAfter: "0"` DISABLES eviction (that `<= 0` branch in `Registry.evictLocked` was dead code while the field was a `time.Duration`, because `withDefaults` mapped 0 to 15m); an unparseable value is a `Validate` error naming the field and the value, while the constructors fall back to the default rather than refusing to aggregate. `Trim`'s fixed span-attribute floor (`keepSpanAttrs`) carries `db.system.name`/`db.namespace` beside Tempo's `db.system`/`db.name` — the shard's `namesDatabase` reads all four, and keeping only the old pair made semconv-1.30 support dead code in the one topology that exists (agent trims, shard reads); `mismatchWatch` cannot see it, since it compares only the CONFIGURED lists. Incremental expiry's budget SCALES WITH THE BATCH's span count (`min(SpanCount()+sweepFloorPerBatch, maxSweepPerBatch)`): a fixed per-Consume budget is a per-BATCH rate, and the batch size is the sender's choice — 1000 half-edges/s drained fine at 20-span pushes and dropped 54% at 200-span ones. A CLIENT/PRODUCER span with a ZERO span id is refused as unkeyable: its key would be (trace, zero), exactly where every ROOT SERVER span of that trace keys, so one malformed SDK invented edges between services that never called each other. `serviceGraphShards.port` defaults to `DefaultShardPort` = 4319, pinned against `-service-graph-listen` by a test in `cmd/kubescrape-agent` (it was 4317 — the agents' OWN ingest port, which the shard pods do not serve); with `protocol: http` the derived URL takes `https://` when TLS is asked for in ANY form (`caFile`, `insecureSkipVerify`, an explicit `insecure: false`) — otlpexport ignores `Insecure` for HTTP, so there the scheme IS the TLS decision and a skip-verify-only config used to go plaintext with the bearer token in the clear. `validateConfig` refuses `-service-graph` with BOTH listen flags empty (the runtime refusal existed; `-check-config` passed a config that CrashLooped the StatefulSet). **Honest limitation, documented as such**: an edge needs BOTH halves, so an uninstrumented callee appears only as a VIRTUAL NODE named from the client span's `peer.service`/`db.name`/`db.system`, and a client naming none of those yields no edge at all.
- **Trace sampling** (`agent/tracesample`, config `traceSampling` section, on the `-service-graph` trace tier): consistent per-trace-ID probabilistic sampling (xxhash of the trace id vs threshold — deterministic across retries AND across shards, so whole traces are kept) with keep-errors (default true) / keep-slower-than guard rails and a spans/second token-bucket cap (applied last, guard-rail keeps included). Wired near the bottom of `buildOwnerChain`, below both the spanmetrics tap and the pairing tap (and ABOVE tail sampling), so RED metrics and the service graph see 100% of spans while only the sampled subset ships; a payload sampled to nothing is acked without a send. Drops count `obs.TraceSpansDropped{reason=probability|rate}`.
- **Tail sampling** (`agent/tailsample` = the policy ENGINE, `agent/tailbuffer` = the BUFFERING/DECISION layer, config `tailSampling` section, opt-in on the `-service-graph` tier): whole-TRACE decisions. `tailbuffer.Buffer` holds a trace's spans keyed by trace id, calls `Evaluator.Decide` once `decisionWait` (5s) has elapsed since the trace was FIRST seen, and exports or discards the trace whole; the two halves meet ONLY at `Decide`, which is why the engine holds no traces and imports no `obs`. The section EMBEDS `tailsample.Config` (so `policies:` stays flat) and every duration is a STRING (`decisionWait`/`decisionCacheTTL`) for the sigs.k8s.io/yaml reason. **THE DELIVERY CONTRACT IS THE THING TO KNOW, and it is this repo's ONE departure from ack-gated at-least-once**: a pushed span is ACKED BEFORE its trace is decided — holding the RPC open for the window would pin an `-ingest-max-in-flight` slot for 5s and stall every sender in the cluster — so BUFFERED-BUT-UNDECIDED SPANS ARE LOST IF THE SHARD IS HARD-KILLED. No sender still holds them (a DECIDED keep is a different case — see below). Bounded three ways: by TIME (`decisionWait`), by SIZE (`maxSpans`), and by SHUTDOWN — `run()` calls `Buffer.Flush` after the receivers have joined and before the exporter closes, so a SIGTERM/rolling update loses nothing and only a SIGKILL/OOM/node failure does; and it is VISIBLE before it is spent (`kubescrape_tail_sampling_buffered_spans`/`_buffered_traces` are exactly what a hard kill would lose). **`maxSpans` is sized against REAL memory** (`memory.go`): the rule is `maxSpans x 1 KiB` must fit a QUARTER of the container's cgroup limit (or MemTotal when uncapped); `New` LOWERS an unset default that does not fit, warns above the share, and REFUSES an explicit ceiling whose spans alone need the whole limit. The loss mode is self-correlated — the likeliest hard kill is the OOM this buffer causes — so early decisions are the relief valve and the OOM is the failure. Kept out of `Config.Validate`, which stays shape-only for `-check-config`. **Bounds decide EARLY, never drop blind** (`enforce`): `maxSpansPerTrace` decides that trace on the spans present (its remainder then follows the verdict through the cache), `maxTraces` and `maxSpans` decide the OLDEST — the one closest to its natural decision, and picking the LARGEST would need a heap keyed by a count that changes per span and would systematically punish deep traces. The engine treats a partial trace as a LOWER BOUND (a slow trace can be missed, a fast one is never invented), which is what makes an early decision degrade gracefully where an eviction does not; each is counted `obs.TailSampleEarly{reason=spans_per_trace|max_traces|max_spans|shutdown}`. **The decision CACHE** (`cache.go`, bounded by entries AND TTL) is what a late span is measured against: forwarded immediately on a keep, dropped on a drop (`obs.TailSampleLate{outcome}`); the entry has TWO lifetimes — the VERDICT expires at `decisionCacheTTL` (a later straggler starts a FRESH window) while the record that the trace was DECIDED AT ALL survives to the SIZE cap, and `decide` passes it as `tailsample.Trace.Charged` so the re-decision PEEKS the `rateLimiting`/`composite` buckets instead of spending them again (`bucket.peek`). Eviction under the size cap is the only remaining double-charge, and `obs.TailSampleCacheEvicted` counts it — only for a still-LIVE verdict, since reclaiming an expired tombstone is the cache working; the map now sits at its cap rather than also draining by age. One mutex guards the map, the arrival FIFO, the tallies, the cache and the two receive-path grouping scratch maps; NO export ever runs under it (a slow collector would serialise every sender). The arrival FIFO is deadline-ordered by construction (one wait for all), so "oldest" is O(1) and removal from the middle is a `gone` flag skipped at the front — with `compact()`, because an ever-growing slice is the same bug as an unbounded map. **Composition** (`buildOwnerChain`, bottom-up): `sgPairTap → spanmetrics.Tap → tracesample → tailbuffer → collector`. Tail sampling is LAST because the graph and the RED metrics count REQUESTS; and it NESTS with the head sampler rather than compounding — both hash the trace id UNSALTED against the same threshold arithmetic, so a 50% tail policy keeps exactly what `probability: 0.5` passed (cross-package tests on both sides pin it). Caveat, now SAID OUT LOUD (`configWarnings` in `cmd/kubescrape-agent/config.go`, emitted by `-check-config` and every start): `traceSampling`'s guard rails are per SPAN, so `keepErrors`/`keepSlowerThan` deliver trace FRAGMENTS to a layer that judges whole traces and can export a trace that never existed. WARNED rather than refused because `keepErrors` DEFAULTS to true — refusing would reject `probability` + `tailSampling`, the most natural composition, and make the same effective config legal or illegal depending on whether the default was spelled out. `probability` (nests) and `maxSpansPerSecond` (overload valve) are the supported half. **A DECIDED keep is DURABLE with `-buffer-dir`**: `drain` marks its payload `otlpexport.Own(ctx)` (and `ExportTraces` marks a push whose `mine > 0` carries early-decided spans), so `Buffered` SPOOLS it instead of passing it through — a collector outage becomes a backlog, and `{outcome=lost}` then moves only if the spool itself refuses. Without a spool it is retried (`sendAttempts`, ctx-aware, permanent errors not retried) and then dropped + counted `obs.TailSampleSpans{outcome=lost}`. Spooling at BUFFER time instead was rejected: an fsync in the ack path is what the ack-first design exists to avoid, it writes 100% of spans to protect the ~1-10% kept, and the queue's in-order cursor could not retire a payload until every trace in it was decided (a restart would re-buffer already-exported traces). a failed forward of already-decided spans instead FAILS THE PUSH, since those are in the payload the sender still holds (its retry re-buffers the still-assembling spans of that payload — at-least-once, the same trade the re-shard hop makes). The receive path is allocation-disciplined (`bench_test.go`): the decided-drop path is 0 allocs/op (asserted), a buffered span costs the pdata copy and nothing else — no per-call maps, no per-span slices, counters and policy label values resolved at `New` from `Evaluator.Names()` so a policy that never fired reads as 0 rather than as an absent series.
- Tailer tests are timing-based: use `startTailer` (guarantees file creation happens after the initial scan — files present at startup are skipped to their end) and `tl.retryBackoff` to keep retry tests fast. A multi-line group that must survive across sweeps (e.g. straddling a rotation) needs **current** CRI timestamps on its lines (`timeNowCRI()`), not the usual hard-coded `2026-07-05`: the multiline stage's age-out (`FlushBefore`) runs against the real clock, so stale line timestamps flush the group before the continuation arrives.

### E2E in kind

`hack/otel-collector.yaml` deploys a contrib collector (debug exporter). Gotchas learned the hard way: with `verbosity: detailed` the collector's own stdout gets huge and kubelet rotates it within seconds (capture with `kubectl logs -f`, not `--since`); the agent must exclude the observability namespace (`-logs-exclude-namespaces`) or it feeds the collector its own output; after a collector rollout the agent's gRPC connection may keep delivering to the terminating pod for a while.
